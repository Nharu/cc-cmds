# 원격 답 — 원격으로 받은 선택지 답을 세션의 열린 질문에 넣는 규칙

원격 전송(텔레그램, 앱)으로 받은 선택지 답을, 세션이 열어 둔 질문(AskUserQuestion, 질문지, autopilot 승인 질문)에 넣는 규칙의 정본이다. 스풀 루트와 사건 기록, 처리 표지, `safe_sid`, 파일 만들기 규칙은 `plugins/cc-cmds/skills/_common/attention-event.md` 가 정하고, 이 문서는 그 위에서 봉투, 우편함, 수령 표지, 이음매 규약, 깨우기 리터럴, 원격 적용 기록, 게이트 응답 경로 필드, 중계의 결과 유도를 정한다.

이 문서는 형식을 고정할 뿐 코드를 싣지 않는다. 세션 이음매, 중계, 게이트의 응답 경로 필드는 뒤 티켓이 이 형식을 읽어 구현한다. 아래 네 표(`## 봉투 키`, `## 수령 표지 키`, `## 적용 기록 키`, `## 주소 규칙`)는 스키마 린트 `scripts/lint-remote-reply-schema.sh` 가 읽어 자기 목록과 대조하므로, 표 하나를 바꾸면 린트의 목록도 함께 바꾼다.

## 공용 문서와의 어긋남

`attention-event.md` 의 스풀 경로표는 세 가지에서 아직 옛 꼴이다. (1) 적용 기록 줄이 `applied/<tool_use_id>.json` 이지만 정본은 `applied/<reply_id>.json` 이다. 수령 표지의 `apply_by_ms`·`woken_at_ms` 칸, 경로마다 작성자가 자기 파일을 지우는 규칙, `woken_at_ms` 를 더하는 덧쓰기가 `mv -n` 이 아니라 `mv` 라는 것도 그 표에 없다. (2) 우편함·수령 표지·적용 기록 경로의 이름, 칸, 지우기 규칙은 이 문서와 베이스 설계의 주의 사건 레코드·스풀 계약을 따른다. 두 문서가 다르면 이 문서가 맞다. (3) 그 표를 이 문서와 맞추는 일은 베이스 설계에서 `attention-event.md` 를 소유하는 원격 자유 텍스트 답 작업의 몫이다. 그때까지 이 단락이 그 사실을 알린다.

## 고른 경로

두 이음매를 모두 쓰고, 기다리는 사전 도구 훅(상한 있는 기다림)은 쓰지 않는다.

- **S-open (모드 경합)** — 열린 AskUserQuestion 호출(일반 질문, 라우터 좌석의 승인 질문)에 대해 모드의 `tool.call` 이 로컬 대화창(`next(e)`)과 봉투 도착을 경합시킨다. 원격이 먼저면 `{result:{questions, answers}}` 를 돌려주고, 로컬이 먼저면 로컬 결과를 그대로 돌려준다. 기다림은 열린 호출마다 긴 `$` 호출 하나이며 `$.clock` 폴링 반복이 아니다. 대화창은 기다리는 동안 평소처럼 그려지고 손 답을 받으며, 손 답이 먼저 오면 원격 대기는 같은 순간 끝나고 대기 자식은 남지 않는다. 하네스의 시간 상한에는 걸리지 않는다.
- **S-open (질문지)** — 열린 질문지(모드 도구 `mcp__cc-cmds__question_form` 이 연 것)는 질문마다 `choose(..)` 를 부른 뒤 `finish('제출')` 로 답 묶음 텍스트를 제출한다. 질문지 도구는 호출을 곧바로 반환하므로 긴 기다림의 경합 지점이 없고, 세션 주소 질문지 봉투는 아래 타이머 살핌으로 알아챈다.
- **열린 승인 질문** — 승인 봉투의 대상에는 `tool_use_id` 가 없으므로, S-open 은 열린 승인 질문의 문면(`승인 <approval_id> — <질문>`)에 실린 승인 id 로 봉투를 찾는다.
- **S-at (사전 도구 훅)** — `hooks.json` 의 PreToolUse(AskUserQuestion) 항목이, 이 세션이 이미 수령한 런 주소 승인 봉투가 있고 그 봉투가 열린 호출에 대해 수락 조건을 모두 만족할 때만 곧바로 `allow` 와 `updatedInput.answers` 만 싣는 출력을 낸다. 없으면 출력 없이 곧바로 exit 0 으로 끝난다. 어떤 경우에도 기다리지 않는다 — 기다리는 동기 훅은 그동안 대화창을 가리고, `async: true` 훅의 답은 적용되지 않는다. S-at 의 항목은 기존 질문 좌석 훅과 병렬로 돌며 둘 사이의 순서 규약은 필요 없다.
- S-at 이 답한 호출에서는 S-open 의 `tool.call` 경합을 다시 돌리지 않는다.
- 세션 주소 봉투(`auq`·`question-form`)는 대상이 이미 열린 호출을 가리키므로 S-open 만 적용한다. S-at 은 런 주소 승인 봉투만 적용한다.
- tmux 키 입력은 어디에도 쓰지 않는다.

## 원격 답 규칙

- 첫 판의 봉투 종류는 `option` 하나다. `text`·`decision` 키는 첫 판 봉투에 없다.
- 모든 라벨은 그 질문의 선택지 라벨과 바이트로 같고, 기타 입력은 없다. `multi_select` 가 거짓인 질문, 질문지의 질문, 승인의 질문은 라벨이 정확히 하나다. 질문지는 모든 질문이 단일 선택이고 조건부 표시가 없을 때만 답할 수 있는 사건이므로 질문지 봉투도 질문마다 라벨 하나다.
- `answers` 는 대상의 모든 질문을 `question_index`(0부터) 오름차순으로 꼭 한 번씩 덮는다. 승인 대상은 질문 하나(`question_index` 0)다.
- `multi_select` 가 참인 질문의 라벨은 하나 이상이고 서로 다르다. 그 질문의 답 문자열은 봉투의 라벨들을 열린 호출의 선택지 순서로 늘어놓고 `, `(쉼표와 공백)로 이은 것이다. 봉투 안 라벨 순서는 따지지 않으므로 같은 라벨 집합은 같은 답 문자열과 같은 해시를 낳는다. 그런 질문의 선택지 라벨 중 하나라도 `, ` 를 담으면 그 봉투는 적용하지 않는다.
- 열린 호출의 한 질문에 같은 라벨의 선택지가 둘 있으면 그 봉투는 적용하지 않는다.
- 답 대상의 질문 문면이나 라벨이 바이트 0x1E 나 0x1F 를 담거나, `auq` 대상에 같은 문면의 질문이 둘 있으면 그 봉투는 적용하지 않는다. 답 해시의 구분자와 `toolUseResult.answers` 의 키가 모호해지기 때문이다.

## 필드 문법

- `reply_id` — 일반 사건 id 문법 `<host_id>.<epoch_ms>.<8 hex>`(확장 정규식 `^[a-z0-9-]{1,32}\.[0-9]+\.[0-9a-f]{8}$`), 앞부분이 봉투의 `host` 와 같다. 파일 이름이 되므로 안전 문자만 쓴다.
- `event_id` — 대상 사건의 id, `host` + `.` 로 시작한다.
- `host` — 호스트 id, `[a-z0-9-]{1,32}`(`$HOME/.config/cc-cmds/host-id` 의 한 줄, 파일이 없으면 `local`).
- `provenance.transport` — `[a-z0-9-]{1,32}`.
- `provenance.sender` — `[A-Za-z0-9_.@:-]{1,64}`. 발신자 인가 파일 `$HOME/.config/cc-cmds/remote-senders.json` 의 발신자 id(`tg:<from.id>` 또는 `app:<device key id>`)를 접두까지 그대로 담는다. 게이트 닫힘 행은 필드를 `|` 로 나누고 줄바꿈으로 행을 끝내며 값의 `|`·줄바꿈·이어진 공백을 고쳐 적으므로, 이 문법은 그 셋을 모두 막아 닫힘 행의 `원격 발신=<sender>` 값이 봉투의 `sender` 와 바이트로 같게 한다.
- `provenance.transport_ref` — 줄바꿈 없는 비지 않은 문자열.
- `provenance.received_at_ms` — 양의 정수, 전송이 받은 시각(밀리초).
- `expires_at_ms` — `received_at_ms` 보다 큰 정수.
- `pickup_by_ms` — 런 주소 봉투에만 있다. 값은 `min(<중계가 봉투를 쓴 시각> + 120000, expires_at_ms)` 이다. 기준은 전송이 받은 시각이 아니라 중계가 그 봉투를 쓴 시각이며, 만료 길이에 하한은 두지 않는다. 봉투에는 쓴 시각 칸이 없으므로 린트는 `received_at_ms < pickup_by_ms <= expires_at_ms` 만 본다. 세션 주소 봉투에는 없다.

## 봉투 키

`inbox/<addr>/<reply_id>.json`. 중계만 만들고 지운다. 키는 아래 표의 것뿐이며 모르는 키는 위반이다. 사건 하나에 봉투는 많아야 하나이고 그 봉투가 대상의 모든 질문을 덮는다. 끝난 사건의 봉투는 만들지 않는다. 만드는 법은 공용 문서의 파일 만들기 규칙(같은 디렉터리 점 임시 파일 + `mv -n`, 디렉터리 0700·파일 0600, 하위 디렉터리는 처음 쓸 때 만든다)이다.

| Key | Type | Value |
| --- | --- | --- |
| `schema` | number | `1` |
| `reply_id` | string | 봉투 id, `<host_id>.<epoch_ms>.<8 hex>`, 앞부분이 `host` 와 같다 |
| `event_id` | string | 대상 사건의 id, `host` + `.` 로 시작한다 |
| `host` | string | 호스트 id, `[a-z0-9-]{1,32}` |
| `kind` | string | `option` |
| `target` | object | 사건 `reply` 의 축자 사본, `surface` 는 `auq`·`question-form`·`approval` 중 하나이고 그 surface 의 필수 필드를 모두 가진다 |
| `answers` | array | `{question_index, labels}` 의 배열, 원격 답 규칙대로 |
| `provenance` | object | `transport`·`sender`·`received_at_ms`·`transport_ref` 네 키, 필드 문법대로 |
| `expires_at_ms` | number | `provenance.received_at_ms` 보다 큰 정수 |
| `pickup_by_ms` | number | 런 주소 봉투에만, `received_at_ms < pickup_by_ms <= expires_at_ms` |

`target` 의 surface 별 필드는 공용 문서의 답 대상 표 그대로다 — `auq` 는 `session_id`, `tool_use_id`, `questions[{question, header, multi_select, options[{label}]}]`, `question-form` 은 `session_id`, `form_id`, `questions[{id, question, options[{label}]}]`, `approval` 은 `run_id`, `approval_id`, `question`(`승인 <approval_id> — <질문>`), `options`(게이트의 라벨 문자열 배열).

## 주소 규칙

주소는 대상에서 정해진다. 그래서 린트는 봉투 하나만 보고 `pickup_by_ms` 가 있어야 하는지 판정한다. `safe_sid` 는 공용 문서의 정의 `${sid//[^A-Za-z0-9_.-]/_}` 를 그대로 쓴다.

| Surface | Address |
| --- | --- |
| `approval` | `r-<target.run_id>` |
| `auq` | `s-<safe_sid(target.session_id)>` |
| `question-form` | `s-<safe_sid(target.session_id)>` |

## 우편함

- **세션 주소** `inbox/s-<safe_sid>/` — 그 세션의 이음매만 읽는다.
- **런 주소** `inbox/r-<run_id>/` — 이음매는 자기 세션의 정방향 색인 `${XDG_STATE_HOME:-$HOME/.local/state}/cc-cmds/session/<세션 id>` 에 적힌 런 id 마다 런 주소를 살핀다. 가져가기 전에 그 런의 디렉터리 `${XDG_STATE_HOME:-$HOME/.local/state}/cc-cmds/run/<run_id>/session-lineage` 에 자기 세션 id 와 같은 줄이 있는지 확인한다. 색인은 후보를 찾는 데만 쓰고, 소속 판정은 계보 파일의 줄 일치다. 헤드리스 교대와 스테이지는 봉투를 가져가지 않는다.
- **살피는 간격** — 활성인 이음매는 런 주소의 봉투와 세션 주소의 질문지 봉투를 30초를 넘지 않는 간격의 타이머로 살핀다. 세션 주소의 AskUserQuestion 봉투는 타이머로 살피지 않고 S-open 이 열린 호출마다 긴 `$` 호출 하나로 기다린다. 「기다림은 긴 `$` 호출 하나이며 `$.clock` 폴링 반복이 아니다」 는 이 AskUserQuestion 경합의 기다림을 말하며, 열린 호출에 묶이지 않은 봉투를 찾는 타이머 살핌과 함께 선다. 살피는 방법과, 시계가 사람 입력 없이 멈췄을 때(거부된 주기에서 끝남 등) 사람 입력 없이 다시 거는 일은 이음매 구현 티켓의 몫이다.
- 수령 표지는 중계가 아니라 이음매가 쓰는 경로이며, 공용 문서의 단일 작성자 규칙은 경로 단위라 같은 디렉터리에 봉투와 표지가 함께 있어도 어긋나지 않는다. 공용 문서의 읽기 규칙은 `.json` 으로 끝나지 않는 이름을 무시하므로, 중계는 봉투 목록을 읽을 때 표지를 봉투로 읽지 않고 `<reply_id>.picked` 이름으로 따로 확인한다.

## 수령 표지 키

`inbox/<addr>/<reply_id>.picked`. 세션 이음매만 만들고 고치고 지운다. 키는 아래 표의 것뿐이다.

| Key | Type | Value |
| --- | --- | --- |
| `schema` | number | `1` |
| `reply_id` | string | 봉투의 `reply_id` |
| `session_id` | string | 표지를 만든 세션의 id |
| `picked_at_ms` | number | 양의 정수, 수령한 시각 |
| `apply_by_ms` | number | 적용 기한, `picked_at_ms + 120000` |
| `woken_at_ms` | number | 깨우기를 낸 시각, `picked_at_ms` 이상의 정수. 깨우기 전의 표지에는 없다 |

- **선점** — 이음매는 봉투를 적용할 수 있다고 판정한 뒤(런 주소는 호출과 무관해 수령 때 볼 수 있는 수락 조건 1·2·4·5 와 계보 소속·표지 없음, 세션 주소는 수락 조건 전부) 점 임시 파일을 쓰고 `mv -n` 으로 표지를 만든다. `mv -n` 의 종료 코드는 읽지 않는다. 대신 표지를 다시 읽어 `session_id` 가 자기 것일 때만 선점한 것으로 본다. 그래서 두 세션이 같은 런 주소를 살펴도 많아야 하나가 적용한다.
- **계보 이어받기** — 런 주소 봉투의 표지가 이미 있고 그 `session_id` 와 자기 세션 id 가 모두 그 런의 `session-lineage` 에 줄로 있으면, 이 세션은 수령된 봉투를 이어받아 적용할 수 있다. `--resume` 이 새 세션 id 를 주어도 재개된 세션이 표지를 이어받기 위해서다. 이어받은 세션은 표지의 `session_id` 를 고쳐 쓰지 않는다. 이어받기는 재개된 세션이 첫 게이트 호출을 한 뒤에만 성립한다 — 정방향 색인과 계보 줄은 게이트 진입에서 쓰이므로 그 전에는 새 세션 id 가 어디에도 없다. 그 전의 좌석은 런 주소를 찾지도 표지를 이어받지도 못하며, 그 사이 `apply_by_ms` 가 지나면 「세션 필요」가 날 수 있다. 이것은 받아들이는 한계다.
- **덧쓰기는 하나뿐이다** — 깨우기를 내는 세션이 `woken_at_ms` 를 더한 표지를 점 임시 파일로 쓰고 `mv` 로 덮어쓴다. 다른 키는 바꾸지 않는다.

## 이음매 규약

**활성 조건** — 대화형 터미널, 주 루프(agentId 없음), 그리고 라우터 판정 `cc_caller_is_router`(`plugins/cc-cmds/orchestrator/notify-run.sh`)가 읽는 파이프라인 표지 `CC_PIPELINE_SEGMENT`·`CC_PIPELINE_STAGE_ID`·`CC_PIPELINE_SHIFT_ID`·`CC_PIPELINE_REENTRY` 가 모두 비어 있음. 사람의 autopilot 라우터 좌석은 해당하고, 교대·스테이지·launchd 부팅 재진입은 해당하지 않는다.

**수락 조건** — 다음을 모두 만족해야 적용한다.

1. 봉투 `host` 가 이 기계의 호스트 id 와 같다.
2. 사건 기록 `events/<event_id>.json` 이 있고 `schema` 가 1 이며 `accepts` 에 `option` 이 있다.
3. 대상이 열린 호출과 바이트로 같다. `auq` 는 `target.tool_use_id` 가 열린 호출의 id 와 같고, 질문마다 `question`·`header`·`multi_select`·선택지 라벨 목록이 호출 입력과 같다. 대응은 `question` ↔ 호출 입력 `question`, `header` ↔ `header`, `multi_select` ↔ 호출 입력 `multiSelect`(키가 없으면 거짓), 라벨 목록 ↔ 호출 입력 `options[].label` 의 순서 목록이며, 문자열은 바이트로 비교한다(선택지 설명은 비교하지 않는다). 질문지는 `form_id` 와 질문마다 `id`·`question`·라벨 목록이 같다. 승인은 열린 호출의 질문이 정확히 하나이고 그 질문이 `target.question` 과 바이트로 같으며, 그 질문의 선택지 라벨을 각각 정규화한 집합이 `target.options` 의 집합과 같다. 정규화는 게이트의 `gate_menu_normalize` 와 같이 첫 ` ← ` 부터 끝까지를 떼는 것이다. 질문이 둘 이상인 호출에는 승인 봉투를 적용하지 않으므로 승인의 답 해시는 그 질문 하나를 덮는다.
4. 모든 라벨이 원격 답 규칙을 만족한다.
5. `now < expires_at_ms` 다.
6. 아직 적용되지 않았다 — `applied/<봉투의 reply_id>.json` 이 없고, 표지가 있다면 그 `session_id` 가 자기 것이거나, 런 주소 봉투에서 그 `session_id` 와 자기 세션 id 가 모두 그 런의 계보에 있다. 그리고 같은 대상 칸(`auq`·승인은 열린 호출의 tool_use_id, 질문지는 `form_id`)의 적용 기록이 이미 있지 않다. 그래서 호출 하나에 적용 기록은 많아야 하나다. 대상 칸으로 기록을 찾는 수단과, 이 확인을 적용 방식 (나)의 쓰기와 한 번에 묶는 수단은 이음매 구현 티켓이 정한다.
7. 세션 주소 봉투(`auq`·`question-form`)는 `provenance.sender` 가 발신자 인가 파일 `$HOME/.config/cc-cmds/remote-senders.json` 의 `senders[].id` 에 있고 그 발신자의 `capabilities` 에 봉투 `kind` 가 있다. 런 주소 승인 봉투에 대한 같은 재확인은 이 문서의 수락 조건이 아니며 게이트 원격 승인 티켓의 수락 조건이다. 그 전까지 같은 사용자의 프로세스가 스풀에 봉투를 써 승인 질문을 닫게 할 수 있는 위험은 받아들인 위험으로 남는다.
8. 질문지 봉투는 대상 질문 어디에도 사람의 초안(선택, 자유 입력, 메모 중 하나라도)이 없다. 초안이 있으면 원격 `choose(..)` 를 부르지 않고 그 봉투를 거절하며, 로컬 대화창은 그대로 남아 손 답을 받는다. 단일 선택 질문의 `choose` 는 이미 고른 라벨을 다시 누르면 선택을 풀므로, 이 조건이 없으면 사람이 먼저 고른 라벨을 원격 답이 비운 묶음이 제출되어 「적용됨」 으로 보고된다.

**적용 방식** — 순서는 고정이다.

- (가) 수령 표지를 만든다(아직 없을 때).
- (나) 적용 기록 `applied/<reply_id>.json` 을 쓰고, 다시 읽어 `reply_id`·`answers_sha256`·대상 칸(`tool_use_id` 키)이 이 봉투와 이 호출의 값일 때만 다음으로 간다. 기록이 없거나 다른 값이면 그 봉투는 거절 동작을 따른다.
- (다) 처리 탭으로 사건 슬롯에 원인 `reply-applied` 처리 표지를 남긴다.
- (라) 결과를 돌려준다. S-open 은 `{result:{questions, answers}}` 를, S-at 은 `allow` + `updatedInput.answers` 만 싣는 출력을 돌려준다.

질문지의 순서는 (가), (라), (나), (다)다. 질문지의 (라)는 결과 반환이 아니라 질문마다 `choose(..)` 뒤 부르는 제출이며, 그 제출은 기록을 소비했는지와 제출한 답 묶음 텍스트를 이음매에 돌려준다. (나)의 적용 기록은 그 반환을 받은 뒤 쓰고 `answers_sha256` 은 돌려받은 텍스트로 계산한다. 제출이 기록을 소비하지 못했으면(사람이 먼저 제출하거나 취소함) 적용 기록과 처리 표지를 쓰지 않으며, 그 경합은 로컬이 이긴 것이다. 질문지에서 (나)의 다시 읽기가 어긋나면 처리 표지를 쓰지 않고, 이미 난 제출은 되돌리지 않는다. 현재 트리의 `finish` 는 기록을 소비하지 못하면 호출자에게 알리지 않고 값 없이 돌아오므로, 소비 여부와 제출한 텍스트를 돌려주는 제출은 이음매 구현 티켓이 만든다. (라)와 (나) 사이에 세션이 끝나면 원격 답은 제출됐지만 적용 기록이 없어 결과가 적용됨이 되지 않는다. 제출되지 않은 답에 적용됨이 나가는 반대 경우보다 나으므로 이 한계를 받아들인다. 「결과를 돌려주기 전에 먼저 기록한다」 의 결과는 하네스에 돌려주는 도구 결과(S-open 의 `result`, S-at 의 `updatedInput`)이고 질문지에는 그런 결과가 없으므로, 이 순서는 그 규칙과 어긋나지 않는다.

**답 문자열** — 결과의 답 문자열은 질문마다 봉투 라벨(다중 선택은 원격 답 규칙의 이은 문자열)이다. 승인은 열린 호출의 그 질문의 선택지 중 정규화한 값이 봉투 라벨과 같은 **호출 쪽 라벨 그대로**다. 그래서 라우터가 붙인 ` ← 추천` 꼬리가 있어도 손 답과 같은 값이 기록된다.

**결과 기록의 모양** — 적용된 답은 하네스가 쓴 도구 결과이며, 게이트 프레임 조건이 읽는 필드(`toolUseResult.answers`)가 로컬 답과 같다. S-at 출력이 `updatedInput.questions` 를 싣지 않는 것은 그 때문이며, 게이트가 답 해시에 쓰는 `input.questions` 는 assistant 줄의 `tool_use` 입력이라 S-at 출력에 기대지 않는다. AskUserQuestion 결과 기록(전사 안의 도구 결과)에는 원격 표지를 넣지 않는다. 원격 승리 결과의 `toolUseResult` 에는 손 답 회차의 `annotations` 가 없으며, 이음매는 그것을 채우지 않는다.

**거절 동작** — 수락 조건 하나라도 어긋나면 그 봉투로 아무것도 하지 않는다. 로컬 대화창은 그대로 남아 손 답을 받고, 적용 기록·처리 표지를 쓰지 않으며, 세션 주소 봉투에는 수령 표지도 쓰지 않는다. 오류를 화면에 내지 않는다. 결과는 중계가 파일에서 유도한다. 만료 뒤에는 늦게 적용하지 않는다. 이음매는 거절 파일을 쓰지 않는다.

**로컬 우선** — 로컬 대화창은 언제나 먼저 그려지고 쓸 수 있다. S-open 은 대화창을 막지 않고 경합할 뿐이며, S-at 은 기다리지 않는다. 세션은 스스로 대화창을 열거나 프롬프트를 제출하거나 자기가 열린 것을 보지 못한 호출에 답하지 않는다. 예외는 깨우기 프롬프트와, 질문지 봉투를 적용하는 `finish('제출')`(질문지의 기존 전이가 안에서 `$.prompt.submit` 을 부른다)이다.

**쉬는 라우터 좌석의 수령 (종단 요구)** — 쉬고 있는 라우터 좌석은 사람 입력 없이 런 주소 봉투를 수령하고 적용한다. 타이머 살핌, 계보 이어받기의 시점, S-at 출력 꼴은 이 요구를 이루는 부분이다. 「쉬고 있음」 은 마지막 사람 입력 뒤 경과 시간이 문턱을 넘었고 진행 중인 도구 호출이 없는 것이다. 그 문턱 값과 이 요구의 검증은 이음매 구현 티켓의 수락 조건이다.

**자리 비움 자동 해소** — 경합에서 로컬과 원격 중 어느 쪽이 이겼는지는 이음매가 스스로 안다. 로컬이 이기면(자리 비움 자동 해소 포함) 로컬 결과로 그대로 두고 적용 기록을 쓰지 않으며, 원격이 이긴 경우에만 적용 기록을 쓴다. 질문지에서는 제출이 기록을 소비했는지가 그 승자다. 결과의 필드 이름으로 자리 비움을 가리지 않는다.

**귀환 훅과의 순서** — AskUserQuestion 봉투는 적용 방식 (다)가 결과 반환 전에 일어나므로, 반환 뒤 사후 도구 훅 쪽에서 처리 표지가 어떤 원인으로 남든 `reply-applied` 가 먼저다. 공용 문서의 읽기 규칙은 사건보다 늦은 가장 이른 표지의 원인을 쓰므로 원인은 `reply-applied` 로 읽힌다. 사후 도구 훅의 귀환 정리는 원격 답이 적용된 호출에도 로컬 답과 같이 돌아 그 세션의 배너를 거둔다. 질문지는 (다)가 제출 뒤에 오므로 이 순서가 서지 않으며, 질문지 봉투의 결과는 적용 기록이 먼저 정하므로 처리 표지의 원인에 기대지 않는다. 귀환 훅은 고치지 않는다.

## 깨우기 리터럴

```text
<cc-remote-approval run=<run_id> id=<approval_id>/>
```

- 한 줄, 앞뒤 공백 없음. `<run_id>` 는 `[A-Za-z0-9-]{1,64}`, `<approval_id>` 는 `[A-Za-z0-9_-]{1,55}-[0-9a-f]{8}` 다. 린트가 쓰는 확장 정규식은 `^<cc-remote-approval run=[A-Za-z0-9-]{1,64} id=[A-Za-z0-9_-]{1,55}-[0-9a-f]{8}/>$` 이다. 고정 예제 파일의 내용은 이 한 줄이며 끝 개행 하나는 허용하고, 줄이 둘 이상이면 위반이다.
- **내는 조건** — 이음매는 자기 세션이 수령한(계보로 이어받은 것 포함) 승인 봉투가 있고, 그 봉투가 만료 전(`now < expires_at_ms`)이며, 그 사건이 공용 문서의 읽기 규칙으로 처리됨이 아니고, 그 대상과 맞는 승인 질문이 열려 있지 않고, 세션이 쉬고 있을 때 그 봉투마다 한 번 이 프롬프트를 플러그인 출처로 낸다.
- **한 번** 은 수령 표지의 `woken_at_ms` 로 기억한다 — 표지에 `woken_at_ms` 가 없을 때만 내고, 내기 직전에 표지에 `woken_at_ms` 를 남긴다. 그래서 세션이 재개되어도 깨우기는 되풀이되지 않는다. 깨우기의 기한은 수령 표지의 `apply_by_ms` 가 함께 진다. 적용이 끝난 봉투는 `reply-applied` 처리 표지로 처리됨이 되므로 이 조건으로 함께 빠진다.
- 라우터가 정규 승인 질문을 열면 S-at 이 곧바로 답한다. 라우터가 이미 그 승인 질문을 열어 둔 채였다면 S-open 이 문면의 승인 id 로 봉투를 찾아 답한다.
- 이 리터럴은 귀환 훅(`plugins/cc-cmds/hooks/session-return-dismiss.sh`)의 봉투 꼴 정규식에 맞고 붙여넣기 예외에는 맞지 않으므로 귀환으로 읽히지 않고 세션의 배너를 거두지 않는다.

## 적용 기록 키

`applied/<reply_id>.json`. 세션 이음매만 만들고 지운다. 이음매가 결과를 돌려주기 전에 쓴다(질문지는 위 적용 방식의 순서). 파일 이름은 봉투의 `reply_id` 이므로 중계는 봉투 하나의 적용 기록을 파일 이름으로 바로 찾는다. 키는 아래 아홉뿐이며 `transport`·`sender` 는 봉투 `provenance` 에서 옮긴다. 만드는 법은 공용 문서의 파일 만들기 규칙이다.

| Key | Type | Value |
| --- | --- | --- |
| `schema` | number | `1` |
| `tool_use_id` | string | 대상 칸 — `auq`·승인은 열린 호출의 tool_use_id, 질문지는 대상의 `form_id` |
| `session_id` | string | 적용한 세션의 id |
| `reply_id` | string | 봉투의 `reply_id`, `<host_id>.<epoch_ms>.<8 hex>` |
| `event_id` | string | 봉투의 `event_id` |
| `answers_sha256` | string | 답 해시, 소문자 16진 64자 |
| `transport` | string | 봉투 `provenance.transport` |
| `sender` | string | 봉투 `provenance.sender` |
| `applied_at_ms` | number | 양의 정수, 적용한 시각 |

**`answers_sha256` 의 원상 (AskUserQuestion 대상 — 일반 질문과 승인)** — 열린 호출 입력의 `questions` 순서대로, 질문마다 `question` 의 UTF-8 바이트, 바이트 0x1F, 돌려주는 `answers[question]` 문자열의 UTF-8 바이트, 바이트 0x1E 를 이어 붙인 바이트열이다. 그 sha256 의 소문자 16진 64자. 이음매와 게이트가 같은 식으로 계산한다. 게이트 쪽은 전사에서 이은 AskUserQuestion `tool_use` 의 `input.questions` 순서와 `toolUseResult.answers` 로 같은 바이트열을 만든다 — `jq -j` 로 질문 문면, `"\u001f"`, 답, `"\u001e"` 를 차례로 출력해 `shasum -a 256` 에 넘긴다. 답 하나라도 문자열이 아니거나 없으면 맞지 않는 것으로 본다.

**`answers_sha256` 의 원상 (질문지 대상)** — 제출이 기록을 소비한 뒤 이음매에 돌려준 답 묶음 텍스트, 곧 실제로 제출된 텍스트(현재 트리에서는 `$.prompt.submit({ text: bundleText(…) })` 의 `text`)의 UTF-8 바이트 그대로다. 사람이 그 사이 칸에 쓴 자유 입력·메모가 묶음에 들어가도 해시는 제출된 바이트를 덮는다. 질문지에는 돌려주는 `answers` 맵이 없으므로 AskUserQuestion 꼴의 원상을 쓰지 않는다.

이 해시는 게이트 닫힘 행의 기존 `답변 다이제스트`(승인 id 슬롯 하나의 답 문자열의 sha256)와 원상이 다르며, 닫힘 행에 옮기지 않는다. 응답 토큰과 `답변 다이제스트` 의 뜻은 바뀌지 않는다.

## 게이트 응답 경로 필드

게이트 원격 승인 티켓이 `gate.sh` 에 넣는다. 이 문서는 필드 이름, 값, 조회 규칙만 고정한다.

- **대상 행** — 기록 틀로 닫힌 승인 행(`응답 토큰` 과 `답변 다이제스트` 가 모두 `-` 가 아닌 행)뿐이다. 자유 입력이나 슬롯 부재로 승인을 `상태=대기` 로 다시 적는 행은 `응답 토큰` 을 싣지만 `답변 다이제스트` 를 싣지 않으므로 대상이 아니다. 자동 닫힘 행은 바꾸지 않는다.
- **조회** — 스풀 루트 아래 `applied/` 의 기록 중 대상 칸 `tool_use_id` 가 응답 토큰과 같은 것. 응답 토큰이 곧 tool_use_id 다. 적용 기록의 파일 이름은 `reply_id` 이므로 게이트는 파일 이름으로 찾지 못하며, `applied/` 를 내용으로 훑지 않고 대상 칸으로 기록을 좁혀 찾는다. 그래서 작성자가 사라진 기록이 쌓여도 조회 길이가 늘지 않는다. 좁히는 수단은 게이트 원격 승인 티켓이 정한다. 호출 하나에 적용 기록은 많아야 하나이므로 찾는 기록도 많아야 하나다.
- **스풀 루트** — 게이트는 스스로 `CC_CMDS_ATTENTION_ROOT` 를 읽지 않는다. 탭 라이브러리 `plugins/cc-cmds/orchestrator/attention.sh` 의 내부 도우미 `cc_attention__root` 를 공개 함수로 열고 게이트는 그 함수를 불러 스풀 루트를 얻으므로, 그 값을 읽는 자리는 라이브러리 안의 하나로 남는다. 함수를 여는 변경은 이 필드를 넣는 티켓이 한다. 스풀 루트는 그 값이 비어 있지 않으면 그 값, 아니면 `$HOME/.local/state/cc-cmds/attention` 이며 `XDG_STATE_HOME` 을 따르지 않는다. 게이트 안의 상태 루트 관례 `${XDG_STATE_HOME:-$HOME/.local/state}`(런 디렉터리와 세션 색인의 뿌리)와 다른 것이다.
- **값** — 기록이 있고 `schema` 가 1 이며 `tool_use_id` 가 응답 토큰과 같고 `answers_sha256` 이 위 원상으로 다시 계산한 값과 같으면 기존 필드 뒤에 `응답 경로=원격` `원격 발신=<sender>` 를 더한다. 그 밖에는 `응답 경로=로컬` 하나를 더한다. `sender` 가 발신자 id 를 접두까지 담으므로 닫힘 행에 `transport` 를 붙이지 않는다.
- **길이 예산** — 필드를 더하는 쪽은 더하기 전에 `gate_row_projected_bytes` 로 더한 뒤의 행 길이를 재어 본다. `GATE_ROW_MAX` 를 넘으면 `원격 발신` 필드를 먼저 빼고, 그래도 넘으면 `응답 경로` 필드도 뺀다.
- 기존 필드와 감사 사다리의 단계는 바뀌지 않고 필드는 더하기만 한다. 기록이 없거나 어긋나거나 길이 예산에 걸려도 승인 닫힘을 막지 않고, 기록 틀이 아닌 것을 닫힘으로 만들지 않는다.

## 중계가 결과를 읽는 법

**종단 요구** — 봉투 하나의 결과는 그 대상 호출의 실제 결말과 일대일로 맞는다. 결말은 원격 답 적용, 로컬 답, 좌석의 거절, 좌석 부재 넷이고, 그 짝은 원격 답 적용 → 적용됨, 로컬 답 → 처리됨, 좌석의 거절 → 거절, 좌석 부재 → 세션 필요(그 뒤 만료에 거절)다.

봉투 하나의 결과는 아래 순서로 처음 맞는 것이다. 이음매는 거절 파일을 쓰지 않으므로 결과는 파일에서 유도한다.

1. `applied/<reply_id>.json` 이 있다 → 적용됨.
2. 사건이 공용 문서의 읽기 규칙으로 처리됨이고 그 원인이 `reply-applied` 가 아니다 → 처리됨. 현재 트리에는 `reply-applied` 밖의 원인으로 처리 표지를 쓰는 운영 코드가 없으므로 이 결과는 지금은 생기지 않는다. 원인이 `reply-applied` 인 표지는 그것만으로 이 봉투의 결과가 되지 않는다. 중계는 적용 기록의 대상 칸(`tool_use_id` 키)과 이 봉투의 대상(`auq` 는 `target.tool_use_id`, 질문지는 `target.form_id`)을 대조한다. 같은 대상 칸의 적용 기록이 없으면 그 표지를 이 봉투의 결과로 보지 않고 다음 규칙으로 간다. 같은 대상 칸의 적용 기록이 다른 `reply_id` 로 있으면 그 호출은 다른 봉투의 원격 답으로 끝난 것이므로 처리됨이다. 승인 봉투의 대상에는 대상 칸과 대조할 값이 없으므로 `reply-applied` 표지는 승인 봉투의 결과가 되지 않는다. 대상 칸으로 기록을 찾는 수단은 중계 티켓이 정한다.
3. 중계가 그 봉투에 「세션 필요」를 아직 알리지 않았고, (가) 런 주소 봉투이며 `<reply_id>.picked` 가 없고 `now >= pickup_by_ms` 이거나, (나) `<reply_id>.picked` 가 있고 `now >= apply_by_ms` 이다 → 세션 필요. 봉투마다 한 번 알리고 봉투는 만료까지 둔다. 알렸다는 사실은 중계가 스풀의 `relay/` 아래 자기 기록에 남기며, 그 형식은 중계 티켓이 정한다.
4. `now >= expires_at_ms` → 거절.
5. 그 밖 → 대기.

「세션 필요」 를 만료 거절보다 먼저 보므로 `pickup_by_ms` 가 만료로 접혀도 「세션 필요」 가 나간다. 그 뒤에도 만료 전에 적용 기록이 생기면 결과는 적용됨이다(1번이 먼저다).

**받아들이는 한계** — 이 규칙이 종단 요구를 지키지 못하는 경우는 다음 다섯이며, 이음매 구현 티켓과 중계 티켓의 수락 조건으로 넘긴다.

- 초안이 있어 거절된 질문지 봉투 — 세션 주소 봉투는 거절 때 수령 표지를 쓰지 않으므로 결과는 만료에 거절이다. 사람이 그 질문지에 이어 답하면 실제 결말은 로컬 답이다.
- 같은 세션의 형제 사건이 로컬로 답해진 봉투 — 그 세션 슬롯의 표지가 다른 사건의 `reply-applied` 뿐이면 2번이 그 표지를 이 봉투의 결과로 보지 않으므로, 결과는 대기를 거쳐 만료에 거절이다.
- 로컬 답이 이긴 봉투 — 처리 표지를 쓰는 운영 코드가 없어 처리됨이 나가지 않는다. 수령 표지가 남은 봉투는 「세션 필요」 뒤 만료에 거절이고, 남지 않은 봉투는 만료에 거절이다.
- 같은 호출에 걸린 둘째 봉투가 승인 봉투인 경우 — 수락 조건 6 으로 거절되지만 승인 봉투는 2번의 대상 칸 대조가 없으므로, 수령 표지가 남아 「세션 필요」 로 보고된다.
- 호출 단계의 수락 조건(3, 6)에서 거절된 런 주소 봉투 — 수령 표지가 남아 `apply_by_ms` 에 「세션 필요」 로 보고된다. 실제 결말은 좌석의 거절이다. 수령 때 볼 수 있는 조건은 수령 판정이 먼저 보므로 이 경우는 열린 승인 질문이 봉투와 맞지 않을 때로 좁혀진다.

중계가 처리 표지와 적용 기록을 읽는 것은 중계 티켓의 소비 계약에 아직 없는 읽기다.

## 봉투 하나의 수명 주기

봉투 하나는 받힘 → 수령 → 깨우기 → 적용 또는 거절 → 정리로 간다. 위 결과 유도는 이 표를 따른다. 지우는 주체는 각 경로의 작성자다.

| 단계 | 남는 파일 | 작성자 | 다음 단계까지의 기한 | 기한을 넘기면 중계가 내는 결과 | 지우는 주체 |
| --- | --- | --- | --- | --- | --- |
| 받힘 | `inbox/<addr>/<reply_id>.json` | 중계 | 런 주소: `pickup_by_ms`(중계가 봉투를 쓴 시각 + 2분과 만료 중 이른 값). 세션 주소: `expires_at_ms` | 런 주소: 「세션 필요」 한 번, 그 뒤 만료에 거절. 세션 주소: 만료에 거절 | 중계(결과를 낸 뒤 사건과 함께 7일 정리 때) |
| 수령 | `inbox/<addr>/<reply_id>.picked`(`woken_at_ms` 없음) | 세션 이음매 | `apply_by_ms`(수령 뒤 2분). 만료가 먼저 오면 만료 | `apply_by_ms` 에서 「세션 필요」 한 번, 그 뒤 만료에 거절. 만료가 먼저 오면 거절만 내며, 거절은 끝 결과이므로 그 뒤 `apply_by_ms` 가 지나도 「세션 필요」 를 내지 않는다 | 세션 이음매(봉투가 사라진 뒤, 활성일 때) |
| 깨우기(런 주소 승인 봉투만) | 같은 표지에 `woken_at_ms` | 세션 이음매(깨우기를 낸 세션) | 수령 단계의 `apply_by_ms` 를 그대로 진다 | 수령 단계와 같다 | 세션 이음매(봉투가 사라진 뒤, 활성일 때) |
| 적용 | `applied/<reply_id>.json`, `handled/<id>.json`(원인 `reply-applied`) | 세션 이음매, 처리 탭 | 없음(끝) | 적용됨 | 적용 기록은 세션 이음매(봉투가 사라진 뒤), 처리 표지는 공용 문서의 처리 표지 규칙대로 |
| 로컬 승리(사람의 답 또는 자리 비움 자동 해소가 먼저) | 새 파일 없음. 질문지 봉투와 수령한 런 주소 승인 봉투는 앞 단계의 수령 표지가 남는다 | 없음 | 수령 표지가 있으면 `apply_by_ms`, 없으면 `expires_at_ms` | 표지가 있으면 「세션 필요」 한 번, 그 뒤 만료에 거절. 표지가 없으면 만료에 거절. 처리됨이 나가지 않는 것은 받아들이는 한계다 | 수령 표지는 세션 이음매(봉투가 사라진 뒤, 활성일 때) |
| 거절 | 새 파일 없음 | 없음 | 없음(끝) | 거절 | 해당 없음 |
| 정리 | 없음 | 없음 | 없음 | 없음 | 위 각 행의 작성자 |

- 어느 단계에서든 사건이 공용 문서의 읽기 규칙으로 처리됨이고 그 원인이 `reply-applied` 가 아니면 결과는 처리됨이다. 현재 트리에서는 이 결과가 생기지 않으며, 처리 표지 배선은 뒤 티켓의 몫이다.
- 세션 이음매는 봉투가 사라진 것을 중계가 결과를 낸 표지로 읽고, 봉투가 없는 `.picked` 와 `applied/<reply_id>.json` 을 활성일 때 지운다. 지우는 쪽은 작성자 역할이며 그 파일을 쓴 세션 하나가 아니다. 중계는 이음매의 파일을 지우지 않고, 이음매는 봉투를 지우지 않는다.
- 다시 활성화되지 않는 세션(끝난 세션, 계보로 잇지 않는 다른 id 로 재개된 세션)이 쓴 수령 표지와 적용 기록은 지울 주체가 없다. 그것이 쌓이는 것을 받아들이며, 쌓임이 게이트 조회 길이에 주는 영향은 대상 칸 조회가 막는다. 작성자 밖의 정리 주체는 게이트 원격 승인 티켓의 위험으로 남는다.
- 적용 단계의 적용 기록은 만든 뒤 다시 읽어 확인한다.
- 질문지 봉투는 제출이 기록을 소비했을 때만 적용 단계로 간다. 소비하지 못하면 적용 기록·처리 표지가 생기지 않으므로 결과는 적용됨이 아니다.

## 고정 예제와 린트

고정 예제는 `tests/fixtures/remote-reply/` 에 있고 파일 이름 앞부분이 종류를 정한다 — `envelope-<이름>.json`(봉투), `picked-<이름>.json`(수령 표지), `applied-<이름>.json` 과 짝 `submit-<이름>.txt`(질문지의 제출 바이트) 또는 `frame-<이름>.jsonl`(전사 두 줄), `wake-<이름>.txt`(깨우기 리터럴). 린트는 `scripts/lint-remote-reply-schema.sh`, 그 시험은 `scripts/test-lint-remote-reply-schema.sh` 이며 둘 다 `make lint`·`make test` 에 걸려 있다.
