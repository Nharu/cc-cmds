# Sidecar File Contract (Shared SOT)

Single source of truth for **out-of-document sidecar files** — the `docs/<kind>/{slug}.md` artifacts a skill writes *beside* a design document rather than into it. `## 1` owns the mechanics every sidecar shares regardless of payload (slug derivation, the provenance guard, atomic write, lifetime, versioning). `## 2` owns the block schema of the **re-convergence sidecar**, the artifact that carries an `implement`-time refutation across a session boundary to a `design` re-convergence.

**Why a sidecar rather than an in-document section.** A design document has a one-writer-per-section invariant, and each writer's byte surface is enumerated so a sweep can prove no other byte moved. A second writer wanting durable state therefore cannot take a new in-document section without enlarging that surface — and an enumerated write surface is the machinery of a *permanent* ledger, not of every feature that needs to remember something. A sidecar keeps the document's surface unchanged, is unaffected by any future re-synthesis of the document — a re-synthesis path would carry no obligation toward a section it does not enumerate, and today no such path exists — and costs nothing in permanence: the sidecar sits in the same tree beside the document it belongs to, so it inherits exactly the document's own **retention class**. Whatever the owning repo grants the design document it grants the sidecar, and an in-document write therefore buys no permanence the sidecar lacks.

**What this file owns vs. what each SKILL.md owns.** This file is *contracts-only*: paths, grammars, schemas, predicates, and write mechanics. It deliberately excludes *workflow prose* — when a writer decides to write, what it reports to the user, and how a reader routes what it finds all live in the owning SKILL.md. A skill that writes or reads a sidecar Reads this file; it never re-authors the grammar.

**Consumption matrix — each consumer's subset is named, because they are disjoint.** A consumer citing `## 1` does not thereby adopt all of it, and the landed three demonstrate that: the subsets they take do not even overlap. `design-audit` Reads **§1.1 only** at Step 1, unconditionally, as both writer and reader of `<kind>=design-audit` (the audit report keyed to the document it audits) — **landed**. Its payload schema is not in this file: an audit report is a single-writer artifact whose block grammar the owning SKILL.md carries. `review` Reads **§1.1 + §1.2** with `## 3` when a design document is supplied to it, to ground a `design-conformance` finding (reader, never a writer) — **landed**. `implement` Reads **§1.1–§1.5** with `## 3` when it records a deviation from the design document (writer of the design-drift sidecar) — **landed**. Two consumers of `## 2` remain unlanded: `implement` at a verification failure branch (writer of the re-convergence sidecar) and `design` at its re-convergence sidecar check (reader).

**What "landed" does and does not certify.** It certifies that a skill Reads this file at a named step. It does **not** yet certify that the mechanics are performed: **no landed consumer executes the compare-and-swap of §1.3** — `design-audit` writes its report with ordinary tooling, and `gate_write_form` has no definition anywhere in this repo. So `## 1` is live contract **as to the subsets named above** and anticipated contract as to the swap, and this sentence must not be shortened into an unqualified certification. The Tier-1 / Tier-2 split of §1.3 is what makes the gap a bounded, stated divergence rather than an unexplained one; whoever lands the first swap-performing consumer should come back and narrow this paragraph.

`implement`'s temporary visual-fidelity gate carries a **partial** copy of the `## 1` mechanics inline — §1.1 slug, §1.2 guard, §1.3 in its same-directory / whole-file core only, §1.6 out-of-tree artifacts; **§1.4 lifetime and §1.5 version-and-migration have no counterpart there** — and is **deliberately not retargeted** to cite this file: that section carries its own removal checklist, so replacing its inline mechanics with a citation would widen the blast radius for no permanent gain — correcting a path anchor inside it is a different and far smaller act, and is not what this declines. The two copies diverge on these **seven** axes, every one of them accepted as-is. The enumeration is closed on purpose: an open list ("at least these …") cannot certify anything, and certification is the whole function this paragraph has. (1) **slug rules** — two rules addressing two different directories, each internally deterministic; (2) **the provenance guard** — here it is defined over a named document key covering both derivation branches and is re-evaluated at the commit point (§1.2 with §1.3), there it is a check-then-act whose comparand is undefined on the non-repo branch; (3) **the write protocol** — both require a same-directory `mktemp` and a whole-file `mv`, but only this file adds the plain-`mv`-never-`mv -n` rule, the post-`mv` read-back, the compare-and-swap at the commit point with a bounded retry and a defined exhaustion disposition, and the stated basis for declining a lock; (4) **header grammar** — `owner=` there, `writer=`/`reader=` here; inert, because no predicate in this repo matches header field 2; (5) **the version token** — emitted and never read there, gated in both directions here; (6) **the header's trailing clause** — a **wording** divergence only (`mechanism-local, never staged by a skill` here, `런타임 사이드카` there); both are repo-agnostic today, so the axis is cosmetic and is kept enumerated rather than dropped so the count stays auditable; (7) **`<base>` anchoring** — stated only here. §1.1 defines `<base>` on both derivation branches, while the inline copy names `<레포 루트>/docs/visual-drift/` unconditionally and leaves the base undefined when no repo root resolves. This is genuinely distinct from axis (2): axis 2 is *what the guard compares*, axis 7 is *where the file is put*, and a copy can satisfy axis 2 completely while writing to the wrong directory. **This file is the newer and stronger of the two — a new sidecar is modelled on this file, never on the `implement` copy.**

## 1. Generic sidecar mechanics

### 1.1 Path and slug derivation

A sidecar lives at `<base>/docs/<kind>/{slug}.md`, where `<kind>` names the mechanism (`design-reconverge`, …) and `{slug}` identifies the design document the sidecar belongs to.

**Creating `<base>/docs/<kind>/` is the writer's duty.** It is a new directory per mechanism and nothing else creates it, so without it the first write of every new `<kind>` fails before it can reach any disposition this contract defines — the `mkdir -p` of §1.3 is what makes that first write reachable at all. **This is the only directory a skill creates inside the owning repo's tree**, and creating it is not a licence against §1.4: a skill that may create this directory still never deletes it or anything in it.

**Deriving `{slug}`.** `{slug}` is the **document key** defined below, with the `.md` extension stripped and every path separator `/` replaced by `-`. So `docs/a/login.md` yields `docs-a-login`. One rule covers both derivation branches without splitting on them, because the key is defined on both.

**Resolving `<base>` and the relative path — keyed on the document's own location, never on the cwd.** Normalize the operand first: `cd` to the design document's own directory and take `pwd -P`, so what follows is keyed to the **physical** path with every symlinked parent component resolved. Run `git rev-parse --show-toplevel` from that directory. If the document sits under the returned root, that root is `<base>` and the relative path is taken against it. If it does not — or if no repo root can be resolved at all — fall back to the document's absolute path with only the leading `/` removed, and `<base>` is the document's own directory. Keying on the document rather than the cwd makes the derivation deterministic even when the cwd is inside a repo but the document is outside it.

**Why the normalization is load-bearing, and exactly how far it reaches.** Reaching a repository through a symlinked parent makes the two spellings of one document derive **different** keys, slugs, and `<base>`s — the physical spelling takes the repo-relative branch while the symlinked spelling falls through to the absolute branch — so a writer and a reader that arrived by different routes write and read two different files in two different directories. Nothing reports it: both writes succeed and the reader simply sees a partial history, which for the design-drift sidecar of `## 3` converts a disclosed divergence into an accusation its subject cannot answer. `pwd -P` collapses the two spellings to one, and it is the *other* operand that needs it — `git rev-parse --show-toplevel` already returns a physical path. **The normalization reaches symlinked parent components only.** A symlinked leaf document is outside it (`readlink -f` is on this repo's portability denylist and `realpath` is absent on BSD), and so is the key migration that any normalization necessarily implies for a file already written under the old spelling. Both are accepted residuals, named here so a green derivation is not read as their absence.

**The containment test must not be written in a form that degenerates on an unresolved root.** `git rev-parse --show-toplevel` yields the empty string when it fails, and the natural containment idiom then reduces to a test against `/*`, which matches **every** absolute path. The no-repo-root case therefore takes the repo-relative arm by accident: `<base>` becomes the empty string — the filesystem root — and the sidecar is addressed at `/docs/<kind>/`. The slug still comes out correct, which is what makes this hard to notice from the artifact. **Test that a root resolved to a non-empty value before testing containment**, and route an empty root to the fallback branch the paragraph above already defines.

**The document key.** For either branch this yields a single string: the repo-root-relative path when a root resolves and contains the document, otherwise the absolute path with only the leading `/` removed. That string is the **document key**. `owner-doc=` carries the document key verbatim, and both guards of §1.2 compare document keys — **never the folded slug, never a basename, never a suffix of either**. The key is defined on both branches, so the guard is a total function over every document this contract can address.

**The slug is deterministic but NOT injective.** Because `/` folds to `-`, a literal `-` in one path can collide with a directory boundary in another: `docs/visual-drift.md` and `docs/visual/drift.md` both yield `docs-visual-drift`. **Collisions are not prevented by the slug — they are caught by the provenance guard of §1.2**, which compares the full document key rather than the folded slug and therefore catches *every* collision regardless of how rare they are.

**No pointer is needed.** A reader re-derives the slug from the same rule and finds the file. Nothing in the design document references the sidecar.

### 1.2 Header grammar and the `owner-doc=` provenance guard

Line 1 is a human-readable H1. Line 2 is the machine header, a single HTML comment:

```
<!-- cc-<kind> v<N>; writer=<skill>; reader=<skill>; owner-doc=<document key>; NOT a design doc; mechanism-local, never staged by a skill -->
```

`writer=` and `reader=` name the roles rather than a single `owner=`, because a sidecar whose writer and reader are different skills has two distinct byte surfaces (see §2.6).

Both fields are required unconditionally. Where writer and reader are the same skill the two names are simply equal; the two-surface rationale above explains why the grammar has two slots, not when to emit them. **Neither field is ever matched by a predicate** — the provenance guard keys on `owner-doc=`, the version check on the `cc-<kind> v<N>` token (§1.5), and the ownership partitions of §2.3 / §2.6 on roles a skill knows intrinsically. Header field 2 is advisory provenance for a human reader.

**The guard is symmetric — a read guard and a write guard with the same predicate.**

- **Read guard.** Before applying anything a sidecar says, compare its `owner-doc=` against the current design document's **document key** (§1.1). On a mismatch the file belongs to a different document (a slug collision): **do not apply its content**, and proceed **as if no sidecar existed for this document**, so the owning mechanism re-runs. Never silent-skip. This is deliberately not the `unprocessed(sidecar)` predicate of §2.7 — that predicate reads the blocks of a file this guard has just ruled out.
- **Write guard.** If the target file already exists, proceed only when **both** hold: its `owner-doc=` matches the current document key, **and** its `cc-<kind> v<N>` token is strictly equal to the writer's own (§1.5). On an `owner-doc=` mismatch, on an **absent** `owner-doc=`, or on a version token that is not strictly equal, do not write: preserve the existing file, report the cause on the user-facing surface, and let the caller's own failure path take over. A version mismatch therefore takes the same disposition on the write path that §1.5 already gives the read path — never delete, never rewrite.

**Absence is treated as mismatch.** A missing `owner-doc=` does not prove ownership, so it fails closed in both directions. This is what makes the non-injective slug safe.

**A file the guard blocks is recoverable, and the recovery is the user's.** §1.1 re-derives exactly one path per document, so a blocked file cannot be set aside under a second name, and §1.4 forbids deleting it or removing a block from it: the state is byte-for-byte the dead end §2.5 describes for a file whose terminator is gone, and it takes the same posture. Surfacing names the state as *recoverable* and names the step — restore or correct the `owner-doc=` header by hand, or move the file aside — and **no skill performs either; this contract defines no write form for it.** The read guard's `as if no sidecar existed` disposition is about how the owning *mechanism* re-runs, and it never licenses passing over the file without telling the user: that would be the silent skip this section forbids.

**What the guard is not.** It establishes **cross-document** provenance. It is not a mutual-exclusion primitive and gives no protection between two writers of the *same* document — that hazard belongs to the compare-and-swap of §1.3, and the guard's own verdict is carried to the commit point by the same mechanism.

### 1.3 Atomic write

Write the whole intended file content to a temp file **in the same directory as the target**, then rename. Every write is a compare-and-swap: the bytes the content was built from must still be the file's bytes at the moment of the rename. The comparison and the rename are two processes, so this is a check-then-act whose window is **narrowed to a single process spawn, not eliminated** — an accepted residual, stated rather than hidden, in the same spirit as the `fsync` residual below. The snippet below is markdown prose, so `lint-bash-portability.sh` — which scans `*.sh` files only — never sees it: its portability, and any implementation's conformance to the rules stated around it, are **manually disciplined**, the same posture §2.6 states for the `sed -i ''` prohibition and for the same reason.

**The snippet is the body of a script or of a `( … )` subshell, and `exit` is its return channel.** This has to be spelled out rather than inferred, because the three bodies it delegates to are shell *functions* by construction — they take arguments and return a status — so the idiom a reader arrives with is "define a function", and wrapping this loop in a fourth one is the natural next move. Under that realization the success path's `exit 0` **terminates the caller with status 0**, which is indistinguishable from a correct run and silently kills whatever was to follow — including the post-`mv` read-back below, the only check there is for a degraded rename. A function realization is fine provided every `exit N` becomes `return N`; what is not fine is leaving the container to inference.

```
set -u                        # $SC_TERM is read unguarded below — see the
                              # terminator bullet: unset must be fatal.
# $SNAP — a copy of the bytes this attempt read. Bare mktemp, so it lands
# out of tree. It does not exist if the target was absent.
# $SC_TERM — the file terminator the payload schema fixes (§2.5 for the
# re-convergence sidecar, §3.6 for the design-drift sidecar). EVERY payload
# schema fixes one, so there is no contract-conforming empty value and no
# arm below exempts one. It is deliberately not named TERM, which is the
# terminal-type environment variable and is non-empty in every bash.
# $EDIT — this attempt's own model-composed text, whatever the payload
# schema's write form contributes. Composed once, before the loop, and
# reused unchanged across attempts.
# $FORM — the write form this attempt is performing, named by the payload
# schema. Threaded into BOTH delegated bodies so the matched pair cannot
# drift apart.
# $SC_BLOCK — the payload schema's block-heading prefix (`## 회차` for §2,
# `## 이탈` for §3). Parameterized for the same reason $SC_TERM is: §1 is
# payload-agnostic wiring and must not name one schema's literals.
for attempt in 1 2 3; do
  mkdir -p "$(dirname "$TARGET")" || exit 1
  SNAP=$(mktemp) || exit 1
  # Absence must be OBSERVED, never inferred from a failed read. A target that
  # exists but cannot be read is a distinguishable cause and exits at once.
  if [ -e "$TARGET" ]; then
    cp "$TARGET" "$SNAP" || { rm -f "$SNAP"; exit 1; }
  else
    rm -f "$SNAP"
  fi
  # Read-path guards on the INCOMING bytes, in THIS order. Version first —
  # see the ordering bullet below: a foreign-version file must be reported
  # as foreign, never as truncated.
  [ ! -e "$SNAP" ] || guard_version   "$SNAP" || { rm -f "$SNAP"; exit 1; }
  [ ! -e "$SNAP" ] || guard_owner_doc "$SNAP" || { rm -f "$SNAP"; exit 1; }
  # Truncation check — the INCOMING bytes (§2.5). Two qualifiers, and neither
  # implies the other: the comparison is over the last NON-EMPTY line, and it
  # is fence-aware. Fail closed, never retry — a fresh read cannot repair a
  # truncated file, and recovery is reserved to the user.
  [ ! -e "$SNAP" ] \
    || { [ "$(grep -v '^[[:space:]]*$' "$SNAP" | tail -n1)" = "$SC_TERM" ] \
         && tokenize_no_open_fence "$SNAP"; } \
    || { rm -f "$SNAP"; exit 1; }
  T=$(mktemp "$(dirname "$TARGET")/.$(basename "$TARGET").XXXXXX") \
    || { rm -f "$SNAP"; exit 1; }
  # Build the whole file into "$T" as a transform OF "$SNAP", here, on this
  # attempt. This comment is a requirement, NOT the enforcement — the gate
  # below is what refuses a build that ignored "$SNAP".
  build_write_form "$FORM" "$EDIT" "$SNAP" > "$T" \
    || { rm -f "$T" "$SNAP"; exit 1; }
  # Completeness check — the OUTGOING bytes. The SAME predicate as the
  # truncation check above, both qualifiers, on the other operand; only the
  # disposition differs. It is deliberately TOLERANT of trailing blank lines,
  # and must stay so: the gate's zero-removed conjunct forbids a build from
  # stripping a blank it inherited, so a strict form here would leave an
  # intact file with no realization able to write to it at all.
  [ -s "$T" ] || { rm -f "$T" "$SNAP"; exit 1; }
  { [ "$(grep -v '^[[:space:]]*$' "$T" | tail -n1)" = "$SC_TERM" ] \
    && tokenize_no_open_fence "$T"; } \
    || { rm -f "$T" "$SNAP"; exit 1; }
  # Write-form gate (§2.6, §3.4) — THE ENFORCEMENT POINT of this loop,
  # evaluated against THIS attempt's "$SNAP". It is bound to the same write
  # form as build_write_form above; the two are a matched pair and the
  # constraints of the two forms are not interchangeable. Where the form
  # forbids removals, that conjunct is what refuses a build that re-emitted
  # bytes composed against a stale read and would otherwise clobber a
  # committed competitor. The creation dispatch lives inside this body.
  gate_write_form "$FORM" "$SNAP" "$T" || { rm -f "$T" "$SNAP"; exit 1; }
  if { [ -e "$SNAP" ] && [ -e "$TARGET" ] && cmp -s "$SNAP" "$TARGET"; } \
     || { [ ! -e "$SNAP" ] && [ ! -e "$TARGET" ]; }; then
    mv "$T" "$TARGET" || { rm -f "$T" "$SNAP"; continue; }   # rename refused
    rm -f "$SNAP"; exit 0     # committed at the mv; cleanup cannot revoke it
  fi
  rm -f "$T" "$SNAP"          # CAS lost — fresh read on the next attempt
done
exit 1                        # nothing was written
```

- **Tier-1 (universal) and Tier-2 (conditional) — the split this section is read under.** More than one place in this repo instructs a writer to adopt *"Tier-1 atomic writes"*, so the boundary has to exist in writing.
    - **Tier-1 — owed by every `## 1` writer, unconditionally.** The torn-write safety floor: build the whole intended file into a temp **in the target's own directory**, then a whole-file `mv` onto the target; plain `mv`, never `mv -n`; never truncate; `$T` in tree and `$SNAP` out of tree; never `git add`. **`Write`/`Edit` do not satisfy Tier-1** — neither is a same-directory temp plus a rename — so a writer reaching for them has not adopted the floor whatever it cites.
    - **Tier-2 — conditional.** The compare-and-swap at the commit point, the 3-attempt budget, the delegated bodies, and the post-`mv` read-back apply where **the writer and the reader are different skills, or concurrent writers are possible**. The basis this section gives for declining a lock is stated in inter-skill terms, which is that same condition.

    Without the split, an instruction to *"adopt Tier-1"* never says what it **excludes**, and the predictable misapplication is a writer that is also its own reader implementing the swap and the retry budget — precisely what the split exists to prevent. It also converts today's gap from silence into a boundary: `design-audit` is its own writer and reader, so it owes Tier-1 and **not** Tier-2, and that is the whole of what it owes.
- **Five bodies are delegated, and the delegation is part of the contract.** The loop calls `guard_version`, `guard_owner_doc`, `build_write_form`, `gate_write_form`, and `tokenize_no_open_fence` and defines none of them: §1 owns the **wiring** — each body's operands, its verdict, and where it sits in the sequence — while the payload schema owns the **predicate**. `guard_version` takes `$SNAP` and returns zero only if the file's `cc-<kind> v<N>` token is strictly equal to the writer's own (§1.5). `guard_owner_doc` takes `$SNAP` and returns zero only if its `owner-doc=` equals the current document key, with an absent field failing closed (§1.2). `build_write_form` takes the form, this attempt's own text, and `$SNAP`, and writes the whole intended file to stdout. `gate_write_form` takes the form, `$SNAP` and `$T`, and returns zero only if that form's own byte-enumerated constraint (§2.6 for `## 2`, §3.4 for `## 3`) holds between them. `tokenize_no_open_fence` takes one file and returns non-zero if the payload schema's fence grammar leaves a fence open at end of file — trivially zero for a schema with no fences, which is why §1 cannot inline it. **`build_write_form` and `gate_write_form` are a matched pair, and the form is threaded into both** so the pairing travels in the call rather than in a convention the reader must remember: both are bound to the one write form this attempt is performing, and the two forms' constraints are not interchangeable — an append gated by a close constraint, or the reverse, rejects a legitimate write. Threading the form into only one of them breaks that claim, because the remaining body would then select its form by some other means the other body cannot see. **A body that cannot fail is not an implementation of it.** This is stated because the two failures it names are silent: a `gate_write_form` that always returns zero restores exactly the clobber this loop exists to prevent, and one implementing only part of its form's constraint lets a write against a truncated file commit and restore the terminator. Neither shows up as an error; both show up as a successful write. **This bullet is the whole of the enforcement, and it is prose** — nothing in a markdown snippet can compel a body to exist, so a reviewer of an implementation checks these five bodies first.
- **The version check precedes the truncation check, and the order is load-bearing.** A version bump makes **every** sidecar already on disk a foreign-version file on the day it lands. If the truncation check ran first, every one of them would be reported as *truncated* — because the terminator the new version fixes is not the one those bytes carry, or is not there at all — and the disposition for a truncated file invites the user to **restore a sentinel by hand that had no business being in those bytes**. In the stated order the same files are reported as version mismatches and take §1.5's disposition instead: skip, report, neither delete nor rewrite. The two guards then run in the order given, version before provenance, because a foreign-version file's `owner-doc=` need not even be in the grammar this writer knows. **Whoever moves either guard must move this rationale with it** — the ordering is one line of a sequence and reads as arbitrary without the paragraph that makes it necessary.
- **Creation dispatch is a universal conjunct and it lives here.** §1 owns exactly three conjuncts that hold for every `<kind>`: **membership** (the write form is one the payload schema declares), **creation dispatch**, and **disposition** (every failure ends at the one destination of the exit-status bullet). Creation dispatch reads: **in the absent-pre-write-bytes state, no diff gate evaluates that write at all.** It is deliberately written over *the gate*, not over *a table*: a clause that exempts only a payload schema's write-form table leaves any constraint stated in prose beside that table still live, and §2.6 states one there — an added terminator line is a construction fault — which would then fire on the creation write, where the terminator is necessarily on the added side. Holding the dispatch at §1 also covers every future `<kind>` by construction, so no payload schema has to remember to re-state an exemption; a schema that re-states it locally is duplicating a rule it does not own. What a payload schema keeps is only its own creation **emission order** — which lines the created file contains and in what sequence.
- **Every payload schema fixes a file terminator; "no terminator" is not a conforming state.** The loop reads `$SC_TERM` unguarded, so an unset value is fatal under `set -u` and an empty value fails closed — for any non-empty file the comparison *last non-empty line equals the empty string* is simply false. That is the point of removing the empty-value arm rather than adding a new check: while the arm existed, an empty `$SC_TERM` short-circuited the truncation check **and** the completeness check at once, and a schema that fixed no terminator made that empty value **contract-conforming**. In that state the carry-forward rule of a write form — strip through the file's last non-empty line — deletes a real field line instead of a sentinel, and the diff gate cannot see it, because `diff` aligns the deleted line against a byte-identical line in the newly appended block and reports nothing removed. No `gate_write_form` predicate closes that: the fix has to be the terminator. Conversely, **once a terminator is fixed, a writer that forgets to set `$SC_TERM` is caught by the existing zero-removed conjunct** — a schema with a terminator degrades safely under an author's mistake and a schema without one does not.
- **The pre-write bytes.** These are the bytes the target holds at the compare-and-swap — equivalently, the bytes this attempt built its content from, since the swap commits only when the two are identical. **Absence is one of the states this term ranges over**: a snapshot taken of a file that did not exist matches only a target that still does not exist. Other sections cite this term rather than restating it.
- **What the swap buys.** It re-runs no check. It makes every verdict already reached on those bytes — the provenance guard and the version token of §1.2 and §1.5, and any further read-time precondition a payload schema adds — **still true as of a comparison performed immediately before the commit point**. A check-then-act guard becomes check-then-verify-then-act without the guard being restated, and any precondition added to the read path later inherits this for free **provided it is a function of these bytes alone**. A precondition over any *other* file is not carried, and needs either its own re-evaluation at the commit point or an explicit statement that it is not carried. Two already exist: the document key the guard of §1.2 compares against is derived from the design document's own location (§1.1), so it can flip while the sidecar's bytes do not move; and the reader's derivation in §2.8 runs two greps and an empty-range check over the design document, from which the close write that follows inherits nothing.
- **On a failed comparison**, discard this attempt's temp and restart the whole read-modify-write from a fresh read: a new read, a fresh re-derivation of anything keyed on the bytes, and a fresh build. Content built against the stale bytes is never reused. **At most 3 attempts**; on exhaustion do not write — preserve the existing file, report the cause on the user-facing surface, and let the caller's own failure path take over, exactly as a guard mismatch does (§1.2).
- **The exit status is the whole of the caller's interface.** `0` means the swap committed; any non-zero status means **nothing was written** and the existing file is intact. The disposition above is therefore not scoped to a failed comparison: an attempt that could not be prepared or committed at all — a failed `mkdir`, a failed `mktemp`, a temp that failed its completeness check, a `rename(2)` that genuinely failed — ends at the same place and takes the same disposition. Every failure path of this contract has exactly one destination. A snapshot that could **not be taken** is never encoded as absence: a failed `mktemp`, or a failed `cp` of a target that exists, is a failure to prepare an attempt rather than an observation that the target was missing. That is why the snapshot arm branches on `[ -e "$TARGET" ]` instead of letting a failed `cp` fall through to the absent case. Under the fall-through the loop builds a creation-form write three times against a target that exists but merely could not be read, burns the whole retry budget, and then reports the wrong cause — *CAS lost* points the user at a competing writer when the truth is an unreadable file, and the two send them to opposite remedies. The absence branch is trustworthy only because it requires the *target* to be absent as well: the `[ -e "$TARGET" ]` conjunct is functionally redundant against `cmp -s`, which already fails quietly on a missing operand, and is kept because it is what separates *the target is gone* from *the bytes differ* — a separation that holds only because §1.4 guarantees no skill ever deletes a sidecar. **The single exception to the one-destination rule is the post-`mv` read-back below**: it runs in a later tool call than the commit, after this status has already been returned, so it is outside the retry budget of the loop and reports to the caller instead.
- **A restart re-derives byte-keyed material only.** On a failed comparison every derivation keyed on the file's own bytes is redone from the fresh read, and nothing built against the stale bytes survives. What a restart must **not** re-derive is a payload-schema question, because the answer names that schema's own fields — `## 2` states its own rule for its close set in §2.1.
- **`$SNAP` is the operand of every read-path predicate.** The provenance guard (§1.2), the version token (§1.5), and every payload-schema derivation over the file's own bytes (§2.1's `max(회차)`, §2.5's tokenizer, §2.5's **truncation check**) are evaluated against `$SNAP`, **not** against `$TARGET`. **Two checks are named apart because they run in opposite directions.** The **truncation check** reads the *incoming* bytes `$SNAP` and asks whether the file this attempt is extending is intact; the **completeness check** reads the *outgoing* bytes `$T` and asks whether the content this attempt built is whole. They compare against the same `$SC_TERM` — one value, one identifier — but they are different checks with different dispositions: the truncation check fails closed and does not retry, because a fresh read cannot repair a truncated file. The `tail -n1` form in the snippet is the completeness check in full; for the truncation check that form is not even a necessary leg — it rejects an intact file that acquired one stray final newline — so the comparison there is taken over the last **non-empty** line, and it is additionally fence-aware, as §2.5 requires of every derivation over these bytes. **Neither qualifier implies the other**: without the tolerance an intact file is rejected, and without fence-awareness a file truncated inside an open payload fence, whose last surviving line happens to be the sentinel text, is accepted. A verdict reached on `$TARGET` in a separate read at a separate moment is not carried by the swap — the swap can only preserve a verdict reached on the bytes it compares. A tool-call boundary **always** separates the read that fed a guard from the `cp` that takes the snapshot — assembling the content at all requires reading the file first, and the `cp` sits in a later call — so every such guard is re-evaluated against `$SNAP` before the content is built. This is a standing fact about the write path, not a condition that may or may not obtain.
- **Same directory is mandatory for `$T`.** A temp under `${TMPDIR:-/tmp}` may sit on another filesystem, where `rename(2)` is not atomic and `mv` degrades to copy-then-unlink. **`$SNAP` carries the opposite requirement and belongs out of tree**: it is never renamed onto the target, so it needs no filesystem affinity, and keeping it out of the tree keeps it out of `git status` and therefore out
  of any boundary gate a caller runs.
- **Where `docs/` is tracked.** The rules above keep `$SNAP` out of the way, but not `$T`, which is
  in-tree by requirement: an orphan `$T` left by an interrupted attempt is an untracked file under
  `<base>/docs/` exactly as the sidecar *itself* is, so in an owning repo that tracks `docs/` both are
  visible to `git status` and therefore to the two-command boundary gate of `_common/verification.md`
  §6. **The duty is a consumer obligation, not a fact about today's tree**: every skill that writes a
  sidecar states, at its own write point, that the write sits outside any team-discussion gate window.
  The prose this replaces asserted that the only located write point was outside one — true when it
  was written, when no consumer had landed, and stale from the moment consumers did land without
  anyone re-evaluating it. An obligation discharged where it can be checked cannot go stale centrally.
- **Plain `mv`, never `mv -n`.** The no-clobber form belongs to a witness file that must not be overwritten — and even there its safety is not atomic no-clobber, since `mv -n` is stat-then-rename on both BSD and GNU (`_common/agent-team-protocol.md` states this outright). Copying that idiom here is a silent data-loss bug for a different reason: every write after the first would be skipped, so an accumulating sidecar would keep exactly its first block forever.
- **What `rename(2)` guarantees, and what it does not.** It is atomic with respect to concurrent readers: a reader sees either the old file or the new one, never a torn one, and a process that dies before the rename leaves the target untouched. It is **not** a durability barrier — this contract issues no `fsync`, so a host-level crash may lose a completed write. Do not carry the atomicity claim into contexts that need durability.
- **No lock.** After the `mv`, read the file back and confirm **that this attempt's own effect on the file is present and the terminator is intact** — never that the file equals what this attempt wrote, and never as a claim of authorship. It is a self-check against a degraded rename, not a concurrency check. **The success predicate is containment, not equality, and it is written per write form** — §1 fixes that shape, and **each payload schema supplies its own arm for every form it declares**, a form §1 has never seen included. Keeping this general clause is what makes that obligation exist at all: without it, a schema that declares a novel form would owe no read-back whatever. The one arm §1 can state generically is **append** — the last non-empty line is `$SC_TERM`, and a `$SC_BLOCK <N>` heading carrying this attempt's own `<N>` is present as a tokenizer-recognised heading. `N` is `max(existing) + 1`, so it names a slot rather than a writer: two writers that read the same bytes derive the same `N`, and this read-back cannot tell whose block it found. **Arms are not interchangeable across forms** — a form that adds no block heading leaves the append arm's second conjunct undefined, and an `mv -n` skip would then pass it vacuously on a heading the pre-write bytes already carried. A file that *also* carries content this attempt did not write is a successful commit followed by a legitimate successor, not a failure — the read-back happens in a later tool call than the `mv`, a window far wider than the one the swap narrows, so a successor landing inside it is ordinary. Treating that as a failure would restart an attempt that had already committed, and the restart would re-derive a higher `N` and commit a **second copy of the same finding**, which §2.9 would then count as corroborating evidence for itself. Containment still catches both cases this check exists for: a `rename(2)` degraded to copy-then-unlink and truncated loses the terminator, and an `mv -n` that skipped leaves this attempt's own heading absent. On a genuine mismatch, report the cause on the user-facing surface and let the caller open a fresh read-modify-write cycle: this read-back runs in a later tool call than the commit, after the success status has already been returned, so §1.3's 3-attempt budget does not reach it — this is the exception §1.3 notes alongside the exit status. It does **not** detect a concurrent writer, and no claim here rests on it doing so. A lock is declined for two reasons. First, **a compare-and-swap is unilaterally effective and a lock is not**: a participant that implements the swap detects and survives a participant that does not, whereas a participant that takes a lock gains nothing against one that does not — and this contract's writer and reader are separate skills, authored separately, so partial adoption is an expected state rather than an exception. Second, these files are user-local and never deleted by a skill, and nothing in this repo reaps an abandoned lock directory. A lock layered *on top* of the swap is harmless; the swap is the part this contract requires.
- **Orphan temps.** A `$T` left behind by an interrupted attempt is harmless: it is a dotfile in the target's own directory, so it is missed by both the exact-path re-derivation of §1.1 and a `*.md` glob. A third detector does see it: in a repo that tracks `docs/`, `git status --porcelain` lists an orphan `$T` as its own untracked entry. That is the same exposure the sidecar itself already has, and it is bounded the same way — the boundary gate of `_common/verification.md` §6 measures a delta against a pre-workflow baseline, so an orphan from an earlier session sits in the baseline and only one created inside the window can fire it. The `rm -f` above targets **this attempt's own temp by name** — never a glob sweep of the directory, which would delete a concurrent writer's live temp. **`$SNAP` is disposed of on every path** — on the committing path and on every restart — because nothing else reaps it: it is not a dotfile in the target's directory and no clause above covers it. Without those removals a single contended write leaves up to three full copies of the sidecar behind, one per attempt of the budget.

### 1.4 Lifetime — never delete, never truncate, never `git add`

- A skill **never deletes** a sidecar and never removes a block from one. State transitions happen in place; cleanup is the user's, by hand.
- A skill **never truncates** an existing file to write a shorter one. Whole-file atomic write means *read, extend in memory, write the whole thing back* — not overwrite-from-empty.
- A skill **never `git add`s** a sidecar. A sidecar is mechanism-local state, not a project artifact. Where the owning repo ignores `docs/` this holds automatically; where it tracks `docs/` this rule is the **only** thing keeping the sidecar out of the index — and the user's own `git add -A` is outside any skill's control, so the rule is a discipline, not a guarantee.

### 1.5 Version token and migration

The header carries `cc-<kind> v<N>`. A reader matches it by **strict equality** against the version it understands. On a mismatch: skip the file, report it, and **do not delete or rewrite it**. The write path takes the same disposition — the version is one of the two conjuncts of §1.2's write guard, and `guard_version` is the body that evaluates it, ahead of the truncation check for the reason §1.3 gives.

**A skip is reported, and the report says what a skip costs.** Naming the path, the version found, and the version expected is the minimum; the report must also say that the mechanism therefore has **no history for that document on this run**, because a consumer that reads "skipped" as "nothing to see" reaches exactly the wrong conclusion — for the design-drift sidecar it would read an unavailable channel as an absence of declared divergences. For the `cc-design-drift` bump from `v1` to `v2` there is a further thing to say: a `v1` file may have **already lost required field lines** to the very write path the bump exists to close, and **that loss does not come back**. Blocks are frozen from the instant they are appended, §1.4 forbids rewriting one, and no payload schema has a rewrite form — so nothing reconstructs a field that was overwritten. Migration is accordingly a user-driven transcription: read the `v1` file, judge by hand which blocks are intact, and re-author those into a fresh `v2` file. A reader must not present this skip as a benign version difference.

**No automatic in-place migration.** A botched migration may have no `git` undo at all: where the owning repo ignores `docs/` the bytes are simply gone, and even where it tracks `docs/` a sidecar is typically uncommitted at the moment a reader would migrate it. Migration, if it is ever needed, is a deliberate user-driven step, never a side effect of a reader noticing an old version.

### 1.6 Artifacts stay out of tree; the sidecar carries the recipe

Binary or bulky products of the mechanism (screenshots, captures, extracted corpora) go to an out-of-tree scratch directory such as `mktemp -d "${TMPDIR:-/tmp}/cc-<kind>-{slug}.XXXXXX"`, and the sidecar does **not** cite those paths — they are session-local and will not exist later. What the sidecar records instead is the **reproducible recipe** — in whatever form the payload schema of the owning `<kind>` fixes (for the re-convergence sidecar, §2.5 fixes the fence and the info string; the observation caps there govern `관측 결과` alone and never the recipe) — plus durable pointers (a prototype path, a document anchor). The duty is to leave behind what regenerates the artifact, not the artifact.

## 2. The re-convergence sidecar — `docs/design-reconverge/{slug}.md`

Carries a refuted or undecidable verification claim from an `implement` failure branch to a later `design` re-convergence, across a session boundary. Header:

```
# 설계 재수렴 요청 — {slug}
<!-- cc-design-reconverge v1; writer=implement; reader=design; owner-doc=<document key>; NOT a design doc; mechanism-local, never staged by a skill -->
```

### 2.1 Cycle blocks

Re-convergence can recur on the same design document, so blocks **accumulate in one file** — one file per design document, never one per cycle. Each block is `## 회차 <N>`, where `N` is `max(existing) + 1` **re-derived from `$SNAP`, the snapshot §1.3 takes on this attempt** — never from memory, and never from an earlier read whose bytes a competing writer may already have superseded. `$SNAP` is the operand §1.3 fixes for every read-path derivation over this file, writer-side and reader-side alike, so no derivation here points at a different read from any other. Where `$SNAP` is absent — the creation write, whose snapshot is of a file that did not exist (§1.3) — the maximum is taken over the empty set and `N` is 1, which is the `## 회차 1` block §2.6 requires of that write. `max(existing)` is taken over the headings the fence-aware tokenizer of §2.5 recognises: a `## 회차` line inside an open fence is payload, not a heading, and never enters the maximum.

Re-derivation guarantees exactly one thing — this writer's counter is fresh with respect to *its own* read. It is not a uniqueness guarantee across concurrent writers (§1.3 **narrows** that hazard rather than arbitrating it — see the residual stated there; under that residual `N` is unique by the losing writer's block being destroyed, not by anything having assigned it), and it is redone from the new bytes on every retry.

A block carries its own `상태`, so the file-level "is there work here" predicate is a disjunction over blocks (§2.7), not a file-level flag.

**What a restart must NOT re-derive — the close set is an intersection whose two conjuncts are treated differently.** §1.3 fixes that a restart re-derives byte-keyed material; this is its complement, and it lives here because it names this schema's own fields. State it as a set: **close set = (the *human* conjunct — the blocks the user routed at this cycle's prompt, fixed at that routing decision and never recomputed) ∩ (the *byte* conjunct — the blocks the fresh bytes still show as `상태: 대기`, re-evaluated on every restart)**. Both directions follow from the one sentence. A block that appeared in the file after the routing decision is absent from the first conjunct, so it is excluded however the byte predicates score it. A block another reader closed inside the window is absent from the second conjunct, so it is excluded however the routing decision scored it. Three rules were candidates and only this one is correct: re-deriving *both* conjuncts closes blocks the user never saw, and retaining *both* inserts a second `처리 기록` into a block another reader already closed — violating `상태`'s once-only mutability and the one-per-block rule of §2.6 at the same time, and permanently, since §1.4 forbids removing the line.

Field lines use the same CANON rendering as the verification contract (`_common/verification.md`): bold key, no leading bullet, one ASCII space after the colon. The one exception is the key line of a payload-bearing field (§2.5).

**Every document-sourced field is re-read from the design document at write time and copied verbatim** (`주장`, `기대 결과`, `실패 시 영향`, `분류`, and the `R<n>` heading text rendered into the `대상 항목` anchor form of the field table above). Never restated from context.

**Field 15 carries the one departure from what was actually run.** Where the recipe as run embeds a session-local path, `실행된 레시피` carries that path in the parametric form the verification contract's recipe rule already mandates, never the expanded one. This is a rule in its own right rather than a clause of the verbatim rule above — field 15 is not a document-sourced field, as the next paragraph says outright — but it is placed here, adjacent to that rule, **so that no reader meets the two duties apart**.

The recipe is deliberately **not** in the verbatim list. Field 15 carries the form actually executed, and every difference from the document's `검증 레시피` is accounted for by field 16.

**No reconstruction, and a closed set of unavailability tokens.** Five fields admit the unavailability token `미확인` (§2.4), on three different grounds. `관측 요지`, `관측 결과`, and `실행된 레시피` admit it because the observation itself may be unavailable. `치환 맵` admits `없음` (the rung did not fire — a positive observation) and `미확인`, the latter only when `실행된 레시피` is `미확인`, since an unobserved recipe cannot warrant the positive claim. `트리 위생` keeps its own `미확인` with the reader-side note of §2.4. **An unavailable observation bounds the verdict**: a block whose `관측 결과` is `미확인` may not carry `검증 등급: 반증됨(실패)` — a refutation is a claim *about an observation that was made*, so an unobserved failure is `검증불가(드리프트)`. The two grades therefore carry different evidentiary duties, which is load-bearing because §2.9 injects *every* block in a group as evidence strength: without this, a block with no observation adds weight it never earned. **For every other required field there is no token: an absent value makes the block malformed**, and a malformed block is surfaced rather than consumed. One reused literal rather than a per-field one is deliberate — the reader's unavailability branch is then a single equality test, and two skills authored separately cannot drift into two token sets. A field carrying `미확인` takes the ordinary CANON rendering with no fence (§2.5). This is what makes a reader's "observation unavailable" branch reachable by contract — without it that branch is dead code, and a full-trust reader then has no defense against a fabricated observation.

**Session handles are never recorded** — no agent identifiers, scratch directories, transcript paths, nonces, generation counters, ledger fragments, or session-local `${TMPDIR}` paths. A sidecar transports findings, not handles. The concrete exposure is `실행된 레시피`: a recipe run inside a temporary worktree naturally embeds a session-local path, and a `/tmp` literal is itself a malformedness axis in the verification contract, so the field table alone does not block it.

### 2.3 Frozen-tail invariant

> **Fields 1–2 are the block's mutable region. Field 1 is seeded `대기` by the writer's append and is thereafter the reader's alone to change; field 2 is the reader's outright. Fields 3–19 are emitted by the writer in that same append and are frozen from that instant — never touched by any writer again, and never by the reader.**

The invariant is what makes the verbatim copies of §2.2 safe from divergence: a reader can say *everything below the mutable region was true at `관측 일시`, and nothing in it claims to be true now.*

The reader obtains `상태` and `사용자 라우팅` — the two fields the predicates of §2.7 key on — from the fence-aware tokenizer of §2.5, keyed on **field name within the block**, never on a line offset from the heading. No offset-based idiom is sound here: field 2 is conditional, so a `처리됨` block moves field 3 down by one, and this file fixes field *order* and field-line *rendering* but never fixes blank-line placement, so one blank line after the heading moves it again. Such an idiom is additionally blind to fences and would read a forged `## 회차` line out of a payload as a real block — exactly the forgery §2.5 declares inert.

### 2.4 Closed vocabularies

| Field | Values |
| --- | --- |
| `상태` | `대기` \| `처리됨` |
| `사용자 라우팅` | `설계 재수렴` \| `위험 수용하고 계속` \| `중단` \| `미응답` |
| `정지 지점` | `구현 전` \| `구현 중(<phase>)` |
| `검증 등급` | `반증됨(실패)` \| `검증불가(드리프트)` |
| `트리 위생` | the five forms of the table below — one of them parameterised |
| `관측 절단` | `줄 수(<N>줄)` \| `줄 길이(<K>줄 절단)` \| `줄 수(<N>줄)·줄 길이(<K>줄 절단)` — `<N>` is the line count **before** truncation, `<K>` the number of lines the clamp cut |
| unavailability token | `미확인` — admitted **only** by `관측 요지`, `관측 결과`, `실행된 레시피`, `치환 맵`, `트리 위생` |

**`상태` has exactly two values.** There is deliberately no in-progress value: with no intermediate state, a reader never has to reconcile a half-transitioned block. Atomicity itself comes from the whole-file `rename(2)` of §1.3, not from the size of this vocabulary — the two-value rule removes the **reconcilable** state, the atomic write removes the **torn** one. It admits no unavailability token for the same reason a third value is excluded. `사용자 라우팅`, `정지 지점`, `검증 등급`, `관측 일시`, `대상 항목`, and the document-sourced fields likewise admit none: for those, absence is malformedness (§2.2).

**`사용자 라우팅` values are frozen to the writer's own prompt labels.** Transport fidelity is the point; translating a value inserts precisely the layer where a byte slips. A reader that needs to disambiguate does so on **its own** option labels, never by rewriting the transported value.

`미응답` is the one exception to that freeze, because it is not a prompt label: it records the **observation that no answer was given** — a prompt dismissed, or a non-interactive run — where the writer nonetheless chose to persist the finding. It is a positive observation, not an unavailability token, which is why `사용자 라우팅` admits no `미확인`.

**`트리 위생` records what actually held at observation time, and maps 1:1 onto the tree-hygiene note the reader writes.**

| `트리 위생` value | What the reader writes |
| --- | --- |
| `워크트리 격리 확인` | `워크트리 격리 확인` — no validity note |
| `진입 시 clean · 진입 대비 무변경 확인` | `tracked-source 무변경 확인` — no validity note, and it is **true** |
| `진입 시 dirty(<N>건) · 진입 대비 무변경 확인` | validity note: (i) sidecar path + `관측 일시`, (ii) this predicate verbatim |
| `구현 중 — 진입 기준선 없음` | validity note: (i) + (ii) no entry baseline exists at this branch |
| `미확인` | validity note: (i) + (ii) unknown |

The second row is the load-bearing one: an implementation-time observation does **not** automatically weaken the tree-hygiene claim. If the entry baseline was empty and the boundary gate passed, the clean note is a true statement. The field carries that distinction, so the reader renders the note with zero judgment.

**`정지 지점` is keyed on which failure branch fired**, not on the emitter's `검증 시점` plan — the two vocabularies share two token spellings only because `implement`'s two failure branches happen to align with two of that field's partitions. The third `검증 시점` value never appears here: a `구현 후` residual executes no recipe, so it produces no verdict and reaches no failure branch, and no block is ever written for it.

### 2.5 Verbatim observation payloads

`관측 결과` and `실행된 레시피` are fenced **whenever they carry a payload**, with a bare-colon key line above the fence. When any of `관측 요지`, `관측 결과`, `실행된 레시피` carries `미확인` (§2.2) it takes the ordinary CANON rendering — `**관측 결과**: 미확인` — and there is no fence.

- **The bare-colon key line is the sole exception to §2.2's CANON rendering.** Its exact form is `**<key>**:` — bold key, one colon, nothing after it, no trailing space. It is therefore **not** matched by the verification contract's sanctioned detection idiom `^(- )?(\*\*<key>\*\*|<key>): <value>$`, whose `<value>` arm cannot be empty. A payload-bearing field is located positionally by the tokenizer — a bare-colon key line whose next line opens a fence — never by that value-bearing grammar. The same field in its `미확인` rendering *is* matched by the grammar, because it then has a value.

- **Variable-length fence**: `N = max(3, longest backtick run in the payload + 1)`, so payload backticks cannot terminate the fence early. Mandatory `text` info string.
- **Caps — `관측 결과` only**: 80 lines, plus a 2000-character clamp on any single line. When either fires, declare `관측 절단` with the value grammar of §2.4, naming which cap fired: `<N>` is the payload's line count **before** truncation, and `<K>` is **how many lines** the clamp cut, since the clamp is per-line and may fire on more than one. This is *payload* truncation, a normal outcome recorded in field 14; it is unrelated to the *file* truncation check below.
- **`실행된 레시피` is never truncated, and the caps above do not reach it.** Field 15's contract is the recipe *exactly as executed*, and §2.10 warrants the field precisely because that recipe is unrecoverable from disk; a silently shortened field 15 falsifies both at once, permanently, inside a frozen tail. Recipe size is bounded upstream instead, by the self-containment rule of `_common/verification.md` §9 — a recipe that cannot be recorded inline is required to split the claim or become residual before it ever reaches this file. A recipe that nonetheless exceeds the observation cap is evidence that the upstream rule was broken: report that, and still emit the recipe whole. Field 14 accordingly speaks about field 13 alone, which is what its name says.
- **Reduction is the recipe's job, not the model's — and this rule governs `관측 결과` alone.** (`실행된 레시피` is exempt from the caps above and is never reduced: a recipe has no aggregation step of its own, and `관측 요지` cannot stand in for a recipe.) The payload carries the values the recipe's own `기대 결과` is a predicate over, exactly as produced, together with the counts and inputs the recipe's own procedure names. When the raw corpus exceeds the cap, reduce it **by the recipe's own aggregation step**. An aggregation the recipe does not specify is a reconstruction, and reconstruction is forbidden. **When the recipe specifies no aggregation step**, elide the payload positionally to the cap, declare `관측 절단`, and let `관측 요지` carry the verdict-bearing numbers. Positional elision and the character clamp are the only two exceptions to the reconstruction ban, and they are narrow ones: both remove content and neither synthesises any, and the verdict survives in field 12 by construction.
- **Fence-aware tokenizing is a normative rule for every consumer of these bytes, reader and writer alike**: inside an open fence, no line is a heading or a field line. This makes block forgery from payload content inert. Every derivation in this contract runs on this tokenizer — block boundaries, field lines, `max(회차)` (§2.1), the reader predicates (§2.7), the grouping key (§2.9), **the diff gates of §2.6**, and the terminator check below.
- **File terminator.** The last **non-empty** line of the file is the fixed sentinel `<!-- cc-design-reconverge: end -->`, emitted by every write form, the creation write included. Trailing blank lines and trailing newlines are stripped before comparing — the same tolerance `_common/agent-team-protocol.md` states for its own witness sentinel and for the same reason: a stray blank at the end must not read as a truncation. A file whose last non-empty line is not that sentinel **outside an open fence** is truncated: fail closed, surface it, and do not write to it. **Both qualifiers are load-bearing and neither implies the other** — a comparison that tolerates trailing blanks but is not fence-aware accepts a file truncated inside a payload whose last surviving line happens to be the sentinel text, and a fence-aware comparison that reads the literal last line refuses an intact file that acquired one blank line. This is the **truncation check**, which reads the incoming bytes; §1.3's completeness check reads the outgoing ones. **Both take this same predicate and differ only in operand and disposition** — the truncation check fails closed and never retries, since a fresh read cannot repair a truncated file, while the completeness check discards the temp and reports, since a temp built wrong can be rebuilt. Holding the outgoing check to a stricter predicate would be unwritable rather than safer: §2.6 permits no removal of an inherited line, so a writer cannot normalise away a blank the file already had, and a stricter outgoing check would leave that file with no conforming realization at all. The sentinel is a constant, so **where the pre-write bytes already carry it** it is byte-identical before and after and therefore never appears in the diff gates of §2.6; on the creation write it is an added line, and §1.3's universal creation dispatch means **no diff gate evaluates that write at all** — note that the exemption has to be stated over the gate rather than over this section's table, because the added-terminator construction fault of §2.6 is stated in a bullet beside that table and would otherwise still fire on exactly the write the exemption exists to permit. **Those two cases are the whole of the invisibility**: where the pre-write bytes do not carry the sentinel, re-emitting it puts a terminator line on the added side, which the diff gates do see and §2.6 disposes of. What is scoped here is the sentinel's *invisibility to the diff gates*, never its emission — every write form emits it, so a writer may always assert it on the bytes it is about to commit. It replaces a fence-parity check, which the variable-length rule above refutes: a payload holding a fenced script — an authorised recipe shape — legitimately contributes fence-looking lines and flips parity on an intact file, and a fail-closed parity check would then reject an intact sidecar wholesale. Parity is also blind to a truncation landing between blocks. The tokenizer's own open-fence-at-EOF signal is kept as a cheap second check, never as the primary one. The truncation paths this is known to defend against include the hand-editing §1.4 invites, a `mv` degraded to copy-then-unlink by a §1.3 violation, and a host-level crash across a rename this contract never `fsync`s (§1.3) — on a filesystem that does not order the data write ahead of the rename, that can leave a zero-length or stale target. Writer *process* death is not one of them, because `rename(2)` is the commit point.

**Recovering a file whose terminator is gone.** The disposition above blocks both write forms at once, and §1.4 forbids deleting the file or removing a block, so nothing in this contract moves such a file forward: §1.1 re-derives exactly one path per document, so there is no fallback name and the document cannot take a second sidecar, and every block already accumulated becomes unreadable along with it. **Recovery is a deliberate user-driven step, never a side effect of a skill noticing the truncation** — the same posture §1.5 takes toward a version mismatch. The step is to restore the sentinel as the file's last line, or to move the file aside by hand; no skill performs either, and this contract defines no write form for it. Surfacing therefore names the state as *recoverable* and names that step, rather than reporting a file the contract has silently condemned. An empty file — `touch`, or a redirection that clobbered it — is the same state and takes the same route; it is not the absent pre-write state of §1.3, so the creation exception of §2.6 does not reach it.

`관측 요지` (field 12) exists because a positional elision cannot promise that the verdict-bearing numbers survive truncation. It is one line: the measured value(s) that decide the verdict, plus the threshold they are measured against. It is not new authoring — the writer is already obliged to produce that same one-line distillation elsewhere; at a pre-plan failure branch the sidecar is simply its only home.

### 2.6 Write forms and their diff gates

Two byte-enumerated forms, partitioned by owner. "Pre-write bytes" means whatever §1.3 defines it to mean at the commit point; this section cites that definition and does not restate it.

| Form | Owner | Constraint on `diff -U0` between the pre-write bytes and the bytes being written |
| --- | --- | --- |
| **append** — emit one complete new `## 회차 <N>` block: every applicable field, including `상태: 대기` and the settled `사용자 라우팅` value | writer | **0 removed lines**; exactly one new tokenizer-recognised `## 회차` heading, and it is the **last** `## 회차` heading in the written file; every added line lies **at or after** that heading and **before the next tokenizer-recognised `## 회차` heading or the terminator, whichever comes first** — the sole exception being one added blank line **immediately preceding** that heading, the block separator |
| **close** — flip `상태` and insert one `처리 기록` line | reader | removed lines confined to `상태` lines of the blocks being closed; added lines are those plus **exactly one** `처리 기록` per closed block, each at field position 2 immediately after its block's `상태` line; **every block outside that set unchanged** |

- **Each owner evaluates its own form's constraint before the `mv`**, against the pre-write bytes and the temp it is about to commit. **The comparison is over the two files' line sequences, in which a final line carrying no terminating newline is the same line as one that does.** Without that normalisation a pre-write file whose last line lacks its newline makes the diff report that line as removed and re-added, so the zero-removed constraint fires on a file that is otherwise intact and the sidecar becomes unwritable over a byte no predicate in this contract reads. Every write form here emits a final newline, so the normalisation only ever reaches a pre-write file that lacked one. Nothing else evaluates it — there is no third party and no post-hoc audit. A violation is a construction fault, not a conflict: discard the temp, do not write, and report the cause on the user-facing surface, the same disposition every other failure branch of this contract takes (§1.2, §1.3). A reader does not re-verify a block's shape against these constraints at read time; it applies the malformedness rules of §2.2 to what it finds.
- **append** is the writer's only write form. After that single atomic write the writer never touches any block again, including its own. **Carrying the pre-write bytes forward strips through the file's last non-empty line**, matching the truncation check of §2.5 rather than the literal last line: against a file that ends with the sentinel followed by a blank, stripping only the last line leaves the old sentinel standing mid-file and the written bytes carry two. Nothing but the terminator is stripped, which is what the zero-removed constraint above requires of the rest of the file.
- **On creation** — the absent pre-write state of §1.3 — the append emits, in this order: the H1 of §2, the machine header of §2, one complete `## 회차 1` block, and the terminator. Nothing else. This is the only place the contract assigns emission of the file header to a writer; the table constraint above governs every later append, where the file already exists.
- **The added side is bound by position, not by count — and the bound is the block, not the file.** A count-only gate passes an edit that inserts a forged field line into an existing block's frozen tail while appending a legitimate block of its own: nothing is removed and exactly one heading is added. Position is the enforceable form of the frozen tail of §2.3, which is what §2.2's verbatim copies rest on. `at or after` is deliberate — the heading is itself an added line, so `after` alone would exclude it and make the gate unsatisfiable. **The upper bound is the next block boundary, not the terminator.** A bound reaching the terminator fixes only where added lines sit *relative to the new heading*, never where that heading sits in the file: write the new block **first** and every line below it — including a forged field line spliced into an older block's frozen tail — lies after that heading and before the terminator. Such an edit removes nothing, because the pre-write bytes remain a subsequence of the written ones and no alignment containing a deletion can win, and it adds exactly one heading. A file-wide bound is therefore *more* permissive the earlier the new block is placed, which is the reverse of what a frozen tail needs. `or the terminator, whichever comes first` keeps the last block bounded, since a heading-only bound would admit lines appended past the terminator. **The new heading is additionally required to be the file's last**, which forecloses the same edit a second way and makes file order agree with the `회차` numbering §2.9 reads. **One blank line is outside the lower bound, and nothing else is**: §2.3 fixes field order and field-line rendering but never blank-line placement, and the tokenizer keys on field name within the block rather than on any offset, so the separator blank a writer puts immediately before its new heading carries no schema content and forges nothing. The exemption stops at that position. A blank added anywhere else is bound exactly as a non-blank line is, because elsewhere a blank is not inert: one inside an open fence alters a byte-verbatim payload field even though no predicate moves, and one after the terminator moves the file's last line off the sentinel — survivable only because §2.5 states its predicate over the last *non-empty* line, which is a tolerance for a stray newline and not a licence to append past the terminator. **Blank** means `^[[:space:]]*$`. **An added terminator line is itself a construction fault.** The sentinel is a constant, so it reaches the added side only where the pre-write bytes lacked it, and those bytes are the truncated state §2.5 requires a writer to fail closed on, with recovery reserved to the user. A gate that sees `<!-- cc-design-reconverge: end -->` on the added side therefore discards the temp and reports, exactly as every other violation of this table does — a terminator silently restored by an append is the one construction fault that would otherwise erase the evidence of the truncation that produced it.
- **`처리 기록` is exactly one per closed block, not at most one.** `at most one` admits zero, and a `처리됨` block with no `처리 기록` is malformed under §2.2 — the reader's own write form would be manufacturing the state the reader must reject on its next pass. **`exactly one` excludes two just as firmly, a block carrying two is malformed by that same rule, and the second direction needs a check of its own**, because the row above constrains the *diff*: a second close of an already-closed block removes and re-adds one `상태` line and adds exactly one `처리 기록`, satisfying every cell of that row while leaving the block with two. Duplication is a property of the file, not of the diff, so no diff constraint can see it. Therefore **a block already carrying a `처리 기록` line is not a member of any close set** — it is one another reader closed inside the window, and the byte conjunct of the close set in §2.1 excludes it on the fresh read — and writing a second one into it is a construction fault under the rule above. The gate is the backstop; the close set is the mechanism.
- **This schema's read-back arm for the close form.** §1.3 fixes that the post-`mv` read-back's success predicate is containment written per write form, and requires each payload schema to supply an arm for every form it declares; the append arm §1.3 states generically covers this schema's append. For **close** the arm is: every block this attempt closed now reads `상태: 처리됨` with its `처리 기록` line at field position 2. It is stated here rather than in §1.3 because it names this schema's own fields, and it is genuinely not substitutable for the append arm — a close adds no `## 회차` heading at all, so the append arm's second conjunct is undefined for it and an `mv -n` skip would pass it vacuously on a heading the pre-write bytes already carried. **The close arm's own residual is fail-safe**: a skipped close leaves `상태: 대기`, so `unprocessed` (§2.7) stays true and the block returns on the next read.
- `sed -i ''` is forbidden. It sits on this repo's bash-portability denylist, but this file is markdown prose and `lint-bash-portability.sh` scans only `*.sh` files, so the rule is **manually disciplined** — the same posture `_common/parse-handoff.md` §10 already states for the same reason. The prohibition is load-bearing regardless of enforcement: an in-place edit is a partial write against a disk snapshot, so it bypasses both the whole-file discipline of §1.4 and the compare-and-swap of §1.3 — the two devices that stand in for the lock this contract declines. The swap is the right one to name: an in-place edit has neither a temp nor a rename, so there is nothing for the swap to gate at all, and §1.3 states outright that the read-back is not what detects a concurrent writer. Build the whole file and `mv` it (§1.3).

### 2.7 Reader predicates

- `unprocessed(sidecar)` — holds iff at least one block has `상태: 대기`.
- `surfaceable(block)` — a **further** filter on `사용자 라우팅`, applied only to un-processed blocks. It exists so that a block can be un-processed and still never be shown to the user. **This file fixes the predicate's name and its domain, and does not yet fix its mapping**: which of `사용자 라우팅`'s four values are surfaceable is written down nowhere — not here, and not in any consumer. That omission is **recorded as a debt, not delegated**: until the mapping is fixed, a reader that picks one privately and a writer that assumes another are both conforming, and `미응답` is the value most likely to be read in opposite directions, since it records that no answer was given rather than any routing the user chose. **The debt is bounded so that its worst outcome is a repeated prompt and never a lost finding**: until the mapping is fixed, a reader does not close a block it did not surface — a block the filter removed is left `상태: 대기`, so `unprocessed` stays true and it returns at the next re-convergence. Without that bound the composition of §2.6 **close** with §2.2's once-only `상태` and §1.4's never-remove rule is terminal: a finding the writer paid a failure branch to persist would be closed without ever being shown, and no later pass could recover it. **The divergence is disclosed on both sides, on the surface the user can see.** A reader implemented before the mapping is fixed states the mapping it applied, on the same user-facing surface where it raises or declines to raise blocks. A writer that emits a value in the belief it will be raised says so on its own failure surface at write time. Neither skill reads the other's prose at runtime, so the user is the only party positioned to notice that the two do not agree — which is why both statements are user-facing rather than in-file.

The two are not interchangeable, and the distinction matters: `surfaceable` decides *whether to ask*; the closing rule (§2.6 **close**, driven by the owning SKILL.md's routing policy) decides *whether it comes back*. Attributing repeat-prompt prevention to the filter is a misreading — a block that is filtered but never closed returns forever.

### 2.8 Read-time derivation of the design document's state

**A sidecar never asserts the current state of the design document.** The reader determines it directly, with **two greps plus an empty-range check** over the targeted `### R<n>` range (from `^### R<n>\.` to the next `^### ` or `^## `):

1. **Is the item flipped?** Match the verification contract's detection grammar with the key `검증 등급` and the value pinned to the terminal-token set. A hit means the document carries the flip; no hit means it is still at the save-time residual token.
2. **How many note lines?** Count lines matching the same grammar with the key `구현 시 검증 기록`. `0` means nothing to remove; `1` is the normal flipped state; **`≥2` is a compounded duplicate**, which no other check in the system detects.
3. **Empty range** (no such heading at all) means the item was migrated or removed by an earlier re-convergence — route to the already-resolved disposition, not to the reset path.

Grep 1 derives the state; grep 2 counts the notes and is the only duplicate detector in the system. Both are needed because **their disagreement is itself a malformedness signal**: a grep-1 hit with a grep-2 count of `0` is precisely the verification contract's malformed R-item — a terminal token with no adjacent `구현 시 검증 기록` line. Surface it and route to neither the flipped nor the un-flipped path; do **not** read that `0` as "nothing to remove".

Field 7 `검증 등급` is not in tension with the opening sentence. It records the verdict `implement` **reached at `관측 일시`**, which may never have been written to the document — finding out is what grep 1 is for. That record is bounded by the unavailable-observation rule of §2.2: where the observation could not be recorded, field 7 carries `검증불가(드리프트)` even where the writer's own reading was a refutation, because a refutation the file cannot evidence must not enter §2.9's evidence strength as one. The bound is a rule about the admissible *pair*, and it errs toward less weight, never more. Where the stored token and grep 1 disagree, **grep 1 wins**: the block's verdict is evidence of what was observed, never of what the document says.

### 2.9 Read-time grouping

Group blocks by `대상 항목` **verbatim** — the whole composite anchor, unparsed. **The order is fixed: filter, then group, then charter.** `surfaceable` (§2.7) is applied to the un-processed blocks first, and only blocks that survive it are grouped; a group with no surviving block is not raised at all. Run the empty-range check of §2.8 on a group **before** taking its charter, so a migrated or renumbered item is disposed of without judgment. Then take the charter from the **newest** of that group's surviving blocks — never from a block the filter removed, whose charter and §2.2 verbatim fields would otherwise reach the user the filter exists to keep them from. **Evidence strength is drawn from a deliberately wider set**: every block in the file carrying the same `대상 항목`, processed ones included, because that is what keeps a history like *drift first, refutation later* whole across the cycle that closed its first half. A processed block contributes as history and is never re-raised, so the wider set adds no prompt and closes nothing twice. A file where `unprocessed` (§2.7) holds but no group survives the filter is a normal state, not a defect: those blocks stay `대기` and return at the next re-convergence, exactly as §2.7 says a filtered-but-unclosed block does. ***Newest* is the greatest `회차 <N>`** — never `관측 일시`, whose value grammar this contract never fixes and which is carried for a human to read rather than to compare. A tie is possible wherever two blocks come to carry the same number: against a participant that does not implement the compare-and-swap, which §1.3 states is an expected state; against a hand edit, which §1.4 invites and no gate constrains; and against a file whose numbering was re-derived over bytes a truncation had already removed. Ties break on file order and the later heading wins. Under §2.6 the appended heading is also the file's last `## 회차` heading, so file order agrees with the numbering; the number is the definition and the agreement is a consequence, not a second rule. Keying on the item alone is what keeps a history like *drift first, refutation later* as one group with one owner — grouping on the item *and* the verdict would split it into two, and the second group would have no knowledge of the first.

**Do not rewrite a block's `대상 항목` anchor** after the underlying item is migrated or renumbered. The anchor is a historical reference, and the frozen-tail invariant covers it; anchor-repair duties apply to the design document, never to the sidecar.

The key is therefore **nominal and deliberately unstable**, and the three mutation branches take three different dispositions, not one. **The number is vacated** — the item was deleted, or renumbering left `R<n>` unoccupied: the empty-range check fires and the old group is disposed of without judgment. **The number is re-occupied by a different item**: the check does not fire, and the old group charters against a range that now belongs to someone else. **The item is retitled without renumbering**: the check does not fire either, and a *live* item is left with two groups that know nothing about each other — the drift block charters from the old title, the refutation block from the new one, which is the split that keeping *drift first, refutation later* in one group exists to prevent. The last two branches are **residuals that are accepted, not disposed of**; only the first is actually routed. Do not derive a key by parsing `R<n>` out of the anchor: it would survive a retitling but would silently **merge** two different items' histories across a renumbering, and a merged charter taken from a block about another claim is worse than a split. Detection, unlike keying, is partially available: the range check already reads the `### R<n>.` line, so comparing that line's title component against the anchor's costs no additional read beyond inverting the anchor rendering of §2.2, which is ambiguous wherever the title itself contains ` — `. What the comparison separates is a mutated anchor from an intact one; it does **not** separate the re-occupied branch from the retitled one, since both yield a non-empty range with a mismatched title. *Gone* is separated by the empty-range check itself, not by this comparison. This contract does not require that comparison — the retitle branch is undetected by choice, not by impossibility.

### 2.10 The field-warrant test

> **A sidecar field is warranted iff the fact it carries — as that fact held at `관측 일시` — cannot be recovered from disk at read time.**

Tree state at observation time is unrecoverable — the tree keeps changing — so it is a field. The design document's **current** state is one grep away (§2.8), so it is **not** a field. What the document said at `관측 일시` is a different fact and is not recoverable at all, which is what warrants the verbatim copies of §2.2 (`주장`, `기대 결과`, `실패 시 영향`, `분류`, the `R<n>` heading); §2.3 already fixes their semantics — true at `관측 일시`, claiming nothing about now. The observation payload, the substitution map, and the recipe **as actually run** are unrecoverable, so they are fields. The recipe's text as the document carries it is **not** a field: it is current, recoverable, and in any case determined by field 15 together with field 16. Apply the test to any newly proposed field rather than re-litigating a rejected one: **a stored snapshot of another mutating file presented as that file's current state** is the shape this test exists to exclude.

## 3. The design-drift sidecar — `docs/design-drift/{slug}.md`

Records where an implementation **knowingly diverged** from the design document it was built from, so an independent reviewer can see the divergence instead of having to rediscover it. Header:

```
# 설계 이탈 기록 — {slug}
<!-- cc-design-drift v2; writer=implement; reader=review; owner-doc=<document key>; NOT a design doc; mechanism-local, never staged by a skill -->
```

**Why this is not `## 2` with different fields.** Not because this one has "one writer" — that framing is false at the process level and vacuous at the skill level, and it should not be leaned on. At the **process** level §1.3 exists precisely because two concurrent writers are possible, here exactly as anywhere else. At the **skill** level `## 2` is equally single-writer over its frozen tail; only its two-value mutable region has a second author at all. **The real difference is that this schema has no reader-side disposition, and its readers are plural.** `## 2`'s reader writes back — it flips `상태` and inserts a `처리 기록` — and that write-back is what forces the mutable-region/frozen-tail split, the close write form, and the unprocessed/processed bookkeeping. This schema's reader is a review team that consumes blocks to ground a `design-conformance` finding and takes no disposition whatever, so every block can freeze from the instant it is appended and none of that machinery is needed. Stating the difference this way is what lets the argument survive contact: a plural read-only readership is a fact about this schema that stays true however many processes write to it.

**Self-scoring is not what this creates.** The implementer only *reports* the divergence; the judgment of whether it was acceptable belongs to a reviewer who did not write the code. A block is evidence, not a verdict — nothing in this schema lets the writer mark its own divergence approved-on-the-merits, and the one approval field records a **user's** approval, which the writer transports rather than issues.

### 3.1 Deviation blocks

Deviations accumulate over the life of an implementation, so blocks **accumulate in one file** — one file per design document. Each block heading matches exactly `^## 이탈 ([1-9][0-9]*)$`: the literal `## 이탈`, one ASCII space, and a decimal with no leading zero. `N` is `max(existing) + 1` re-derived from `$SNAP`, the snapshot §1.3 takes on this attempt, under the same rules and the same fence-aware tokenizer §2.1 uses. On the creation write the maximum is over the empty set and `N` is 1.

**Fixing the heading grammar is load-bearing, not pedantry.** This file's reader is a multi-agent review team, so *"recognise a deviation block"* has to be a predicate several independent readers evaluate identically; §3.4's append gate also counts tokenizer-recognised `## 이탈` headings. A grammar loose enough to admit `## 이탈 01` or `## 이탈 3 (수정)` lets one reader count a heading the next one does not, and the gate then disagrees with both.

**`<N>` is the only ordering key.** Blocks are read in ascending `<N>`, never by `관측 일시`: two divergences recorded on the same day have an order, and a date cannot express it. This mirrors §2.9's rule for the other schema and holds for the same reason.

**Correction is structurally impossible, so a superseding record is a new block — and it has to be recognisable as one.** A block freezes on append (§3.2) and this schema has no rewrite form, so a writer that got a record wrong cannot repair it in place. What it does instead is append a **replacement block repeating all 8 fields** — never a delta — whose field 3 (`대상 섹션`) is **byte-identical** to the block it supersedes. Field 3 is therefore the grouping key: blocks sharing it form one group, and **the greatest `<N>` in a group is the current record** while the earlier members are superseded history rather than additional divergences. Without this rule a correction and a second divergence are indistinguishable, and a reviewer counting blocks over-counts the implementer's departures.

**The residual is named rather than papered over.** Grouping by field 3 still cannot separate a correction from a genuinely *distinct second* divergence against the same design section — both yield two blocks with the same field 3. So the reader takes the newest as current **and surfaces the whole group** instead of silently dropping the older members, which keeps a real second divergence visible even when it was mis-grouped. Closing this properly would need a ninth field naming the superseded `<N>`, and §2.10 refuses it: a writer that says so in `사유` makes the fact recoverable at read time, and a fact recoverable at read time does not warrant a field.

### 3.2 Field schema — 8 fields, fixed order

| # | Field | Required | Notes |
| --- | --- | --- | --- |
| 1 | `관측 일시` | always | exactly `YYYY-MM-DD` — no time, no zone. The reference point every other field in the block is stated *as of*; it is **not** an ordering key (§3.1) |
| 2 | `티어` | always | which binding tier the deviated-from material sat in, **at `관측 일시`** |
| 3 | `대상 섹션` | always | the design document section identity that determined field 2 — a section heading, plus the decision or issue identifier where the section has them |
| 4 | `설계 진술` | always | what the design said, **verbatim**, re-read from the document at write time and copied — never restated from context |
| 5 | `구현 결과` | always | the writer's own **characterization** of what was built instead — one CANON line, never the built thing itself |
| 6 | `사유` | always | why the divergence was taken |
| 7 | `승인` | always | see the closed vocabulary below |
| 8 | `영향 범위` | always | the repo paths the divergence **landed** in, so a reviewer can scope its blast radius without inferring it. One CANON line: repo-root-relative paths, separated by ` · ` |

Field lines use the CANON rendering of `_common/verification.md`: bold key, no leading bullet, one ASCII space after the colon.

**What this schema borrows from §2.5, and what it cannot.** The **fence grammar** is borrowed by citation and holds unchanged: a payload-bearing field is a bare-colon key line — `**<key>**:`, nothing after the colon — whose next line opens a fence of `N = max(3, longest backtick run in the payload + 1)` backticks carrying the mandatory `text` info string, and a fence still open at end of file is what `tokenize_no_open_fence` rejects. **The caps are not borrowed, because they are not general rules.** §2.5's 80-line cap, its per-line character clamp, its `관측 절단` declaration and its never-truncate exception are each keyed to a **named field of `## 2`** — `관측 결과` and `실행된 레시피` — and this schema has neither field. A sentence asserting that §2.5 "applies here unchanged" is not merely loose about the caps: where the caps are concerned it has **no referent at all**, which is a harder failure than an over-broad rule and reads as coverage while providing none.

**The fence-eligible domain is field 4 alone, and it carries no cap — deliberately.** Field 4 is the design document's own text copied verbatim, so its length is **bounded upstream** by the section it was copied from; a cap here could only truncate the quotation whose whole value is that it was not truncated, and this schema has nowhere to declare that a truncation occurred. Recording the no-cap choice as a *decision* matters more than the choice itself: an unstated absence of a cap is indistinguishable from an oversight, and the next reader closes it by adding one. Every other field — 1, 2, 3, 5, 6, 7 and 8 — is a single CANON line and may not open a fence.

**Field 5 is a characterization, and the single CANON line is what bounds it.** What was built is on disk and is the very artifact the reviewer is reading, so under §2.10 the field is warranted only for what the disk cannot supply: the writer's own account of *which* reading of the built code constitutes the divergence. Holding it to one CANON line bounds its length **structurally**, which is why this schema needs no cap mechanism for it and therefore never needs a place to declare that a cap fired — closing the same gap that a ninth field would have opened. **The narrowing is not a ban on content.** Forbidding a payload outright would push a writer into re-describing code in prose, and re-description is exactly the reconstruction §2.5 forbids: point at the code, do not paraphrase it.

**A block is written after the divergent change has landed, not when the divergence is decided.** Field 1 is the instant every other field is stated as of, which only holds if every field is an *observation* at that instant — and field 8 is not one at decision time. The paths a divergence will touch are a **forecast** then, and a forecast recorded in the grammar of an observation is a claim the reviewer has no way to check. Moving the write point past the landing makes field 8 observable and costs the schema nothing it was relying on, since nothing here is consumed before the implementation exists.

**Every block is frozen from the instant it is appended, and §3.4's positional bound is the only thing enforcing that.** No field has a mutable region and no reader writes to this file, so §2.3's frozen-tail invariant applies to the whole block rather than to a tail of it. **Naming the enforcement here is deliberate**, because the invariant and its gate live in different subsections: a future paraphrase of §3.4 that keeps the readable summary *"every added line inside the new block"* while dropping the positional bound would delete this invariant's only enforcement **without touching the sentence that asserts it**, leaving a contract that still claims freezing and no longer obtains it. Anyone rewriting §3.4 is rewriting this invariant too.

### 3.3 Closed vocabularies

| Field | Values |
| --- | --- |
| `티어` | `구속` \| `참고` |
| `승인` | `사용자 승인` \| `불요(참고 티어)` |

`승인` has exactly two values because the tier already decides which is admissible: a `구속`-tier deviation is only ever taken under explicit user approval, and a `참고`-tier deviation never needs one. A `구속`-tier block carrying `불요(참고 티어)` is therefore **malformed**, not merely unusual — it asserts a binding-tier divergence that nobody approved, which is the one combination this schema exists to make unwritable.

**The rule covers absence exactly as it covers the wrong value.** A `구속`-tier block whose `승인` line is **missing** asserts the same unapproved binding-tier divergence, and does so more quietly: there is nothing on the page for a reader to object to. Both states are malformed and take §3.5's disposition. This has to be said because the sentence above is a rule about a *combination*, and a combination rule is vacuous on a field that is not present — which is precisely the state a write path that eats a field line produces.

**`미확인` is admitted on fields 4 and 8, and nowhere else.** The writer of a `설계 진술` whose source has since been renamed or removed has three options — fabricate a quotation, discard the whole record, or say the source could not be recovered — and only the third is acceptable, so the token exists to make it available. Field 8 takes it for the same shape of reason: a blast radius can be genuinely unknown at write time. The other six fields have no `미확인` rendering, because each is something the writer knows by construction at the moment it diverged: when it happened, which tier, which section, what it built, why, and whether a user approved. **Reader-side bound**: a `미확인` field is not a groundable value — a reviewer may not ground a `design-conformance` finding on one — but it does not poison the block, which stays groundable on its remaining fields. `미확인` is a stated gap, and a stated gap is what distinguishes this from the malformed states above.

### 3.4 Write form and its diff gate

One write form: **append**. The writer emits a whole new `## 이탈 <N>` block with all 8 fields through the compare-and-swap of §1.3, with `$FORM` bound to `append`.

**The gate is §2.6's append row, cited and then adjusted — not paraphrased.** A paraphrase is what dropped the positional bound once already. Take the row's four conjuncts as written and apply exactly these substitutions, which are the whole of the delta:

- the heading token is `## 이탈`, never `## 회차`;
- the terminator is the sentinel §3.6 fixes, not §2.5's;
- there is no close form in this schema, so the companion close row and its one-`처리 기록`-per-block rule have no counterpart here and nothing in them may be carried across.

Read that way the constraint is: **0 removed lines**; exactly one new tokenizer-recognised `## 이탈` heading, and it is the **last** such heading in the written file; every added line lies **at or after** that heading and **before the terminator**; the sole exception is one added blank line **immediately preceding** the heading, which is the block separator. The readable summary *"every added line inside the new block"* is a summary of the positional bound and **not a substitute for it** — §3.2's frozen invariant rests on the bound.

**Carry-forward strips through the file's last non-empty line**, per §2.6's carry-forward rule, and that rule is sound here **only because §3.6 fixes a terminator**: the line it strips is the sentinel. Under a schema that fixed none, the same rule strips a real field line — and the diff gate does not see it, because `diff` aligns the removed field line against the byte-identical line the new block re-emits and reports nothing removed. That is the failure this section's terminator exists to close, and it is why the terminator is a property of the schema rather than of any gate predicate.

A write that removes or edits a line of an existing block fails the gate: `## 3` has no rewrite form, and `sed -i ''` is forbidden here for the same reason §2.6 forbids it. **Creation reaches no diff gate at all** — the absent-pre-write-bytes state is dispatched by §1's universal creation clause before any gate is evaluated, so nothing here needs to re-state an exemption; §3.6 fixes what the created file contains.

### 3.5 Reader predicate

`review` reads the file only after the §1.2 read guard passes. A block is **groundable** iff it is **well-formed**, and this schema owes that definition rather than pointing at one. A block is well-formed iff all three hold:

1. **Completeness and order** — all 8 fields of §3.2 are present in the fixed order, each as a CANON line, or (field 4 only) as a bare-colon key line followed by a closed fence.
2. **Vocabulary** — `티어` and `승인` carry values from §3.3, and `승인` is admissible under the block's own `티어`. An absent `승인` fails this, exactly as an inadmissible one does.
3. **Gap tokens** — any `미확인` sits on field 4 or field 8.

**Line rendering is not a well-formedness axis.** A leading bullet or a missing bold is absorbed by the detection grammar of `_common/verification.md` §3.4 and must not be reported here — the same posture that contract takes for its own residual-item predicate, and for the same reason: a rendering difference is a style note, not a defect in the record.

**A malformed block is surfaced to the user — never consumed, never silently skipped.** The reader states which block, which of the three conditions failed, and what it therefore did not ground. This disposition is load-bearing beyond tidiness: this surfacing is the **only reader-side detector** that a write path corrupted this file, and it detects the *damage*, not its cause — it reports that a block is malformed, never that a write ate a field. That is worth stating plainly so nobody mistakes a green reader for a healthy writer.

**Read-time derivation, and what a mutated design document does to it.** Field 3 names a section of the design document, and the reader resolves that heading against the document **as it stands at read time**, not as it stood at `관측 일시` — the same lookup shape §2.8 gives the other schema's reader. Three outcomes, and the schema owes all three:

- **resolves** — the section is the live baseline; ground the divergence against it.
- **retitled or removed** — the anchor resolves to nothing. The block is then **historical context, not a live baseline**: it records that a divergence was taken against text that no longer exists, which is worth reading and is *not* something a `design-conformance` finding can be grounded on today. Report it as unresolved rather than dropping it.
- **never repair the anchor.** Field 3 is frozen with the rest of its block, and anchor-repair duties belong to the design document, never to this file — the rule §2.9 states for its own anchors, holding here for the stronger reason that this schema has no rewrite form at all.

**Field 8 is the reader's only diff-scoping key, and the cross predicate is this:** a block is *in scope for the diff under review* iff at least one path in its field 8 is touched by that diff. Without the scoping, every block ever recorded is re-grounded against every later PR, so an accumulating file becomes an accumulating tax on unrelated work. The CANON grammar §3.2 fixes for field 8 — repo-root-relative, one line, ` · `-separated — is what makes this predicate mechanical instead of interpretive; an unfixed value grammar would leave each reader to guess at path boundaries.

There is no unprocessed/processed distinction — the reader takes no disposition, so every groundable block is available on every read, and a reviewer that has already seen one is not a state this file tracks.

### 3.6 File terminator and creation emission order

The last **non-empty** line of the file is the fixed sentinel `<!-- cc-design-drift: end -->`, emitted by every write form, the creation write included. Trailing blank lines and trailing newlines are stripped before comparing — the same tolerance §2.5 states for its own sentinel, and for the same reason.

**Creation emission order.** A created file contains, in this order: the H1 of `## 3`, the machine header of `## 3`, one complete `## 이탈 1` block, and the terminator. Nothing else. The order is this schema's own; the *exemption* that lets a creation write past the diff gates is not — that is §1's universal creation dispatch, and re-stating it here is what §1 exists to make unnecessary.

**Why a terminator, and why it could not have been a gate.** Without one, `$SC_TERM` had a contract-conforming empty value, and an empty value short-circuits both the truncation check and the completeness check of §1.3 at once. The carry-forward rule of §3.4 then strips a required field line rather than a sentinel, and no `gate_write_form` predicate can catch it: `diff` is content-based, so it aligns the removed line against the byte-identical line the incoming block re-emits, and the removal never appears on the removed side. Two blocks whose last field values differ do get rejected — which is why the failure looks intermittent from the outside. The recovery path is empty by construction (§3.2 freezes a block on append, §1.4 forbids deletion and truncation, and this schema has no rewrite form), so the loss is permanent where it lands. Fixing this at the schema is the only place it can be fixed.
