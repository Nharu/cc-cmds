#### Planning the segments

Segment planning starts only after the audit has ended as above, or straight after item 5's freeze check when the plan names no audit step.

**A reviewer run is the one exception: it plans one review-only segment per pull request** (「Reviewing pull requests on a reviewer run」 below). Its plan reads `run_profile: reviewer` and its one step is a `review`; it has no design, no audit and no `슬라이싱` — the snapshot prints `리뷰 세그먼트` instead.

**A plan with no `implement` step plans no segment** — the reviewer run aside. When `steps[]` names no step whose `skill` is `implement`, the graph ends at the design — or at the audit, when the plan names one — and there is nothing to plan. Once item 5's freeze check passes and, when the plan names an audit step, the check after the audit in 「Dispatching the audit stage」 passes too, nothing is left to dispatch: propose done, with each clause's evidence the design (and audit) step's `stage-result` row and the document's freeze line. Do not settle a clause as `불가능` because no segment exists: in that state termination condition 1 holds, so when every clause is settled satisfied the gate records the proposal as satisfied.

The snapshot's `슬라이싱` field is the read: its branch (`미통치`, `선언통치`, `선언불완전`), the slice ids in declaration order, and each id's branch name, worktree path and base ref. A slice the planning rule below defers gets none of the three calls — no `git fetch` and no `git worktree add -b` either — until that rule plans it. **For each slice, in declaration order, three calls:**

1. `gate.sh exec … --surface 읽기 -- git fetch origin` against the slice's target. When the slice's `슬라이싱` `베이스` begins with `refs/heads/`, that target has no remote: skip this call and fetch nothing.
2. `gate.sh exec … --surface 워크트리쓰기 -- git worktree add -b <슬라이싱 의 브랜치> <슬라이싱 의 워크트리> <슬라이싱 의 베이스>`. `<슬라이싱 의 베이스>` is the `베이스` of the slice's `슬라이싱` entry written verbatim — a remote-tracking ref such as `refs/remotes/origin/master`, or `refs/heads/<base>` for a target with no remote — and never a local branch name (`main`, `master`) or `HEAD` in its place; when call 1's fetch fails, call 2 still uses that same value. When the gate refuses call 2 because its start point is not the base ref it expects, call 2 once more with the ref the refusal names.
3. The plan row, which the gate fills from the frozen document rather than from this loop:

   ```
   gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <slice id> \
     --cutpoint <token> --surface 읽기 --snapshot-digest <H> --from-declaration \
     -- 상태=계획됨 워크트리=<슬라이싱 의 워크트리>
   ```

   Pass no `레포`, `선언 파일 집합`, `선행`, `절단점` or `리뷰 정책`: under `--from-declaration` the gate refuses them, takes them from the document's `## 구현 슬라이싱`, and requires `워크트리` to be the derived path. On `미통치` the segments are the plan's implementation steps: with no `세그먼트 입양` row, the first one, on the home target; with adoption rows, every step a row names, each on the target whose common git directory the row's worktree shares, and at most one step no row names, on the home target. The snapshot's `슬라이싱` lists each with its `대상`, and the planning act refuses a segment outside that set or a `--target` other than the one listed.

**A slice with a `선행` is planned only once its predecessor's `segments[]` entry reads `"착지": true`**, so its branch is cut from a base that already carries that landing. That value is the dispatch floor's own landing judgment, and it covers both a segment whose last `segment` row is `머지됨` or `완료` and one parked after a `머지됨` — unless that merge still owed this run its apply. A `머지됨 적용=대기` segment whose target's applies a target stop holds reads `"착지": false` until the stop is released. **A slice is planned when two conditions hold together**: every `선행` token's predecessor reads `"착지": true` in its `segments[]` entry, and every `머지 순서` token of the slice — read from the snapshot's `슬라이싱.세그먼트[]`, because a slice with no row yet is not in `segments[]` — already has a `segment` row. A slice whose `선행` is `없음` and whose `머지 순서` tokens all have rows is planned and dispatched at once, cut from the current base. **A slice whose `슬라이싱` entry reads `"착지 행": true` and that has no `segments[]` entry is brought in, not built**: the manifest carries a `선행 착지` row for it, so issue call 3 alone at once, whatever its `선행` and `머지 순서` read — no `git fetch` and no `git worktree add -b` — with `--target` the entry's `대상`, or the alias whose `home` is `예` in `targets[]` when `대상` is empty, and `워크트리=` the entry's `워크트리`, or `-` when it is empty; the act writes the slice's own `상태=머지됨 · 출처=매니페스트` row and no planned row, so do not dispatch it, and its dependents are planned by the rule above once its `segments[]` entry reads `"착지": true`. A refusal with exit 3 here ends the shift as the predecessor import's refusal below does. A `머지 순서` token with no row yet (that slice still waits on its own `선행`) defers the slice until the row appears, and a slice carrying both lists follows the same product: with D `선행` A and D `머지 순서` C, D waits for C's row even after A has landed. Planned earlier, the slice is refused with exit 2 by the floor that requires every token to name a segment this ledger knows. The two imports below — a predecessor an earlier run already merged, and one the manifest's `선행 착지` row names — apply to a `머지 순서` token as well, and the planning act writes that predecessor's row itself; without them the row would never appear and the slice would never be planned. With C `머지 순서` B and B `선행` A, B is planned after A lands, and C is planned once B's row exists and runs alongside B. Pass no `머지 순서` on the planning row: the gate writes it from the declaration and carries it forward. **A predecessor an earlier run of the same document already merged needs no row from this loop**: the planning act above finds it in that run's ledger, checks its `머지 커밋` against the base branch, and writes its terminal row with `출처=<that run's id>` before the slice's own row — so plan the dependent slice directly, and never hand-write a `segment` row for the predecessor (a caller's `출처=` is refused). **A predecessor no run ledger records is brought in the same way from the manifest's `선행 착지` row**, which the kickoff froze after a person confirmed it — the row is written with `출처=매니페스트`, and for a repository this run does not target the gate asks the remote whether the commit is on its default branch. When that check refuses with exit 3 (the earlier merge or the row's commit has not landed, cannot be judged, or still owes its apply, or the row's slug is not the slice's `레포`), the refusal names where it looked; write nothing more and end the shift with a `사유=중단` handoff, as for the structural refusals below. A slice with no `segment` row has nothing a `shift-halt` can stop, so this stays a handoff. **A refusal with exit 2 saying a token 「is declared in the frozen document and has no segment row on this ledger yet」 is a deferral, not an ending**: write nothing, make no `사유=중단` handoff, say nothing of a new run, and plan the same slice again once that token has a row. Any other refusal with exit 2 naming a predecessor that no ledger shows landed — a slice the document does not declare, or one whose `레포` is not a target of this run — is the same ending: a run cannot gain a `선행 착지` row after its kickoff, so say in the handoff that a new run with that row is what plans the slice. When an earlier pass already made the slice's derived branch and worktree (the `슬라이싱` entry's branch and worktree), planning it again does not cut them a second time: skip calls 1 and 2 and issue call 3 alone. When a slice is planned, dispatch its implementation with the stage form above. **Two refusals are structural**: `선언불완전` (the refusal names the slice and the missing fields) and a resolved review policy other than `리뷰없음` on a plan that has no review step. The gate leaves the run-scope block for either inside the refusing act — this loop cannot create a run-scope block — so write nothing more and end the shift with a `사유=중단` handoff.

**A slice whose `슬라이싱` entry carries `입양` is a segment an earlier run cut**, handed to this run by the manifest's `세그먼트 입양` row: its `브랜치` and `워크트리` are that run's, and `입양` names the run — or is `-` for a branch a person cut outside any run, which has no earlier run, ledger or halt answer and is otherwise routed the same way. The branch and the worktree already exist, so skip calls 1 and 2 and issue call 3 alone, with `워크트리=<슬라이싱 의 워크트리>` as for any slice. The gate plans it only when that worktree is the target's, has that branch checked out, the earlier run did not land the segment, and none of the earlier run's stages is still running on it; on its refusal (exit 3, naming which) write nothing more and end the shift with a `사유=중단` handoff — except a refusal ending in `거절 부류:` on an entry that carries `머지 입양` too, which the next paragraph routes. **An answer the earlier run took and never handed on comes first.** When the earlier run's ledger holds a person's `중단 답` on the segment that no later `stage-result` row of it took up, and that answer is `재수렴` to an implement stage's binding-tier stop (CFI-U3 BT-STOP), a person's `재수렴` to an implement stage's refutation stop (`Step 1.5d`, `Step 1.5a 반증 대기` or `Step 3 구현 중 반증`) whose item's carrier block still waits in the design document, or one an `이월` row of that ledger names (a carry act of that run found no account with room before its deadline and kept the answer for the next run), or — with no such row — a `좌석 실행` answer to an implement stage's seat-run stop (a step beginning `Step 3 잔여 검증 좌석 실행` or `Step 3 게이트 도달 좌석 실행`) followed in that ledger by a `사유=마감 초과 — <segment>` row and no `stage-result` row of the segment, the planning act copies the halt record under this run's `halt/` and writes the answer as this run's own `중단 답` row with `출처 런` and `출처 기록`; read the snapshot again and route the `answered_halts[]` element, whose `origin_run` names the run the person answered in, by 「Handing on a person's answer to a halt」 before the first stage below — a binding-tier `재수렴` by item 5, a refutation `재수렴` (`route` `반증-재수렴`) by `refutation-reconverge.md` instead, an answer an `이월` row named and a `좌석 실행` answer by item 3's carry act. Until that carry act takes the answer, the gate refuses every other dispatch on the segment, the first stage included, with exit 3 and names the `--carry-answer` line. Any other open answer stays with the earlier run — its route re-attaches the halted session, which is that run's — and the planning act names it in a warning; carry that warning into the handoff's `막힌 지점` so the seat can put the question to the person again, and go on with the first stage. A person's `승인` at the shift's `강제 표면 승인` stop is neither carried nor warned about when the earlier ledger vouches for it: its approval rides this run's manifest as `강제 표면 승인` rows. **An adopted segment's first stage is a full review, not the implementation, when the entry's `PR` is a number** — its code is already on the branch. Push the branch first (`gate.sh exec … -- git push origin <슬라이싱 의 브랜치>`) so that the pull request's head is the worktree's HEAD, then dispatch the review of the pull request the entry's `PR` names, the way a segment's first review is dispatched; its findings come back through 「Re-dispatching the implementation after review findings」. **Open no pull request for it**: `PR` is the segment's pull request, and the merge row carries that number. **When the entry's `PR` is `-`, the earlier run stopped the segment before its pull request, and its first stage is the implementation.** Push nothing. First read the remote once with `gate.sh act --kind remote-check --target <alias> --segment <id> --cutpoint 커밋 --surface 읽기 --reach 협업` (nothing after `--`), so this run's ledger holds the segment's own `원격 판독` row — a run after this one reads its adoption evidence there. Then, with an answer brought in, its carry act above is the first stage; without one, dispatch the implementation in the stage form above, as for a slice no run cut. From there it is routed like any other slice: review, then the pull request opened on the ordinary path, then the merge.

**A slice whose `슬라이싱` entry carries `머지 입양` is a pull request merged outside this run**, handed to it by the manifest's `머지 입양` row for a review after the fact; `머지 입양` names the pull request. When the entry carries `입양` too, the open fix pull request an earlier run left comes first: route the segment by the paragraph above, in that row's branch and worktree, and its first review — of the fix pull request — covers the merge as well, because the fix branch was cut from a base past it. Otherwise plan it as any slice: calls 1 and 2 cut its branch and worktree from `origin/<베이스>`, and call 3 plans it. Pass no `리뷰 정책` on its planning row either way: the planning act resolves the policy to `선리뷰후머지` itself, and the gate refuses any first row of the segment other than that `--from-declaration` act or a `park`. The planning act reads the pull request on the remote again, fetches its head, and writes the segment's `리뷰 의무` row before its planned row. **Its refusal (exit 3) parks the segment, not the shift**, and its text ends with the refusal's class. When the entry carries `입양` too, its branch and worktree are the earlier run's and may hold that run's uncommitted or unpushed fix, so the refusal removes and deletes nothing: on `거절 부류: 재시도 가능` issue call 3 alone once more, and a refusal with no class, first or second, is the paragraph above's and ends the shift as that paragraph says. Otherwise, on `거절 부류: 재시도 가능` take call 1, `gate.sh exec … --target <대상> --surface 워크트리쓰기 --destructive -- git worktree remove --force <워크트리>`, `gate.sh exec … --target <대상> --surface 워크트리쓰기 --destructive -- git branch -D <슬라이싱 의 브랜치>`, call 2 and call 3 again once, in that order — the removal leaves the branch the first call 2 cut, which holds no commit of its own yet, and call 2's `-b` fails on a branch that exists. Either way, on a second refusal, on `거절 부류: 영구`, or when call 1 or 2 fails, write `act --kind segment --target <대상> --segment <id> -- 상태=park 워크트리=<워크트리> 선행=없음` and a `blocked` row saying why, and go on with the shift. The gate takes that `park` as the first row of a `머지 입양` segment with no planning row, as it does for a `리뷰 PR` segment, and a refused planning act wrote no `리뷰 의무` row, so no open obligation holds the run on the parked segment. **Its first stage is a review, not the implementation**: while `review_next[]` reads `사후리뷰`, write `상태=사후리뷰` and dispatch the line `gate.sh review-line` prints, unchanged, with `--trigger '첫 리뷰'`, then record its `cycle` row with the report's `리뷰 HEAD`, which is the line's `--judge-head` value. Then branch on `review_next[]` (「Branching on `다음` after a review」): `입양 종결` closes the segment with no push and no pull request, and a fix takes the ordinary `선리뷰후머지` path on the segment's own branch — record `act --kind obligation` once a passing review covers the fix, before that fix merges.

**The decisions are collected before the first implementation plans.** The gate's first process A implement dispatch of the run collects every `구현 전 결정` entry of the design document into one halt record, `halt/decision-collect-<digest 12>.md`, which lists each entry with its recommendation, and writes a `결정 수거` row naming the segments the entries reach. A process A dispatch of such a segment is refused with exit 3, the refusal naming the record, whether the record was answered or not. That refusal is not a park and needs no row: count the segment as waiting on a person, as the snapshot's `decision_holds[]` shows it, and go on dispatching the segments it does not hold. The record is a person's question — the seat asks it, and the answer comes back through 「Handing on a person's answer to a halt」 with route `구속-재수렴`. When only held segments are left and nothing else can move, end with `사유=중단`, naming the record in `막힌 지점`.
