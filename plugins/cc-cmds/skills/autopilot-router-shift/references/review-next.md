#### Branching on `다음` after a review

Once a segment has a `cycle` row and has not merged, the snapshot's `review_next[]` carries one element for it: `세그먼트`, `다음`, and the last cycle's `사이클`, `리뷰 HEAD` and `리포트 경로` (absolute). **`다음` is the only value you branch on after a review** — not the counts in `cycles[]`, not `review_carry`, which carries the gate's cycle cap `REIMPL_CYCLE_CAP` and re-check round cap `RECHECK_ROUND_CAP` for display only. The gate derives it from the ledger and the report by the table in `_common/pipeline-sidecar.md` §3.2, and the merge rule reads the same facts in the same order, so a branch taken on anything else meets a refusal. Take it only when that review's `stage-result` row is `정상 완료` and the segment has no live stage:

- **`머지`, `이월 머지`** → 「Merging and applying a segment」.
- **`이월`** → carry the findings over by `_common/carryover-issue.md`: one issue per finding, then the `리뷰 이월` row (`act --kind review-carry`), then read `다음` again and merge on `이월 머지`. `이월` comes only after the lead fix's re-check.
- **`수정`** → 「Re-dispatching the implementation after review findings」. On a target whose cutpoint is `PR`, `머지` or `배포` a review that asks for a fix reads the CI of its HEAD first, so the same review can read `CI 대기`, `CI 재실행`, `CI 대기 한도` or `CI 합류 수정` instead — each is routed below, and `수정` comes once CI passed, has no run on that head, failed on a cause the base branch shares, or its rerun is still unresolved.
- **`리드 수정`** → the segment reached the cycle cap and has had no lead fix, or a re-check left findings and the segment's re-checks are still within `RECHECK_ROUND_CAP` (2) rounds after the first. Dispatch it once, with the branch and the `설계는` directive of the segment's review line (「Spelling a review dispatch」) and `--lead-fix` naming the element's `리포트 경로` — no `--report-path` or other review flag, as the fixed-graph driver sends it. `--segment` is required: it binds the stage to that segment, whose acts carrying `--segment` run in the segment's worktree, where it commits to the segment branch and pushes it when the target's cutpoint is `push` or above. The stage session itself starts in the directory this shift is in, not in that worktree. Write no `segment` row for it:

  ```
  gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <seg> \
    --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> \
    --rationale '리드 수정 — 사이클 <사이클> 리포트' \
    -- lead-fix -p '/cc-cmds:review-unattended <브랜치> --lead-fix <리포트 경로> "설계는 <문서 인자>"'
  ```

  The gate refuses (exit 3) a lead fix unless `다음` is `리드 수정`. Each time `다음` reads `리드 수정`, dispatch one lead fix: **do not dispatch it a second time in the same round**, whatever it ended as — a crash, a usage limit or a continuation that ran out included. Once its row lands, `다음` reads `확인 리뷰`.
- **`확인 리뷰`** → a lead fix, or a re-implementation, follows the last cycle. Dispatch the segment's review as you would any review, with `--recheck <리포트 경로>` added to the prompt, `<리포트 경로>` being the element's — the report the step answered. Its `cycle` row is a re-check, and `다음` after it is `머지`, `이월`, `이월 머지`, `리드 수정`, `재수렴` or `잔여 보류`. **Not while the segment has an `implement_next[]` element whose `다음` is not `리뷰`**: a re-implementation's process A that only emitted its plan already turns `다음` to `확인 리뷰` while the branch holds nothing of the new plan, and the gate does not refuse that review — route the segment by 「Routing a segment after its implementation ends `정상 완료`」 instead.
- **`재수렴`** → the re-check's report classes at least one remaining finding `설계` in its `결함 수준` lines, the manifest names a design document, and the segment has not re-converged since its first lead fix. Dispatch the re-convergence once, on that report, with the document as its main-worktree absolute path (the snapshot's `design_doc`), as 「Routing a pre-implementation refutation to re-convergence」 item 5 spells it. Write no `segment` row for it:

  ```
  gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment <seg> \
    --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> \
    --rationale '재수렴 — 설계 수준 잔여 사이클 <사이클>' \
    -- reconverge -p '/cc-cmds:design-reconverge <스냅숏 design_doc> "설계 수준 잔여 <리포트 경로>"'
  ```

  The gate refuses (exit 3) this scope unless `다음` is `재수렴` and `<리포트 경로>` is the element's. Once its row lands, `다음` reads `재구현` when it ended `정상 완료` and `리드 수정` otherwise — a failed re-convergence is not a park, and the segment has no second one. Under `판정: 재설계 필요` re-plan the **other** segments through `replan_due[]` exactly as that subsection's item 6 says; this segment's own plan is voided by its `종류=reconverge` row.
- **`재구현`** → a re-convergence ended `정상 완료` after the last cycle. Dispatch the implementation once as 「Re-dispatching the implementation after review findings」 spells it, with the element's `리포트 경로` as the fix target and `<n>` the element's `사이클`. The gate lifts its cycle-cap refusal for this dispatch while `다음` reads `재구현`; once its row lands, `다음` reads `확인 리뷰`. The lift reaches the same re-implementation's later runs: while `다음` reads `확인 리뷰`, a `정상` re-convergence follows the last cycle, no lead fix follows it, and the segment's `implement_next[]` element reads `구현`, the gate still admits the implementation, so a process A that only emitted its plan is followed by its process B and not by the re-check. The `무커밋 구현` limit bounds those runs.
- **`잔여 보류`** → the segment's re-checks passed `RECHECK_ROUND_CAP` (2) rounds after the first and the last left a P0, a blocking P1 or a P1 classification that does not parse. File one issue and park:
  1. `gate.sh residual-body --manifest <매니페스트> --segment <seg>` prints `잔여 제목=`, `잔여 본문 파일=` and `잔여 부류=`; the gate writes the body file. A segment with no pull request yet — a review-before-merge segment has none until its review passes — gets a body that names its branch and the last re-check's `리뷰 HEAD` instead.
  2. Create the issue through the gate: `gate.sh exec … --cutpoint 커밋 --surface 외부상태변경 --reach 협업 --rationale '리뷰 잔여 — <seg>' -- gh issue create --repo <slug> --title '<잔여 제목>' --body-file <잔여 본문 파일>`. The URL is the last output line; try a failed create once more. **Do not add `--assignee`.**
  3. Write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` `blocked` row with `원인=막힘`, `'사유=리뷰 잔여'`, `이슈=<url>` and a `근거` that starts with the `잔여 부류` value. Write no `재킥 원인`. When `residual-body` exits 3 or the create fails twice, write the same rows without `이슈=` and put the failure in `근거`.

  **A termination clause this segment leaves unmet is written one way**: `불가능`, with a `근거` that names the residual issue's URL — or the failure, when there is none — and the `잔여 부류`. Not `보류`: no answer is owed, and the issue is where the findings now live.
- **`베이스 해소`** → the reviewed HEAD, or the renumbering merge of it the gate proved, conflicts with the base the latest `베이스 판정` named. Dispatch the segment's implementation with the element's `베이스` on a line of its own in the prompt — `베이스 해소: <베이스>` — and the element's `충돌 파일` and `부류` beside it. The gate refuses (exit 3) a `베이스 해소:` prompt unless `다음` is `베이스 해소` and the sha is that `베이스`; the dispatch spends no cycle budget. Under `부류=릴리스 메타` the stage runs the gate's `meta-merge` helper and pushes; otherwise it merges the base and resolves the conflict. Once it pushes, `다음` reads `해소 리뷰` — or `머지` again for the helper's merge, which the gate proves without a review.
- **`해소 리뷰`** → the worktree moved past the reviewed HEAD. Dispatch the segment's review as you would any review, with `--resolve-basis-cycle <기준 사이클> --resolve-basis-head <기준 리뷰 HEAD> --resolve-base <베이스>` from the element added to the prompt. Write its `cycle` row with `모드` and `기준 사이클` copied from the report's `리뷰 모드` line as **The row's mode is copied from the report** says: `- **리뷰 모드**: 해소 (기준 사이클 <n>, 기준 리뷰 HEAD `<sha>`, 베이스 `<sha>`)` → `모드=해소 '기준 사이클=<n>'`. A `cycle` row the gate refuses for a `해소` claim is repaired by no row: re-dispatch the review as a full review without the three flags. A passing resolution review makes its `리뷰 HEAD` the next reviewed HEAD, and the base is checked again before the merge.
- **`베이스 해소 한도`** → the segment has conflicted with its base more than three times. Stop the segment at site `베이스 해소 한도` (「Stopping one segment for a person」), with the four `베이스 판정` rows' `베이스` and `충돌 파일` in `관측`, and go on with the other segments.
- **`판정 불가`** → the last cycle's `P0` or `P1` is empty or not a canonical count. Write a segment `park` row and a `스코프=cone` block with `'사유=리뷰 집계 판정 불가'`.

**The thirteen CI values come only on a routed run, where the review would otherwise merge or send a fix.** Their elements also carry `head sha`, `PR`, `실패 체크`, `재실행 회차` and `기본 브랜치`, and a `CI 대기 한도` element `상태` and `대기 시계` besides. The four that compare with the base branch — `CI 대조`, `master 대기`, `master 재합류` and `master 수리 불가` — also carry `사건`, `master 상태` and `판독 관측`, and a `master 수리 불가` element `처음 커밋`, `서명 요약` and `수리 사유` besides, a `master 재합류` element `베이스` and `판정` (the segment's latest `베이스 판정` row).

- **`CI 재실행`** → a check of the HEAD failed, and its rerun budget is not spent or its last request never closed. First issue the pre-authorized `gate.sh exec … -- git fetch` as before the base check, then the rerun act with the element's `head sha` — the gate chooses the runs, checks that none can deploy, and sends the request itself:

  ```
  gate.sh act --manifest <매니페스트> --kind ci-rerun --target <alias> --segment <seg> \
    --cutpoint PR --surface 외부상태변경 --snapshot-digest <H> \
    --rationale 'CI 재실행 — <seg>' -- 재실행 <head sha>
  ```

  Exit 0 → read `다음` again (usually `CI 대기`). Exit 3 naming a missing base object → fetch once and issue it once more. **Every other exit 3 is one disposition**: the gate folds every refusal — a pending check, a busy lock, a moved head, a run not finished, an empty failure set, a `다음` that is no longer `CI 재실행` — into 3, so the code does not tell you why. Read `다음` again and take that value's branch, and do not issue the act a third time for the same head in this shift. Exit 11 → stop the segment at site `도달 거부` (「Stopping one segment for a person」), never retried by you.
- **`CI 라벨 인정`** → a check the kickoff let a label answer failed on the HEAD — the manifest's `라벨 인정` row names it for this segment's target — or the label round of this head never closed or closed `실패`. First issue the pre-authorized `gate.sh exec … -- git fetch` as before the base check, then the label act with the element's `head sha` — the gate checks that the slice declared the check, that the label starts a new run and that nothing it wakes can deploy, and puts the label on itself:

  ```
  gate.sh act --manifest <매니페스트> --kind label-ack --target <alias> --segment <seg> \
    --cutpoint PR --surface 외부상태변경 --snapshot-digest <H> \
    --rationale 'CI 라벨 인정 — <seg>' -- 라벨 <head sha>
  ```

  Exit 0 → read `다음` again (usually `CI 대기`). Exit 3 naming a missing base object → fetch once and issue it once more. Every other exit 3 is the same one disposition as the rerun act's: read `다음` again and take that value's branch, and do not issue the act a third time for the same head in this shift. Exit 11 → stop the segment at site `도달 거부` (「Stopping one segment for a person」), never retried by you.
- **`CI 대기`** → CI on the HEAD is still running, has not been observed yet, or the rerun's result has not been observed yet. Do nothing for this segment; when nothing else is dispatchable, end with `대기` carrying `'CI 대기=<id>'`. The gate refuses (exit 3) a review fix dispatch while `다음` reads `CI 대기`, `CI 재실행`, `CI 대기 한도`, `CI 대조`, `master 대기`, `master 재합류` or `master 수리 불가`.
- **`CI 대기 한도`** → the wait on this HEAD's CI passed its two-hour cap with no verdict. Write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` `blocked` row with `원인=막힘` and `'사유=CI 대기 한도'`, whose `근거` names the element's `상태`, `재실행 회차` and `대기 시계`, and go on with the other segments.
- **`CI 합류 수정`** → the review asked for a fix and a check of the HEAD failed again after its rerun, on a cause the base branch does not share. Dispatch the implementation as 「Re-dispatching the implementation after review findings」 spells it, with ` · CI 합류: <head sha> · 실패 체크: <…> · PR: <…>` added after the fix target from the element's values, so the review's findings and the CI failure go to one stage. The gate refuses (exit 3) a `CI 합류:` line unless `다음` reads `CI 합류 수정` and the sha is the worktree tip, and refuses an implementation without that line while `다음` reads it. Unlike `CI 수정` it spends the cycle budget as `수정` does.
- **`CI 수정`** → the rerun failed again on a cause the base branch does not share. Dispatch the implementation as 「Re-dispatching the implementation after review findings」 spells it, with `CI 수정: <head sha>` on a line of its own in the prompt and the element's `실패 체크` and `PR` beside it. It spends no cycle budget: the gate lifts its cycle-cap refusal only while `다음` reads `CI 수정` and the sha is the worktree tip. Once it pushes, `다음` reads `CI 리뷰`.
- **`CI 리뷰`** → a CI fix moved the HEAD. Dispatch the full review of the new HEAD as you would any review; a passing cycle makes it the reviewed HEAD, and its CI starts at round 0.
- **`CI 기존 실패`**, **`CI 수정 한도`** → the rerun failed again and the base branch fails the same workflows, or the CI fix budget is spent. Stop the segment at site `병합 거절` (「Stopping one segment for a person」), with the failing check names, `재실행 회차` and `기본 브랜치` in `관측`. A `재시도` answer takes the merge again, and passes once a later observation reads `통과`.
- **`CI 대조`** → the rerun failed again while the base branch's CI is red, or after the base fixed a failure the segment does not have yet. Compare the HEAD's failure with the base branch's through the match act, with the element's `head sha` — the gate only reads check runs and job logs and writes the result:

  ```
  gate.sh act --manifest <매니페스트> --kind ci-match --target <alias> --segment <seg> \
    --cutpoint PR --surface 읽기 --snapshot-digest <H> \
    --rationale 'CI 대조 — <seg>' -- 대조 <head sha>
  ```

  Exit 0 → read `다음` again; it reads one of the three `master` values below, `CI 수정` (the failure adds something the base does not fail on) or `CI 수정 한도` when the CI fix budget is spent, or the merge the table gives (a repair run's pass). **Every exit 3 is one disposition**, as for `CI 재실행`: read `다음` again and take that value's branch, and do not issue the act a third time for the same head in this shift.
- **`master 대기`** → every failure of the HEAD is one the base branch also fails on, or the match could not tell, and the base is not fixed yet. Rest only this segment; when nothing else is dispatchable, end with `대기` carrying `'master 대기=<id>'` (beside `'CI 대기=…'` when there are CI segments too). The gate wakes your successor when the base branch's reading moves — another state, other signatures, another event — or goes stale; the successor reads `다음` again. Once the reading has moved — other signatures, another event — `다음` reads `CI 대조` again, and the match act runs once more against the new reading; a reading that differs only in its tip or in when it was observed leaves the wait as it is. While the base branch's reading is `진행 중` or `판정 불가` — every new tip passes through them — the wait holds even with no match yet, and the gate refuses the match act (exit 3): the match runs once the reading is red or green again.
- **`master 재합류`** → the base branch fixed a failure the HEAD still has. Issue `act --kind base-check` as before a merge — when the remote tip is missing, the pre-authorized `git fetch` once and the check once more — and branch on its `판정`: `이동` → dispatch the segment's implementation with `베이스 해소: <베이스>` on a line of its own and `부류=master 재합류` beside it, `<베이스>` the check's `베이스` — the snapshot's `master 재합류` element carries it as `베이스`, beside `판정`, both read from the latest `베이스 판정` row; the gate admits it only while `다음` reads `master 재합류` and the latest `베이스 판정` reads `이동`, and the dispatch spends no cycle budget. Once it pushes, `다음` reads `해소 리뷰`. `충돌` → read `다음` again and take the `베이스 해소` branch. `일치` → dispatch nothing; read `다음` again — a HEAD whose last check reads `일치` has nothing to take in, so `다음` no longer reads `master 재합류` and falls back to the value the table gives the failure without the base branch.
- **`master 수리 불가`** → the HEAD waits on a base-branch failure the host could not start a repair run for, and this segment holds the event's representative marker. Stop the segment at site `master 수리 불가` (「Stopping one segment for a person」); the question names the event — the repository, the element's `처음 커밋` and `서명 요약` — and the element's `수리 사유`. The gate writes no recommendation at this site. Other segments waiting on the same event stay at `master 대기`.

**`ci_early[]` sends the one rerun while the review still runs.** `다음` keeps the table's value until a review ends, so a check that failed while the segment's review is live would wait out the whole review. The snapshot's `ci_early[]` names each such segment — a live review stage, a settled round-0 failure on the worktree HEAD, no rerun spent on it — with `세그먼트`, `head sha`, `PR` and `실패 체크`. For an element, issue the same `git fetch` and rerun act as `CI 재실행` above with the element's `head sha`, although a stage is live on the segment: the gate takes the act on that predicate. Do not issue it more than twice for the same head in one shift, and do not name the segment in `CI 대기` for it — the review's end wakes your successor. **An exit 11 on it stops nothing**: write no `shift-halt` and no `park`, and leave the segment to the `CI 재실행` branch after the review ends, which takes the refusal there. Any other exit is read as that branch reads it.

**A declared segment's review carries `--slice <seg>`.** When the segment came from the document's `## 구현 슬라이싱` — its id is a slice id — every `/cc-cmds:review-unattended` dispatch for it, a full or a delta review alike, adds `--slice <seg>` to the prompt, so the review counts other slices' findings apart from this one's. The gate refuses (exit 3) a review dispatch whose `--slice` is not its `--segment`. A segment that is not a slice carries no `--slice`; the recovery dispatch carries none either. **A `cycle` row refused for its other-slice section is answered by one review without `--slice`.** The gate refuses (exit 2) the row of a report that gives a finding to a slice that is not another segment of this run still to land — merged, done, parked, missing, or this segment itself — and (exit 2) one whose other-slice items do not each carry exactly one `    - **배정**: 슬라이스 <id>` line. The reviewer cannot see which slices have landed, so the same dispatch would write the same report again: dispatch the review of that segment once more, the same kind as the refused one, without `--slice`, so every finding counts as this segment's own, and name the refusal in `--rationale`. That second review's row is written as any other; a second refusal of the same kind is the review's failure, not another re-dispatch.
