#### Re-dispatching the implementation after review findings

When a segment's `review_next[]` element reads `다음` `수정`, that review's `stage-result` row is `정상 완료`, and the segment has no live stage, dispatch the implementation again with the review report as its fix target. The values are already in the snapshot's `cycles[]` and `문서 인자`:

```
gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <seg> \
  --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \
  -- implement -p "/cc-cmds:implement-unattended <문서 인자> \"세그먼트 <seg> (사이클 <n>) · 선언 파일: <files> · 수정 대상: <리포트 절대 경로> 의 P0·P1\""
```

**Carry the segment's enforcement-surface values into every implementation prompt.** The snapshot's `segments[]` element of the segment carries `강제 표면` and `좌석 적용 커밋`. Copy each into the prompt right after `· 선언 파일: <files>`, in the gate's spelling, as `· 강제 표면: <값>` and `· 좌석 적용 커밋: <값>` — in this form and in the first implementation a carried answer dispatches with `사이클 1` — and leave out the one whose value reads `없음`. **A carry act (`--carry-answer <line>`) is not such a prompt**: its `-p` is the answer element's `carry_prompt` byte for byte, as 「Handing on a person's answer to a halt」 item 3 says, and you add neither value to it — the gate compares the prompt with its own build of the re-entry frame, which has neither. The re-attached stage reads them to know which declared paths only a seat-apply can commit and which edits a person already approved; do not write either value from memory or from an earlier prompt. **`· 선언 파일: <files>` is the segment's `segments[]` element's `선언 파일`, copied byte for byte** — never a set from memory or from an earlier prompt. The gate compares the two on every fresh implementation dispatch of a segment planned with `--from-declaration` and refuses a phrase that differs, or a prompt without it, with exit 2 naming both values: copy the value again and dispatch once more.

`<n>` is that cycle row's `사이클` and the report path is made absolute as 「Dispatching a review cycle in delta mode」 item 2 says. When the element reads `CI 합류 수정` instead, the same directive carries ` · CI 합류: <head sha> · 실패 체크: <…> · PR: <…>` after `의 P0·P1`, the three values the element's. The gate refuses a prompt whose document argument differs from the snapshot's `문서 인자`. Once the fix ends, the next review is that subsection's to dispatch. The gate refuses (exit 3) a review while no implementation or lead fix followed the last `cycle` row and the segment's worktree HEAD is still that row's `리뷰 HEAD` — the same HEAD is not reviewed twice. **The gate caps the cycles**: it counts the segment's `cycle` rows at every implementation dispatch and refuses with exit 3 once they reach `REIMPL_CYCLE_CAP` (2), unless `다음` reads `재구현`, or reads `확인 리뷰` with a `정상` re-convergence after the last `cycle` row, no lead fix after it and the segment's `implement_next[]` element reading `구현` — the same re-implementation's run after its process A. On that refusal dispatch no implementation and read the segment's `다음` instead: past the cap it is a step of the segment's ladder — `리드 수정`, `확인 리뷰`, `재수렴`, `재구현` — or a value that ends the review loop — 「Branching on `다음` after a review」 routes each. **An exit 3 whose refusal text names 「파견 자리 대조」 is the dispatch-site comparison, on any implementation dispatch** — the first one, the `구현` branch or the re-dispatch after review findings: write a segment `park` row and a `스코프=cone` block with `'사유=구현 재파견 거절'` and the refusal text in `근거`, and dispatch its implementation no more. It is not the cycle cap's exit 3, so do not read `다음` and step onto the ladder. A segment whose `선언 파일` reads `판정불가` is not skipped: dispatch it, and this refusal is how it stops.
