**The evidence a clause row carries depends on its state.**

- **`충족` cites the ledger or an observable artifact** — a row anchor `A-<8 hex>`, a merge commit's full sha, a PR number, a run-directory or document path with its line, or `중단 답 줄 <n> · 첨부 <경로>` — never prose alone. For grounds that cite no execution the gate checks only that `근거` is not empty and, when they name a posted review, that the review's `리뷰 게시` row reads `대조=일치`; the rest of keeping to this is yours. Grounds citing `실행 A-…` are checked by the gate: the row is this clause's `종료 절 실행` row and exited 0, and a `트리밖쓰기` or `외부상태변경` execution is followed by `재조회 A-…` — the same clause, graded `읽기` or `워크트리쓰기`, exit 0, after it, a different command; any miss is exit 3 with no row. A clause that has an execution of this run must cite `실행 A-…` or `중단 답 줄`. The gate adds `자체 근거=예` to a row that passed; never pass it yourself (exit 2).
- **`불가능` cites what decided it** — a residual issue URL, a design step's `stage-result` row and halt record path, or the `중단 답 줄 <n>` of a `불가능으로 정산` answer. An act that passed the gate and then failed cites its ledger row anchor `A-<8 hex>`; an act the gate refused cites the refusal line, the exit code and the target cutpoint. The rules of `references/review-next-1.md` and `references/design-dispatch.md` for their own `불가능` rows stand as they are.
- **`보류` names an open `절단점=판단` approval id**, and one approval holds one clause unless the design step opened it.
- **`이관` carries no grounds from you** — write `act --kind clause -- id=<id> 상태=이관` and nothing else (passing `근거` is exit 2). It settles only a clause whose `근거 시점` is `종단 뒤`: its evidence exists only after the run ends, so the run hands its material over to the morning report. The gate runs the leftover reader `run-leftovers.sh`, keeps its output at `$CC_PIPELINE_RUN_DIR/clause-handover/<id>.md` and writes the grounds itself — `종단 재료 <path> · sha256 <64 hex> · 항목 <n>건 · 판별 <표지|문면 런 보고서에서 읽|문면 아침 보고서에서 읽>`. It refuses with exit 3 a clause that is not such a clause, one already settled `충족`, `불가능` or `이관`, one with an open evidence request, and one whose reader run failed.

**Settle the termination clauses before you propose done.** Enter this order when no unmerged, unparked segment is left to dispatch, no stage is alive, no `shift_halts[]` element holds a segment, and no segment parked by a `스코프=cone` row reading `사유=시각 승인 대기` still has its `시각-승인` approval open in `pending_approvals[]`. While one is open, end with `사유=승인` as item 2 of 「Dispatching the visual stage」 says, and do not propose done. A plan with no implementation step (「Planning the segments」) and a design that stopped follow the same order.

1. Read the snapshot's `clauses[]` — one element per termination clause, with its `id`, `문면`, `상태` (`미정산`, `충족`, `불가능`, `보류` or `이관`), `근거`, `요청` (the evidence request still open on it), `근거 실행` (the execution shape the kickoff bound the clause to, or `null`), `근거 시점` (`"종단 뒤"` when the gate judges the clause's evidence to exist only after the run ends, else `null` — read this key and never judge the wording yourself), `실행` (the last `종료 절 실행` row's `앵커`, `종료 코드` and `축2`, or `null`) and `실행 이력` (every such row in order — take a write's anchor back from here after your context was compacted).
2. For each element whose `상태` is `미정산` and whose `근거 시점` is `"종단 뒤"`, neither look for its evidence nor ask for it: settle it with `act --kind clause -- id=<id> 상태=이관`, and the gate writes the grounds. When that `이관` is refused with exit 3 because the leftover reader failed, do not issue it again in this shift and write no evidence request for the clause (the gate refuses one): end the shift with `사유=중단` and put `이관 판독기 실패 <id> — <거부 줄>` in `막힌 지점`, `<거부 줄>` being the gate's refusal line. When the ledger's last two `handoff` rows both read `사유=중단` and both their `막힌 지점` carry `이관 판독기 실패 <id> — ` for this clause — read them through `gate.sh exec … --surface 읽기` — the reader has failed in two shifts in a row: do not issue `이관` again, and settle it without a question with `act --kind clause -- id=<id> 상태=불가능 '근거=이관 판독기 실패 연속 2교대 — <거부 줄>'`. That `불가능` voids the run's ending, which leaves the clause on the `done` line's `불가능 절` tail and in the morning's leftover list.
3. For each other element whose `상태` is `미정산`, find by gate reads the evidence its `문면` asks for — ledger rows, the run directory, a merge commit's `git show --stat` or `git diff`, `gh pr view`, each through `exec … --surface 읽기` — and when you find it, write `act --kind clause`.
4. For each clause whose evidence you cannot produce, write an evidence request (below) — one per such clause, all in this shift. A clause whose `근거 시점` is `"종단 뒤"` does not come here.
5. Once every clause is settled, check with `plan --kind propose-done` and then take `act --kind propose-done`.
6. While any evidence request is open, do not propose done: end with `사유=중단` and put each record's absolute path in `막힌 지점`.

**A clause that asks for a pull request review is settled by a review the gate posts for you** — do not hand it to a stage, and do not post it yourself. Spell it `gate.sh act … --kind review-post --segment <seg> --clause <절 id> --cutpoint 커밋 --surface 외부상태변경 -- 게시`; the act posts `POST repos/<owner>/<repo>/pulls/<n>/reviews` once.

- **The gate takes every value from the ledger**: the pull request from the segment's branch, `commit_id` from the `리뷰 HEAD` of the segment's last `cycle` row (and the report's `리뷰 HEAD` must match it), the P0 and P1 counts from that row and the finding titles from its `리포트 경로`. The body comes from the run's wording file's `정산 본문` template — the `리뷰 문면` row's file, or the plugin's default — and `event` is `COMMENT` unless the clause's `문면` names `REQUEST_CHANGES` or `APPROVE`. When the segment has no `cycle` row, the act is refused: settle the clause `불가능` saying so.
- **Posting a review any other way is refused in every run**: `exec` refuses a non-GET `gh api` under `repos/<owner>/<repo>/pulls/<n>/reviews` or `…/comments`, `gh pr review` and the GraphQL review mutations with exit 3, a `사전 인가` row notwithstanding.
- **The act reads before it posts**: it checks the posting login, reads the pull request's review list, and when its own earlier attempt left a review on the same `commit_id` it compares that one instead of posting again.
- **The `리뷰 게시` row it writes is the `충족` evidence**: cite it as `리뷰 id=<id>`. The gate takes a `충족` row whose `근거` names a review only when that review's `리뷰 게시` row reads `대조=일치`.
- **On exit 3** the act stops at one of three sites — `리뷰 게시 거절`, `게시 대조` or `보류 리뷰 선점` — and the gate's refusal text says which: stop the segment there with `shift-halt` (「Stopping one segment for a person」). It is not retried in this shift. At `리뷰 게시 거절` the cause is one of those the site table lists — no dedicated write credential and no readable `gh` login on this host, a login other than the frozen account, a 4xx, or an unknown outcome — and the refusal line carried in `관측` names it.

**When a clause's `문면` asks for an execution** — a paid or credentialed call, a local launch, a device, or a person's confirmation — and no ledger row, stage report or answer attachment shows it done, take one of three ways. Do not settle such a clause `불가능` without a question. The `불가능` without a question in item 2 of the order above is a different case: it applies only to a clause whose `근거 시점` is `"종단 뒤"` and whose `이관` the leftover reader failed in two shifts in a row. Posting a pull request review is not such an execution: you issue it yourself through the gate, as above. A clause whose `근거 시점` is `"종단 뒤"` does not come here: it has no execution to run during the run, and the gate refuses its `clause-exec` with exit 3.

1. **Runnable** — the execution is a read the grading table grades `읽기`, or a `사전 인가` row names it whole, and when the element's `근거 실행` is not `null` the command starts with it. Issue `act --kind clause-exec --segment - … -- 절=<id> <argv…>`, where `…` is the `--cutpoint`, `--surface`, `--reach` and `--snapshot-digest` you would give the same argv on `exec`, with the same values. The gate prints the output and one stderr line `[clause-exec] 행 A-<8 hex>`, the row's anchor. When that execution is `트리밖쓰기` or `외부상태변경`, read its result back with a second `clause-exec` of the same clause — graded `읽기` or `워크트리쓰기`, a different command. When every call exited 0 and the output (the re-read's, when there is one) shows the state the `문면` asks for, write `act --kind clause -- id=<id> 상태=충족 '근거=실행 A-…[ · 재조회 A-…]'`.
2. **Ran, and failed or did not match** — ask with `shift-halt -- 절=<id> 실행=A-… 질문=… 관측=…`. The gate writes the `**실행 결과**` line from that row. Do not run it again: the gate refuses a clause execution after a failed one, and the record's `근거 제출` is the person's checked result as an attachment, not a re-run.
3. **Outside the authorization** — ask with `shift-halt -- 절=<id> '명령 초안=<argv>' '기대 결과=<한 줄>' [추천=근거 제출 '추천 근거=…'] 질문=… 관측=…`. Take this way too when `clause-exec` ended without a new `종료 절 실행` row for the clause — a precondition or rule refusal (exit 3) or a reach park: put the argv you issued in `명령 초안` and the gate's exit code and refusal line in `관측`. An approval wait is handled as on `exec`: the clause stays `미정산` until that approval is answered.
