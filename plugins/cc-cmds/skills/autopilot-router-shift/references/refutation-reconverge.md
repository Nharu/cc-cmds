#### Routing a pre-implementation refutation to re-convergence

When an implement stage refutes a residual verification item before implementing (its Step 1.5d), it leaves the design document untouched, appends a `## 회차 <N>` block with `**상태**: 대기` to the re-convergence carrier, writes a halt record, and stops. **A refutation during implementation takes the same route** (its Step 3 mid-implementation failure branch): it flips the item in the document first, then writes the same carrier block and a halt record whose `**스텝**` begins with `Step 3 구현 중 반증`, and stops. Everything below applies to both; where they differ it says so. **That halt is not a park for a person — it is this loop's to route**, to `/cc-cmds:design-reconverge`, whose terminal verdict returns the segment to planning inside this same run. No new run id, manifest or authorization record is needed, whatever the halt record's option text says: the gate records a moved document digest as a `문서 해시` row and refuses nothing on it. Nothing else dispatches this — the fixed-graph driver's re-convergence sits on its escalation ladder, which only a review finding reaches, and a refutation inside an implement stage happens before any review.

**Every read here is a gate call**, one command per call with no pipe after it, under `--surface 읽기` with the segment's `--segment`, and it answers only when its output carries `게이트 통과` — on exactly the terms 「Recovering a review stage that crashed」 states, including the three-retry limit on exit 4 and its `blocked` disposition for a probe that stays unanswered (`사유=재수렴 라우팅 — 판정 읽기가 답하지 않는다 (<exit code>)`). The `blocked` form in this subsection is that subsection's item 3 form, with `사유` changed.

1. **The segment stopped in an implement stage, and nothing is running on it.** Read its last `stage-result` row as the crash arm does (`grep -nF '| 세그먼트=<id> | 스테이지=<id> | 종류=' "$CC_PIPELINE_LEDGER"`, last line). It must read `종류=implement` with `종단 부류=의도된 park` **or `정상 완료`**, and the segment must be in none of `live_stages[]`, `orphan_stages[]` and `waiting_stages[]`. `정상 완료` is admitted because the classifier finds a halt record by one name only — `halt/<segment>#<attempt>.md` — and a stage that named its record differently was measured landing on `정상 완료` with the record on disk. `크래시`, `한도 종료`, `공허한 성공` and `외부 종료` are not this case: both halts are a clean stop by contract.
2. **A Step 1.5d or Step 3 refutation halt record binds to it.** Scan the halt directory by content, not by file name, in one read with no shell glob: `grep -rn -e '^<!-- cc-pipeline-halt v1;' -e '^\*\*스킬\*\*: ' -e '^\*\*스텝\*\*: ' -e '^\*\*분류\*\*: ' -e '^<!-- /cc-pipeline-halt v1 -->' "$CC_PIPELINE_RUN_DIR/halt"`. On a call that carries `게이트 통과`, exit 1 or a missing directory means no record. A record qualifies when its lines read `**스킬**: implement-unattended`, `**분류**: precondition-failed`, a `**스텝**:` value beginning with `Step 1.5d`, with `Step 3 구현 중 반증` or with `Step 3 구현 결함 반증`, and it carries the closing fence. **No other Step 3 halt qualifies** — a lock conflict, an admission refusal or a diff-gate violation is not a refuted item and has no branch to route. **It binds by its header's `stage=` field**: equal to `<segment>#<실행 버전>` of item 1's row, or to `<segment>`. A header whose `stage=` is the skill's own name binds only when **exactly one** segment satisfies item 1 in this snapshot and no `blocked` row already names that record as `근거`; with zero or several candidates write the `blocked` form with `사유=재수렴 라우팅 — 중단 기록 <path> 를 세그먼트에 묶을 수 없다 (<k>개 후보)` and dispatch nothing. **When the record and the row disagree, the record wins** — the contract's read priority is "a halt record present ⇒ halt" — and the dispatch's `--rationale` says so: `row 종단 부류=<class>; halt record <path> bound by <stage=… | single candidate>`.

   **The branch is the gate's, read from the snapshot's `refutation_next[]`.** It holds one element per segment such a record binds to, keys in the order `세그먼트`, `기록`, `항목`, `다음`, `사유`, `앞선 커밋`, and the gate builds it by this same binding rule and decides `다음` with its decision function over the record and the design document. Read the element; never decide the branch from the record's prose and never bind the record again yourself. A segment with no element has no refutation to route. Every row the branches below write names the record's path in `근거`, and that is what keeps the element from coming back in the next shift:
   - **`재수렴`** → items 3 to 6 below.
   - **`파킹`** → the design decided that this refutation ends without a new measurement. When `앞선 커밋` is `0` the branch has nothing to show: push nothing, open nothing, and say `앞선 커밋 없음 — push·PR 생략` in `근거`. Otherwise push the segment branch when the cutpoint reaches a push (`--cutpoint push --reach 협업`), and when it reaches a pull request and none is open on the branch, open one whose title is `반증 파킹 — R<n>` (or the element's `사유` when it names another reason, `구현 결함 수정 한도` and the like) and whose body states, in this order, the refuted item's id, the expectation and the observation as the record's `**관측 상세**` holds them, and that the design chose to park without measuring again — no document path. A push or a pull request that fails does not hold the park back; its failure goes into `근거`. Then write the segment's `park` row and a cone `blocked` row: `act --kind blocked -- 스코프=cone 원인=막힘 '사유=<the element's 사유>' '근거=<record path>[ · PR #<n>]' '앵커 세그먼트=<segment>'`. For a parking the design chose, that value already reads `반증 파킹 — R<n>`; for a parking the decision function reached on its own it names that reason (`구현 결함 수정 한도`, `결함 경로가 선언 파일 밖`, `구현 결함 기록 형식 위반`), so the ledger gives one cause on both paths.
   - **`구현 수정`** → the stage's own code made the recipe fail. Dispatch the segment's `implement` stage with its prompt, the tail replaced by ` · 수정 대상: <기록> 의 <항목> 구현 결함` (the element's two values verbatim, no ` 의 P0·P1` piece) and `(사이클 <n>)` the segment's last `cycle` row's cycle, `1` when it has none; write no `cycle` row. The gate lets it in only while the element reads `구현 수정` for that record and item, and spends no cycle budget on it. When the gate refuses it, write the segment's `park` row and a cone `blocked` row with `'사유=구현 수정 재파견 거절'`, the record's path in `근거` and `'앵커 세그먼트=<segment>'`.
   - **`판정 불가`** → write a cone `blocked` row with `'사유=반증 라우팅 — 판정 불가 (<사유>)'`, the record's path in `근거` and `'앵커 세그먼트=<segment>'`, and dispatch nothing.

   A person's answer to such a record comes back through two routes of the gate's halt-answer table, and this subsection carries both out:

   | 경로 id | 갈래 |
   | --- | --- |
   | `구현-수정` | the `구현 수정` branch above, for an answer `구현 수정` to a `Step 3 구현 결함 반증` record |
   | `반증-파킹` | the `파킹` branch above, for an answer `파킹` to a refutation record |

   **The answer reopens the element.** A `blocked` row naming the record closes its element only until a person's answer `구현 수정` or `파킹` stands on it: while that answer is unspent the element is back, carrying `기록`, `항목` and `앞선 커밋`, so read those from it as the branch does. The gate takes such an answer only while the record binds to the segment's last implement attempt and the segment is not terminal, and `구현 수정` only while the decision function still reads that branch, so the dispatch the answer asks for is the one the gate lets in. The two routes differ from the branches above in two ways:
   - **`반증-파킹` follows the person, not the element's `다음`.** Whatever `다음` reads, park the segment as the `파킹` branch does, with `'사유=반증 파킹 — 사람의 답 (<항목>)'` on the `blocked` row and as the pull request's title. The `park` row spends the answer.
   - **A refused dispatch or act hands the answer back; it does not park.** Parking over a person's `구현 수정` would reverse it. Write the routing block of item 8 of 「Handing on a person's answer to a halt」 instead, `사유=중단 답 라우팅 — <기록 파일 이름> — <거절된 동작의 이유>`, so the record is a question to a person again.
3. **An open carrier block names the item, and the item is not spent.** The carrier is `<home main worktree>/docs/design-reconverge/<slug>.md`, where `<slug>` is the design document's repo-relative path with `.md` stripped and every `/` replaced by `-` (the manifest's `## 요소` names the document; `_common/sidecar.md` §1.1 is the rule). Read it with `grep -n -e '^## 회차 ' -e '^\*\*상태\*\*: ' -e '^\*\*대상 항목\*\*: ' -e '^\*\*처리 기록\*\*: ' -e '^<!-- cc-design-reconverge: end -->' <carrier>`. When the record carries a `**대상 항목**` line, take the first block whose `상태` is `대기` and whose `대상 항목` names that line's `R<n>`; a record written before the line existed takes the first block whose `상태` is `대기` and whose `대상 항목` names an `R<n>`. **That `R<n>` must have no block reading `**상태**: 처리됨`** — one item is re-converged at most once per run, and an item refuted again after its re-convergence goes to a person as `blocked` with `사유=재수렴 라우팅 — R<n> 이 재수렴 뒤 다시 반증됐다`. A carrier whose last marker is not the end marker is truncated: `blocked`, `사유=재수렴 라우팅 — 캐리어 잘림`. No such block at all → `blocked`, `사유=재수렴 라우팅 — 반증 중단 기록에 대응하는 대기 블록이 캐리어에 없다`.
4. **Exclusion.** Dispatch no re-convergence while another `reconverge` stage is live, and dispatch no `implement` stage while one is — the document lock detects a second writer, it does not keep one out.
5. **The dispatch reuses the halted segment's row.** Stage kind `reconverge`, the segment's own `--segment`, and the document as its **main-worktree absolute path** — the same value the design arm builds from `## 요소`:

   ```
   gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment <id> \
     --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> \
     --rationale '<R<n>, carrier 회차 <N>, and item 2's binding>' \
     -- reconverge -p "/cc-cmds:design-reconverge <스냅숏 design_doc> R<n>"
   ```

   **The stage runs in the segment's linked worktree, and `docs/` is not there** — it is gitignored, so no linked worktree carries the document or its carrier. That is why the document argument is always the main-worktree absolute path and never a relative one or one resolved against the segment worktree: the skill uses the path as given and derives the carrier from the document's own directory, and the stage's settings already list the main worktree. Write no `segment` row for the re-convergence — a new row owes a terminal state nothing here would drive it to. `/cc-cmds:design-reconverge` has no `-unattended` pair because it is itself the unattended skill; it is the one name this rule admits beside the `-unattended` ones, and the driver dispatches the same name.
6. **After it ends, the segment goes back to planning — or to a person.** A re-convergence dispatched by item 5 of 「Handing on a person's answer to a halt」 is that item's to follow up, not this one's — it has no carrier block, so this item would read its absence as a failed re-convergence. So is a re-convergence row carrying `정산=`: the gate wrote it when item 3 of that subsection settled an answer, with no session, no stream and no carrier block, and the **After it ends** of item 5 there reads it, in a later shift as in the one that settled it. Read the re-convergence's `stage-result` row, then two authored facts: its terminal literal in its own stream (`grep -cF '재수렴을 종료합니다. 판정은 여기까지이며 추가 패스는 없습니다.' "$CC_PIPELINE_RUN_DIR/log/<id>#<실행 버전>.json"`), and item 3's block for that `R<n>` now reading `**상태**: 처리됨` with a `**처리 기록**:` line carrying `판정: 재설계 필요` or `판정: 불필요`.
   - **Both present** → dispatch the segment's `implement` stage again with the prompt it had. The stage starts from its first process on the edited document: after a Step 1.5d halt the segment holds no `plan_sha256` row, and after a Step 3 halt the row it holds predates the `종류=reconverge` row, which the stage's phase resolution reads as void. A further `대기` block for the same document comes first, through item 3 again. **This holds under both verdicts, `재설계 필요` included.** The re-converged segment's own `plan_sha256` rows are what the `종류=reconverge` row voids, so they are never a reason to park it — the next bullet parks other segments and never this one.
   - **`판정: 재설계 필요`** additionally re-plans every **other** unmerged segment whose `implement` rows carry a `plan_sha256`: its plan was derived from the binding surface that just moved, and only the segment the re-convergence ran on has the `종류=reconverge` row that makes its own plan void. **Read which siblings and whether each may go now from the snapshot's `replan_due[]`, never from the stream or a driver function** — the gate writes `재수렴 판정` on the re-convergence's `stage-result` row and derives the key from it. For each element: `state:"가능"` → `act --kind replan --segment <segment> -- 재수렴=<reconverge>`, which voids that sibling's plan so its next implement dispatch plans afresh from process A; `살아 있음` → a stage of the sibling is running, so read the key again after it ends; `상한` → **first look in `answered_judgments[]`: when it holds a `state:"승인"` `사람-결정` element on this sibling, do not raise a question — carry that answer out (**Reading the answer** above) and consume it (**Consuming it**)**, because the gate keeps listing the sibling as `상한` until the answer is consumed, and a fresh question would be asked again in new words, under a new id, spending one of the segment's two; otherwise the sibling has been re-planned twice this run, so raise a `사람-결정` on it (the **CFI-S4 exception** above) whose recommendation is to re-dispatch it on the plan it holds, with the park as the alternative — a `거부` or `무효` is then the park, the person's choice — and give it the decision aid that paragraph names, the keys `추천=` and `선택지 리스크=` under the question-writing convention of `_common/judgment-grade.md` (Emission form), the `거부` and `무효` risks saying the sibling is parked; once that question's `승인` has been consumed (`결정=채택` or `결정=자유 입력 소비`) the gate leaves the sibling out of `replan_due[]` for this re-convergence, so a sibling you do not find there any more has been decided and is not asked about again; `보류` → a `사람-결정` already holds it, so do nothing. **A park is left only for the `사람-결정` cap and for a refusal**: when the gate refuses the third question on the sibling with exit 3 and the warning `a third is not opened`, park it — any other exit 3 on that submission (an answer already spent, a refusal not yet parked, a `답한 승인` the gate rejected) is not the cap and parks nothing — its `park` row and a `blocked` row with `사유=재수렴 라우팅 — 구속면 이동(재설계 필요)으로 계획이 낡았다`. **When the re-convergence's row reads `재수렴 판정=없음` while item 3's `**처리 기록**:` line carries `판정: 재설계 필요`**, the gate could not read the verdict off the stream and `replan_due[]` lists nothing for it, but the binding surface moved all the same: park every **other** unmerged segment whose `implement` rows carry a `plan_sha256` — its `park` row and a `blocked` row with that same `사유` — rather than letting it run its old plan. The gate refuses a re-plan citing that row (clause 4), so a park is the one way left.

     **A row of this `사유` anchored on the re-converged segment itself is a misrouting, and it holds nothing.** It is the one when its `앵커 세그먼트` is the segment whose `종류=reconverge` `stage-result` row is the last such row on an earlier ledger line — no other segment's re-convergence ended in between, so nothing but its own verdict could have parked it. The gate has no verb that closes a cone row anchored on a segment (`원인=해소` resolves run scope and a cone anchored on a run-scope step only) and does not refuse a dispatch for one, so a successor that waits for a resolution row waits forever. Do not wait and do not write another row about it: dispatch that segment's `implement` as the bullet above says, naming the misrouted row's ledger line in `--rationale` (`재수렴 대상 자신의 park 는 오적용 — 줄 <n>`). Parks of other segments stand.
   - **Either missing** — a halt, a crash, no literal, no closed block → `blocked` for the segment with `사유=재수렴 라우팅 — 재수렴 종단 술어 거짓 (<which is absent>)`, and no second re-convergence for the same item.
