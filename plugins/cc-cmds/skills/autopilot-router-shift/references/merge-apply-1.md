#### Merging and applying a segment

**Whatever the review policy, merge a segment only when its snapshot `머지 대기` is empty.** A non-empty `머지 대기` names the predecessors, by `선행` or `머지 순서`, that have not landed yet: do other work, or wait as 「Waiting on a stage」 chooses. A refusal with exit 3 that names such a predecessor and its `상태` means the same — wait — whether the refused act was the merge or another act leaving the worktree whose grade the gate could not read; it is not **Any other cause** below, and nothing is written for it. A predecessor that was parked has already parked this segment through its cone.

**A segment a `머지 입양` row adopted records `act --kind obligation` before it merges, and does not merge when that act is refused.** The obligation is the one its planning act issued, and the passing review that covers the fix fulfils it; record it before the base check, the merge and any apply. The gate refuses a merge or an apply of such a segment while that obligation is open (exit 3). **A refusal that says the obligation is already closed (`this review obligation is already closed`) is not a refusal to merge on**: the segment fulfilled it on an earlier arrival at `머지` and came back after a base resolution, so do not record it again and go on to the base check and the merge — the gate's own refusal above still holds the merge while the obligation is open.

**Below the `머지` cutpoint nothing is merged.** `다음` does not read the target's cutpoint, so a segment whose target stops at `커밋`, `브랜치`, `push` or `PR` reads `머지` or `이월 머지` once its review passes all the same — at `PR` only once the pull request's CI has a verdict, so such a segment goes through `CI 대기` first and ends on `완료` after it. For it, check no base, merge nothing and apply nothing — the gate refuses the merge above the cutpoint, and a `머지됨` for a tip that has not landed. End the segment instead with its `완료` row, carrying the worktree HEAD the review read as its full 40-character sha, and at `PR` the pull request's number as `PR=<n>` as well:

```
gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <id> \
  --cutpoint <token> --surface 읽기 --snapshot-digest <H> \
  -- 상태=완료 커밋=<구현 워크트리 HEAD> 브랜치=<브랜치> 워크트리=<구현 워크트리> 선행=<계획 행의 선행>
```

**Check the base before the merge.** Under `선리뷰후머지`, once `review_next[]` reads `머지` or `이월 머지`, first issue the pre-authorized `gate.sh exec … -- git fetch` against the target, then write the base check — nothing after `--`, every field is the gate's:

```
gate.sh act --manifest <매니페스트> --kind base-check --target <alias> --segment <id> \
  --cutpoint 커밋 --surface 읽기 --snapshot-digest <H> --rationale '베이스 판정 — <id>'
```

The gate asks the remote where the base is (`git ls-remote`, never the local tracking ref), merges the reviewed HEAD with it in an object directory of its own, and writes a `베이스 판정` row: `일치`, `이동` or `충돌`. Read `다음` again. `머지` or `이월 머지` → merge as below. `베이스 해소` or `베이스 해소 한도` → 「Branching on `다음` after a review」. Exit 3 naming a fetch → the base moved after your fetch; fetch once more and check once more, once. Any other exit 3 names why the gate did not judge; read `다음` again, which says what comes first. The same check twice writes one row, so a check that changes nothing costs nothing.

**The merge.** For a segment whose resolved review policy is `선리뷰후머지`, merge once its review has passed — its snapshot `review_next[]` element reads `다음` `머지` (P0 and P1 at zero, or findings a person dismissed at the seat with a `리뷰 기각` row the gate honours only while that cycle stays the segment's last) or `이월 머지` (its open P1 findings were carried over to issues; see 「Branching on `다음` after a review」) — On a run the CI layer stands on (a routed run, or an unrouted run opened on an absent inventory baseline that no fixed-graph driver entered) `다음` carries the segment's CI state too: `머지` and `이월 머지` mean the worktree HEAD's observed checks are not recorded as failed, not still running and not waiting on a rerun's result — on a target whose cutpoint is `PR`, `머지` or `배포` a HEAD with no `checks` row yet reads `CI 대기`, and only a `통과` or round 0's `미등록` five minutes old lets the merge through; below `PR` such a HEAD keeps the table's value — and only on those values do you check the base and merge. A failing check, required or not, reads as one of the fourteen CI values instead (「Branching on `다음` after a review」). **Never send `gh run rerun`, a rerun or re-request REST path, or the `rerequestCheckSuite` mutation** — the gate refuses every spelling of them; a rerun is `act --kind ci-rerun`. A label on a pull request is `act --kind label-ack` and nothing else — the gate refuses every other write of a pull request's labels. The merge is pinned to the implementation worktree's HEAD as its full 40-character sha with the REST merge: `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge -f sha=<구현 워크트리 HEAD> -f merge_method=merge`. The gate refuses any other value (see **Bind a remote merge** below) — not the `리뷰 HEAD` of the last cycle row, which may be recorded abbreviated; the review rule is what checks that the review read that HEAD. A `gh pr merge` without `--admin` is refused as unbound even with `--match-head-commit`, and the branch is not deleted in this argv. When the REST merge is refused with 405 — GitHub's "merge cannot be performed" — the status does not say why, so read the response body's `message` and `gh pr view <n> --json state,headRefOid,mergeCommit,mergeStateStatus` through the gate before writing anything, and branch on the cause:
- **Already merged** (`state` reads `MERGED` and `headRefOid` equals the implementation worktree's HEAD, all 40 characters — an earlier shift's merge whose record did not land, or a person's that merged what the review read): park nothing; go on to the `상태=머지됨` record below with that `mergeCommit`. **`MERGED` with any other `headRefOid`, or a `상태=머지됨` record the gate refuses, is the last bullet's case, not this one**: a commit was added to the pull request after the review, or the merge rewrote the commits into ones the gate cannot match to the worktree's tip. Recording it would put a merge of unreviewed content down as reviewed, and leaving it unrecorded would send the same merge every shift, so take **Any other cause** with `MERGED` and the `headRefOid` (or the refusal) as its `사유`.
- **A required check not finished yet** (the `message` names a required status check as expected or not yet succeeded, and `gh pr checks <n> --required` shows it pending rather than failed): this is not a refusal of the merge and nothing terminal is written. Read the checks once (`gh pr checks <n> --required`, through the gate) and do not watch them inside your turn. Still pending → write no block and no `park`; route other work, and when nothing else is dispatchable end with `대기` carrying `'CI 대기=<id>'` as *Waiting on a stage* describes. The gate wakes your successor when that segment's CI reaches a verdict, and the successor sends the same merge once more when the required checks read green.
- **A failed check, required or not** → read `다음` again and take its branch. Only when it still reads `머지` or `이월 머지` is it the next bullet's case, at site `병합 거절`. An exit 3 merge refusal that names the checks is read the same way: read `다음` again.
- **Any other cause** — a base that requires a merge queue, a missing required review, a conflict: no bound merge passes the gate and that merge goes to a person: instead of ending the shift with a `사유=중단` handoff, stop the segment at site `병합 거절` (「Stopping one segment for a person」), with the 405 and the response body's `message` in `관측`, and go on with the other segments. No shift sends the same merge again until the answer comes back. **A conflict is the base check's first.** A 405 whose `mergeStateStatus` reads `DIRTY` goes back to **Check the base before the merge** once — fetch, `base-check`, read `다음` — and takes this bullet only when `다음` still reads `머지` or `이월 머지` after it. Never merge or rebase the moved base into a branch yourself: only a `베이스 해소` dispatch does that, and what it adds is reviewed before it merges.

Under any other policy pin the same way. Under `선머지후리뷰` the merge comes before the review (**The merge-first loop** below) and the apply follows it as it does under `선리뷰후머지`; under `리뷰없음` issue no apply act afterwards. Either way read `gh pr view <n> --json mergeCommit` and record it:

```
gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <id> \
  --cutpoint <token> --surface 읽기 --snapshot-digest <H> \
  -- 상태=머지됨 PR=<n> '머지 커밋=<M>' 워크트리=<구현 워크트리> 선행=<계획 행의 선행>
```

Every `segment` row this loop writes for the segment, this one and a `park` alike, carries the plan row's `선행` again. The gate does not trust `머지 커밋`; it checks it when the apply act runs.
