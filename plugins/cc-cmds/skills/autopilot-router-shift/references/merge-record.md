### Merging a segment and recording it

**Bind a remote merge to the segment worktree's HEAD.** Spell it as the REST merge `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge -f sha=<워크트리 HEAD> -f merge_method=<merge|squash|rebase>`, with the full 40-character sha of the implementation worktree's HEAD; the branch is not deleted in this argv — the REST merge has no such argument, and deleting a branch is not a merge. It merges at once or is refused (409 when the pull request's head is another commit), so it merges what the rule approved. A `gh pr merge` without `--admin` is not a binding, `--match-head-commit` or not: on a base that requires a merge queue it enables auto-merge while required checks are pending and enters the queue once they have passed, comparing the head only at the request, and since the argv does not say whether the base requires a queue the gate refuses that spelling as unbound on every target. On a base that requires a merge queue the REST merge is refused with 405, so no bound merge passes the gate there: that merge goes to a person through the `park` ending **The merge** above gives a 405. Do not use auto-merge or the merge queue for a segment merge (`gh pr merge --auto`, GraphQL `enablePullRequestAutoMerge`, `enqueuePullRequest`): GitHub compares the head only when the request is made and merges later, so a commit pushed to the segment branch in between is what lands, and the gate reads them as merges with no binding whatever head they name. Under `선리뷰후머지` with `리뷰-후-머지` on, and under `선머지후리뷰` whether the rule is on or not, a merge argv for a segment that has a `segment` row is refused with exit `2` before the rules run when the binding is missing, names another commit, or the worktree HEAD cannot be read; the message names the argument and the HEAD. A merge-first segment is bound because the review obligation its merge issues names the worktree HEAD, and the deferred review reads that commit. The REST path is read with its `?query`, `#fragment` and trailing `/` removed, and `gh api`'s short options are read letter by letter as gh reads them, so `-iXPUT` is a PUT. Flags ahead of `api` (`gh --hostname=github.com api …`) are skipped the way gh skips them to find its command, and an argv whose `api` word may or may not be that command (after `--`, or taken as a flag's value) is read as a merge with no binding. A merge spelling with no binding argument (`…/merges` whatever fields it carries — a `sha` there binds nothing on the server — and `mergeBranch`), a REST merge whose query string carries a `sha` key, a `gh` call inside a `find -exec` whose words carry `{}` (judged at `머지`), a GraphQL body in a file, and one carrying a `#` comment, a `"""` block string, a fragment, a directive, a second field or operation, or its input object passed whole as a variable are refused the same way; spell the merge as the REST merge above, and send any other GraphQL a segment act needs inline with `-f query=`. Any other non-GET GraphQL body is read as a base change with no binding unless every operation is a `query` or calls only mutations that move no ref (comments, reactions, labels, assignees, issues, reviews, pull request state, project items): `updateRefs`, `updateRef`, `createCommitOnBranch` and every mutation the gate does not know are judged at `머지`, refused the same way, and are not on the collaboration surface — push to the segment branch and merge with the REST merge above instead. So are the REST writes that move a branch without a pull request — a non-GET `…/git/refs…`, `…/contents/…` (with or without `branch`; without it the commit goes to the default branch) and `…/merge-upstream` — and the background merge `…/pulls/<n>/merge-async`, which merges or enqueues after the request whatever `sha` it carries. Respell the merge that way and call again. A local `git push` to the base is bound by what it puts there: the gate strips wrappers and git's global options and runs `git push --dry-run --porcelain` with the same arguments where the push runs. A push that updates the base is judged at `머지` whatever you declared (below it is exit `8`; `배포` is judged at `머지`), and every commit it would put on the base must be the worktree HEAD, or it is refused with exit `2` naming the updated ref and the HEAD. This holds for every spelling the dry-run can reproduce — `U:<base>`, `U:heads/<base>`, `git -c … push`, `git -C <dir> push`, `command git push`, `env git push`, `:`, a glob, `--all`, `--mirror`, `--branches`, a configured `remote.<name>.push` — so a local base ref ahead of the reviewed HEAD is refused through all of them. A push it cannot reproduce is refused with exit `2` before the rules run, whatever you declared: on a target with a base branch, a push inside `bash -c`/`sh -c`, `env -S` or under `sudo` (and every such string the gate cannot show runs no push: one that names `git`, carries an expansion, a glob or a group, or whose command word is off the gate's short list of commands that run no text of their own — call the command directly instead), inside a `find -exec` whose words carry `{}`, behind an environment assignment other than `LANG`, `LC_*` or `TZ` (`HOME=` and `XDG_CONFIG_HOME=` included) or an `env` option, with a command-running `-c` key or `--config-env`, or with a push option outside the gate's allow-list (an abbreviation such as `--no-dry` or `--exe=` included). The allow-list passes `-f`, `--force-with-lease`, `--force-if-includes`, `-u`, `-d`, `--all`, `--branches`, `--mirror`, `--tags`, `--follow-tags`, `--prune`, `--atomic`, `--repo`, `-o`, `-4`/`-6`, `--thin`, and drops `-q`, `-v`, `--progress`, `-n`, `--dry-run`, `--porcelain`, `--verify` and their `--no-` forms; `--receive-pack` and `--exec`, in any prefix, are refused as a form on every push. Respell it as `git push <remote> <refspec>` without that wrapper or option. Push `HEAD:<base>` or `<segment branch>:<base>` (a segment's act runs in the segment worktree, so `HEAD` is that tree's HEAD). When the dry-run names no ref, the gate reads the refspecs and treats `:`, a glob, `--all`, `--mirror` and `--branches` as pushes of the local base ref. These checks run at `머지` and above, and first compare the segment's last `segment` and `cycle` rows as the review rule picks them (by substring) with the gate's picks (by field); when a sibling row's text carrying `id=<segment> ` or `세그먼트=<segment> ` makes them differ, the merge is refused with exit `2` naming the series — write one more row of that series for this segment and call again.

**`머지 대조`, `최종 사이클` and `수렴` are written by the gate and never passed by you** — a `segment` row carrying any of them is refused with exit `2`, with an empty value too (`머지 대조=`). `id` is the gate's too — it is carried from `--segment` — so a `segment` row carrying `id=` is refused with exit `2`. A row of any kind whose field key has a space, a CR or a tab before or after it (` 상태=머지됨` on a `segment` row, ` P1=0` or ` 리뷰 HEAD=…` on a `cycle` row) is refused with exit `2` whatever the key is — write every key bare. On a `상태=머지됨` row the gate compares the merge against the segment's last `cycle` row and writes both fields itself — `머지 대조` reads `충족`, `이월` (a carry-over merge on `다음=이월 머지` whose review covers the merged tip), `기각` (a merge of a last cycle a person dismissed at the seat with a `리뷰 기각` row, P0 findings included, whose review covers the merged tip), `메타 해소` (a merge of the renumbering merge the gate proved), `패치 동일` (a merge of a resolution HEAD the gate proved carries the reviewed branch change unchanged by patch-id), `위반(카운트)`, `위반(미포함)`, `위반(카운트·미포함)`, `리뷰 없음`, `판정 불가` or `정책 면제`. The same row is refused with exit `2` when the worktree tip has not landed on the base. A `완료` or `park` row carrying a `커밋` that has already landed is refused with exit `2` too, unless the segment already has a `머지됨` row or the commit landed inside a sibling's `머지됨` row that carries a `커밋`: if you merged, write `상태=머지됨`; if the segment has no commit of its own, drop `커밋`. A `머지됨`, `완료` or `park` row whose `워크트리` differs from the segment's **recorded worktree** is refused with exit `2`. The recorded worktree is the one named by the segment's first non-terminal row, **written before its first `머지됨` row, that names the segment's own worktree** — not the target's main checkout, the top level of its checkout when the directory exists and is inside a repository, and on the segment's branch: the `브랜치` of the first such row carrying one, compared with what each candidate's directory has checked out (a detached HEAD has no branch, so it pins none and matches none; the row's own `브랜치` stands in only when the directory is gone or outside a repository). A non-terminal row that leaves `브랜치` off gets it filled by the gate from the checkout it names; one you pass is kept. No row carrying `브랜치`, or rows naming checkouts of two branches, leaves no record. A row naming the main checkout or a directory inside it, such as the `계획됨` row written before the segment's worktree exists, is not that row, and a non-terminal row written after a `머지됨` row never becomes the record. A tree another segment named earlier is not excluded — a segment inheriting a tree and its branch records that tree. So the segment's rows name the segment's own worktree, or the main checkout before that worktree exists — never a linked worktree on another branch. The gate reads the merged tip there, so a terminal row always carries the segment's own worktree, even after that directory has been removed — never the main checkout, and a later non-terminal row naming another checkout does not move it. When a terminal row is refused for naming a worktree other than the record, name the segment's own tree if that is where it worked; if the record was established on a tree the segment did not work in, do not name another checkout: instead of ending the shift with a `사유=중단` handoff, stop the segment at site `워크트리 기록 없음` (「Stopping one segment for a person」), with the refusal and the recorded worktree in `관측` — a `park` row would name a worktree too and meet the same refusal. A segment with no such row — its first row already terminal, every non-terminal row before its first merge on the main checkout, no row carrying `브랜치`, or rows on two branches — has no recorded worktree: its `머지됨` row is accepted with the tip unread, so under `선리뷰후머지` it reads `판정 불가` (or `리뷰 없음` with no `cycle` row), which condition 11 holds; write a non-terminal row naming the segment's worktree before its terminal row. Once a `머지됨` row is written without a record, no record can be established: do not name another checkout — instead of ending the shift with a `사유=중단` handoff, stop the segment at site `워크트리 기록 없음` (「Stopping one segment for a person」), saying in `관측` that the segment has no recorded worktree (the `머지됨` row already makes the segment terminal). Pick `리뷰 정책` on the first row; a row that loosens it against the previous row's policy — the strict default when the previous row names none or there is no previous row — is refused with exit `2` on a `머지됨` row always, on any other row once the segment carries `머지 대조`, and on any row once the segment has left planning: a loosening is accepted only while every earlier row of the segment reads `상태=계획됨`, the segment has no `cycle` row, and no stage was dispatched for it (no `승인` or `자율 승인` row with `kind=skill` naming the segment, no `stage-result` row of the segment), because after execution starts the gate cannot tell whether the segment's code already reached the base outside it. A planning row that left the policy off is corrected on the `실행중` row. To recover from the refusal, restate the previous row's policy (or omit the field to inherit it). Restating or tightening it is accepted.

**Termination condition 11** holds a segment under `선리뷰후머지` whose last row carrying `머지 대조` reads `위반(…)`, `리뷰 없음` or `판정 불가` — any value other than `충족`, `정책 면제`, `이월`, `기각`, `메타 해소` or `패치 동일`, an empty one included — while `리뷰-후-머지` is not set to `끔`. The violating row stays; the last row carrying `머지 대조` is the answer, and a later row without the field — a `완료` after the merge — does not clear it. The resolution is an appended second `상태=머지됨` row carrying the segment's recorded worktree (its own worktree, never the main checkout), and what goes before it depends on which half failed. A coverage violation (`위반(미포함)`): dispatch a review that covers the merged commit and write its `cycle` row first. Send the line `gate.sh review-line` prints as it is: on a segment a person merged before a review covered it, that line carries `--merged <머지 커밋>`, `--base-sha` and the three `--basis-*` flags of the segment's last full cycle, so add no flag to it and drop none. Write the `cycle` row in the review mode its report records, then the second `머지됨` row. A violation of both halves (`위반(카운트·미포함)`): dispatch the same covering review first and write its `cycle` row and the second `머지됨` row; when that row reads `위반(카운트)`, the count violation below follows, and when the covering review judged the basis findings resolved and it reads `충족`, the segment is done. The trigger of either dispatch is the review dispatch rule's as it stands: a fact token the ledger stands behind, or `라우터 판단` with its reason. When `review-line` refuses with exit 3 — the merge commit is empty, the recorded worktree is gone or its tip unreadable, the merge was a fast-forward (onto the worktree tip or onto commits pushed to the branch past it), or the base cannot be derived — stop the segment at site `종료 조건 11 판독 불가` (「Stopping one segment for a person」), quoting the refusal in `관측`. A count violation (`위반(카운트)`): a person looks at the merged last cycle's findings at the seat and writes its `리뷰 기각` row first, and the second row then reads `기각`. You cannot write a dismissal — it is seat only — so a count violation holds the run under condition 11 until a person answers; do not dispatch another review as its cure. If that checkout has been removed, or the segment has no recorded worktree, the second row records `판정 불가` and condition 11 stays: do not repeat the review and do not name another checkout — instead of ending the shift with a `사유=중단` handoff, stop the segment at site `종료 조건 11 판독 불가` (「Stopping one segment for a person」), naming condition 11 and the unreadable tip in `관측` (the `머지됨` row already makes the segment terminal).

**Termination condition 12** holds a `선머지후리뷰` segment that has a `리뷰 의무` row and whose last row is not `park` until its last `cycle` row covers the `머지 커밋` of its last `리뷰 의무` row and that cycle's review table value is `머지` or `이월 머지` (a person's `리뷰 기각` makes the table read `머지`). A last row of `머지됨` or `완료` does not close it: P0 or P1 findings after the merge keep the run open, and so does a coverage reading of `판정 불가`. `## 룰 설정` does not switch it off. A segment with no `리뷰 의무` row, and one that ends in `park`, is not held. The cure is the deferred review itself — write `상태=사후리뷰`, dispatch the review `review_next[]` names, and when it reads `수정`, implement on the same branch, merge again through a new pull request once the earlier obligation is paid, and review that merge. **A segment a `머지 입양` row adopted is held the same way, whatever its review policy, from the moment it is planned**: its planning act writes its `리뷰 의무` row, so the run stays open until a passing review covers the adopted merge commit — the review that reads `입양 종결`, or the review of the fix that merges after it — and one that ends in `park` leaves condition 12 while condition 9 still holds its open obligation.
