**The apply.** After the `머지됨` row is written, read the snapshot again and look at `적용` on that segment's `segments[]` element. `없음` → the merge is the segment's end — it has no apply command, its cutpoint is below `배포`, or its handover to a person is already recorded — so issue neither the fetch nor the apply act. `미정산` → the segment came in from an earlier run that merged it and never said how its apply ended: never issue `act --kind apply` on it. While it is in the snapshot's `apply_unsettled`, fetch and settle it with `act --kind apply-settle` and no answer, as for any segment in that list — the gate measures it once with the earlier run's ledger as evidence; once it is in `apply_imported`, the gate already measured it or its evidence did not stand, and a person settles it at site `들여온 적용 정산`. `대기` or `인계` → first issue the pre-authorized `gate.sh exec … -- git fetch` once more: the merge happened on the remote, and until a fetch the local clone holds neither M nor an `origin/<베이스>` that contains it. Then:

```
gate.sh act --manifest <매니페스트> --kind apply --target <alias> --segment <id> \
  --cutpoint 배포 --surface 외부상태변경 --snapshot-digest <H> -- 적용
```

The argv is the fixed token `적용`; the gate checks five preconditions it does not let any rule switch off, writes `적용 준비` and returns, and a supervisor it starts runs the frozen apply command and writes the ending — `완료`, or `park` with the gate's own `blocked` row. **An exit 0 whose segment's last row reads `적용 준비` means the apply is running**: read `live_applies` in the snapshot, route the other segments, and when that apply is all there is left to wait for, end with `대기`. Do not write either state for a segment that still has an apply pending: the gate refuses both from `act --kind segment`. An apply act that reaches a segment owing no apply is answered with `적용 불필요` and exit 0, and the gate writes nothing: that too is the segment's end, not a refusal. **A `선머지후리뷰` segment applies after its merge and before its deferred review**: the gate takes the segment's open `리뷰 의무` row in place of a passing cycle and compares its `머지 커밋` with the merge commit's second parent, so issue the apply on its `머지됨` row without waiting for the review, and after a second merge issue it again on the second `머지됨` row. **When the apply act is refused on a precondition**: a missing or stale remote ref (precondition 4) → fetch and issue it once more, and only once. Any other precondition refusal → instead of ending the shift with a `사유=중단` handoff, stop the segment at site `적용 전제 거부` (「Stopping one segment for a person」), with the refused precondition number and the gate's wording in `관측`, and go on with the other segments. No shift walks into the same refusal until the answer comes back. **When the apply itself fails before its command ran**, the supervisor has written the segment's `park 적용=사전 실패` row and an act-scope `blocked` row — on a later snapshot, after an apply act that returned 0, so write no `shift-halt` for it: a `park` segment is terminal and no answer could retry its apply. It is act scope, and the other segments go on. **An exit 11 on an act of a segment** that the segment cannot do without — a push whose remote disagrees, or any other reach the gate refused — stops the segment at site `push원격불일치` or `도달 거부`, never retried by you. **An exit 11 whose standard error holds a line containing `[run][warn] 베이스 이동 — `** is not one of those: the gate has already written the `베이스 이동` stop record and its cone row and stopped the segment, so write no `도달 거부` shift stop for it and route the other segments. Carry that record's `재시도` answer as you carry the other shift stop sites' answers; the segment goes on from the next step it had before it was stopped. **A stage that stopped on that move is re-attached by the same `재시도` answer — its own record is not a second question.** Such a stage wrote a halt record with no option whose `**관측 상세**` names the gate's record as `게이트 기록=<경로>`: name the gate's record, not the stage's, in `막힌 지점`. On every shift while the ledger holds a `중단 답` row with `선택지=재시도` on a `베이스 이동` record — whether or not `answered_halts[]` still lists it, because a target-key latch is lifted at the entry of any act on that target and the answer may be spent before you reach it — find those stage records with a gate read, `grep -rlF -e '/halt/shift/<기록 파일 이름>' "$CC_PIPELINE_RUN_DIR/halt"`, keeping only a `halt/<key>#<실행 버전>.md` whose `**관측 상세**` line carries `게이트 기록=` naming that file (never a file under `halt/shift/` or an `.answer.md`). Re-attach one when its key is in none of `live_stages[]`, `orphan_stages[]` and `waiting_stages[]`, the key's last `stage-result` row — passing over rows that end `크래시`, `한도 종료` or `외부 종료` — is of the same `실행 버전`, reads `종단 부류=의도된 park` and stands before that `재시도` row, and no `중단 답` row names the stage record as `중단 기록`: issue the `--resume` form item 3 of 「Handing on a person's answer to a halt」 shows — a third case it serves — with that row's `세션 id`, the attempt's stage kind, target and `--segment`, `--rationale '중단 답 줄 <line>'` with `<line>` the `재시도` row's line, and as `-p` this sentence with only `<스테이지 기록>` and `<record>` filled in: `중단 기록 <스테이지 기록> 이 가리키는 게이트 기록 <record> 에 \`재시도\` 답이 달렸고, 게이트가 베이스 이동 걸쇠를 풉니다. 선택지 없는 기록에 대한 고정 답 \`원인 해소 후 재개\` 입니다. 기록이 적은 스텝을 그 시작부터 다시 돌려 전제를 다시 재고, 원인이 남아 있으면 이번 시도의 경로에 새 중단 기록을 쓰세요. 중단 전에 끝낸 그 앞의 스텝은 다시 하지 마세요.` That act's entry lifts the latch and spends the answer with its `원인=해소` row; a refused act, or a stream that shows no session start, goes to item 8 of that subsection. Only when no such stage is found, read the segment's `다음` again and take its branch. A dispatch's `11` that left the segment's key a last row carrying `차단=파견 전` stops nothing: it is a size block, not a reach the gate refused, and the gate refuses `도달 거부` on it.

**A target whose applies are stopped.** Before the fetch of the apply paragraph above, look the segment up in the snapshot's `apply_target_stopped`. A `대기` segment it lists → the target's applies are stopped on an earlier segment's target defect: issue neither the fetch nor the apply act and write no `shift-halt` — the apply act would only write the act-scope `대상 적용 정지 <별칭>` row and return 0 — and go on with the other segments; the segment leaves that list when the stopping segment settles `완료` or a person answers it `세그먼트 park`, and is applied then.

**Settling an apply that did not say how it ended.** When the supervisor cannot tell how far the command got, it writes `park 적용=불명` and a run-scope `blocked 사유=적용 불명 <id>` row — except on a target defect (the command exited 0 and the post probe still reads `필요`) of a target whose `폭발 반경` is not `런` and on which no other repository's segment waits: then the `park` row carries `고칠 곳=대상 레포` and no run-scope row is written, only that target's later applies stop, and a settlement that measures `필요` again opens no run-scope row either; when it was cut off, the last row stays `적용 준비` with no supervisor alive. Either way the segment appears in the snapshot's `apply_unsettled`, and that run-scope row is **not** a reason for a `사유=중단` handoff. For each such segment issue the pre-authorized `gate.sh exec … -- git fetch` first — the settlement reads M and `origin/<베이스>` from the local clone as the apply does, and a stale clone parks it as `측정 실패` — then:

```
gate.sh act --manifest <매니페스트> --kind apply-settle --target <alias> --segment <id> \
  --cutpoint 배포 --surface 외부상태변경 --snapshot-digest <H> -- 정산
```

The argv is the fixed token `정산`. The gate pins a fresh worktree at M, runs the frozen probe once, and writes `완료 적용=정산` when the probe says the apply is in, releasing the block and removing the apply worktrees. Exit 3 is a refusal that writes nothing — a supervisor still alive or just launched, or a segment that is not at a settlement entry — so route the others and read the snapshot again later. When the settlement ends in `park … 정산 판정=필요|측정 실패`, stop the segment at site `적용 정산` (「Stopping one segment for a person」); the gate measures the same park again only after that site's `재시도` answer. **An imported segment** — `머지됨 적용=미정산`, brought in from an earlier run — is settled the same way while it is in `apply_unsettled`: fetch, then the same act with no answer; the gate reads the ledger of the run that did the work as evidence and measures once. When that settlement ends with the park exit code, read it neither as an exit 11 the segment cannot go on without (`push원격불일치`, `도달 거부`) nor as the `적용 정산` site: the gate wrote a `들여온 정산` row and left the segment row as it was, so a stop at `적용 정산` is one the snapshot drops. Read the snapshot again — a segment now in `apply_imported` is stopped at `들여온 적용 정산`, and one still in `apply_unsettled` (no verdict row was written) is read as `도달 거부` under the rule that applies now. Its exit 3 — an earlier run still alive, or a verdict already recorded — raises no stop: route the other segments, and a later shift opens it again as the snapshot says. **A segment in `apply_imported`** — one the gate already measured or whose evidence did not stand, with no `재시도` answer since — is stopped at site `들여온 적용 정산` at once, and a person's answer is carried out as 「Handing on a person's answer to a halt」 item 6 says.

**The merge-first loop.** A segment whose resolved review policy is `선머지후리뷰` and whose cutpoint is `머지` or `배포` merges first and is reviewed after, and the review it defers is recorded as a `리뷰 의무` row the merge issues. Its loop, in order:

1. `implement_next[]` reads `선머지`, or on a run the CI layer stands on one of the CI values its CI layer puts in that place (`CI 대기` and the rest) → first bring the branch to an open pull request, whatever the value: take 「Pushing and opening a pull request」 on `원격 단계` — push on `push 필요`, open the pull request on `PR 필요`, read the remote again after each — until it reads `PR 있음`, which on this segment means go on here, not dispatch a review. The CI layer reads the checks of that pull request, the poller reads only an open one, and no stage opens it — the implementation and the lead fix commit and push only — so a `CI 대기` on a segment with no open pull request waits on checks nothing will start. Once `원격 단계` reads `PR 있음`, route a CI value as 「Branching on `다음` after a review」 routes it, and on `선머지` itself fetch and `act --kind base-check` as **Check the base before the merge** says; the gate judges the worktree HEAD, since no review HEAD exists yet.
2. Merge with the REST merge bound to the worktree HEAD, as **The merge** above spells it — the binding is checked under `선머지후리뷰` as under `선리뷰후머지`. Record `상태=머지됨` with `PR` and `머지 커밋`, then take **The apply** below when `적용` reads `대기` or `인계`.
3. Write `상태=사후리뷰` (with `워크트리` and the plan row's `선행`) once the merge and any apply are recorded. The gate takes the row only on a `선머지후리뷰` segment that has a `머지됨` row and a `리뷰 의무` row; it reopens the segment, so condition 1 keeps the run open until the deferred review settles. `review_next[]` reads `사후리뷰` while no `cycle` row follows the last `머지됨` row; when the segment's last row still reads `머지됨`, write the `사후리뷰` row first.
4. On `사후리뷰` dispatch the review from `gate.sh review-line` unchanged: it carries `--base-sha <분기점>` — the fork point the segment's first merge recorded on its `리뷰 의무` row, since this path writes no `베이스 sha` — and `--post-merge <커밋>`, and the review re-runs the design's checks on that commit. The commit is the merge commit, or the worktree tip when the branch carries commits past the merged tip (a lead fix not merged yet). After a merge that follows the last `cycle` row, the gate dispatches this review even on the HEAD that cycle already read. Record its `cycle` row, then `act --kind obligation` against the obligation the merge issued.
5. Read `review_next[]` again and take the table's value. `머지` or `이월 머지` → do not merge again: the segment is done, so write `상태=완료` (the gate refuses it while an apply is still owed). `선머지`, or on a run the CI layer stands on a CI value in its place → a lead fix added commits after the merged tip; go back to step 1, which opens the new pull request before any CI wait. `수정` → dispatch the re-implementation as 「Re-dispatching the implementation after review findings」 says; once it ends, `implement_next[]` reads `선머지` again.

**A merged pull request takes no new commit.** When the branch of a merged pull request gains commits — a re-implementation or a lead fix after the post-merge review — push them to the same branch, open a new pull request from it, and carry the new number as `PR=<n>` on the segment's next row; the second merge is bound and recorded as the first was. The gate refuses it while the earlier `리뷰 의무` is still unfulfilled, so record the post-merge review's obligation act first; the second merge then issues a new `리뷰 의무` row of its own.
