# autopilot — lead copy of the router loop (no runtime reader; the shift runs `autopilot-router-shift`)


The router decides **what happens next**. The gate decides **whether it may**. This act is the half that judges.

### The loop, and its only input

```
snapshot  →  decide  →  gate call  →  (repeat)
```

1. **Read the snapshot.** `bash <plugin root>/orchestrator/gate.sh snapshot --manifest <매니페스트>` — one JSON object. Add `--render` for the human table when reporting to the terminal; that table carries the run's liveness — live stages, how long ago the ledger grew, the watcher's last heartbeat, and whether the run has terminated — so "is this still going?" is one command rather than a pid comparison. It also carries what is HOLDING the run: a `대기 승인` count that stays on the table at zero rather than vanishing, so "no approvals" and "no line" remain different readings, and a `미충족 조건` line naming the termination conditions by number and saying so when the only thing left is an invalidation. **This is the router's entire declared input, with one derived exception.** The emitted digest — the `[gate-digest]` stderr line an acting call ends with, and the file it writes beside it — is a value the gate wrote from the state this same snapshot describes — it carries no decision and no obligation, only the `H` a caller would otherwise re-read, so taking it is a shortcut through the round trip rather than a second source of truth. Everything that is not that number comes from the snapshot, or from a gate-routed read of the ledger or the run directory that this skill prescribes in the form it prescribes (`gate.sh exec … --surface 읽기`) — 「Re-attaching a cut stage」 decides on such reads. A read the router composes for itself is not input. Do not carry a decision across turns, do not remember an obligation the snapshot does not show, and do not treat a previous turn's plan as binding.
2. **Decide one next act.**
3. **Call the gate with that decision as argv.** The decision is not a document the router writes; **it is the argv**, and the gate's argument parser is the schema check. That is also what makes the router testable without a model in the loop: drive the verbs with bad argv against a fixture ledger and assert the exit code.
4. **Read the exit code and go back to 1.**

**The keys of that object are the contract, and the render table is not a substitute for them.** The router is told to read the JSON every turn and is judged on doing so, so a key that exists in the output and nowhere in this document is a key the router has no reason to trust or even to look for. Everything the object carries:

| Key | What it carries |
| --- | --- |

| `targets[]` | `alias`, `slug`, `cutpoint`, `home` — one object per target |

| `pending_approvals[]`, `pending_approvals_total` | `id`, `blocks`, `cutpoint`, `class`, `disposition`, `question` — what the run is stopped on and what answering it releases. `class` is the judgment approval's `판단 부류`, `-` on an act or boundary approval and on one issued without a class; `사람-결정` marks the question only a person answers and `시각-승인` the question a visual sidecar's approval answers — the held classes, each of which holds its `blocks` segment and counts against termination condition 2. `disposition` is `-` until a person answers with free input, then `자유 입력` (or `슬롯 부재`): the approval is still open but has been answered and no disposition could be derived, which is not the same state as unanswered. A run of `무기록` rows never pushes a real handoff out of this window. This is where a successor learns what its predecessor already tried and dropped, and `기록 시각` says when that was observed. | `waiting_stages[]` | one object per stage that was dispatched while every account in its group was exhausted and is **waiting for an account before it spawns** — its supervisor (or the driver) asks the router again every half of the effective `STALL`, writes a `stage-wait` row each time, and spawns the stage on the first grant. A key here is **in flight exactly as a `live_stages[]` key is**: never dispatch it again (the gate refuses that with 17), and wait on it as on a live stage. A waiter whose refresh has stopped while its holder process lives stays here and is never re-dispatched; the recovery is to end that holder process, after which the next gate call settles its attempt and the key can be dispatched again |
| `ledger_damage`, `chain_intact` | the ledger's integrity, as a count and as a boolean |
| `H` | the snapshot digest to copy into the next acting call's `--snapshot-digest`. An acting call that carried `--emit-digest` has already printed this same value as its last stderr line and written it to that file, so the line is the ordinary way to obtain it, the file the next, and calling `snapshot` again the fallback |

**THE LOOP DOES NOT STOP TO ASK.** The person was present exactly once, in Act 1, and everything the run may do without them was frozen there. Inside this loop there is **one** place a question belongs — exit 5, where the gate has issued an approval and the run genuinely cannot answer itself. Everywhere else the router decides, records the decision, and continues.

That includes the moments that feel like natural checkpoints: a stage just finished, a review came back with findings, the next step is large or expensive, the previous act failed. None of those is a question. **A router that asks at one of them stops the run**, and the stop is invisible — the ledger is well-formed, the last row is a normal one, nothing refused anything. It is not even distinguishable from a run waiting on an approval, because *that* state leaves a `승인` row and this one leaves nothing at all. Unattended, nobody answers and the night is spent.

**Where a decision is genuinely yours to make rather than to act on, the answer is the judgment grades below — not a question.** Grade 0 you take, grade 1 you take and record, grade 2 you escalate, and escalation means issuing an approval through the gate so the stop is a row rather than a silence.

**Every acting call carries `--snapshot-digest <H>`, and every acting call carries `--emit-digest` so the next one does not have to go looking for it.** The gate computes that value after its own last ledger row, prints it as the call's last stderr line `[gate-digest] H=<H> actor=<actor>` and writes it to the file, so its `H` is the value the *next* acting call needs. Take it from that line in the immediately preceding response's tool result when that response made exactly one `--emit-digest` call; otherwise read the file and check its `actor`; only then call `snapshot` again. **Fall back to `snapshot` wherever the emitted value is not yours to use** — the line is absent and the file is absent (the first acting call of a run, or an emission that failed), its `actor` is not you, it is stale by construction (anything happened after it was written, a dry run included), or the gate refused the flag with exit 2 as an unknown argument (the hook receives the gate as a runtime parameter, so the two copies can be different deployments). In that last case drop the flag and keep using `snapshot`. The list is open on purpose. What does **not** change is the binding: the digest is still compared against live state, and it is still the one just observed rather than one held across a turn. This is the mechanical enforcement of conversational statelessness, and its scope is bounded rather than total: a remembered digest is refused with exit 4 **when the run has since made progress, or when the ledger has grown past the bounded ancestry window** — not merely because rows landed after it. A value a few rows old belongs to a concurrent writer and is admitted on purpose, so one actor's act does not invalidate every other actor's digest. A digest carried across a compaction is far outside that window in practice, so the enforcement still stands where it was aimed; it is not a guarantee about *any* remembered value. Re-read; never re-type from memory.

### Turn economy — what a routing turn costs, and the four rules that cut it

A shift's cost grows with the square of its length, so the cheapest thing a router can do is finish the same work in fewer responses. The waste is not in what the calls do: most responses carry exactly one tool call. The four rules below are the whole of the intervention; they are also stated in `_common/agent-team-protocol.md` because a team seat spends turns the same way.

- **Issue independent calls in one response.** Two calls are independent when neither's arguments depend on the other's result. Split a response at a real dependency and nowhere else — not at a topic change, not to narrate between them, and not because a snapshot "feels stale" when nothing has happened since it was read.
- **Reuse one `--snapshot-digest` across up to three READ `exec` calls in the same response.** Most snapshot round trips between reads re-read a number that has not moved. **Three** is the bound because the ancestry window is eight rows (`GATE_ANCESTRY_WINDOW=8`) and the shared value has to stay inside it. The cap is on **reads only** — an acting call carries `--emit-digest` and the next one takes its `[gate-digest]` line, else the emitted file, else `snapshot`, as the paragraph above requires. A digest that went stale is refused with exit 4 and costs one extra ledger row; that is the designed failure, not a reason to re-snapshot before every read.
- **Pass absolute paths; never prefix a command with `cd`.** `grep`, `sed`, `ls` and `python3` all take a path argument, so `cd X && …` buys nothing and costs a shell. It costs more than a shell here: the working directory is not part of the act's record, so the morning report holds a command a reader cannot re-run.
- **Never wrap a command in `bash -c` to batch it.** The gate grades an act by the basename of its argv0, so the wrapper launders the grade — a network act is recorded as a worktree write, and the 도달 audit of Act 3 reads a run that never left the machine. Batching means several calls in one response and never several commands inside one call.

**Narrow the snapshot with `--fields` rather than by reading less of it.** `snapshot --fields <selector>` is schema-driven and the selector owns the comma; the steady-state list is `H,disposition,unmet_conditions_total,pending_approvals_total,live_stages,waiting_stages,shift,pace`. Use the full object whenever a decision needs a key outside that list — the point is to stop paying for the whole object on turns that only need the digest and the liveness, not to route on a narrower input than the decision requires.

### The verbs

| Verb | What it does |
| --- | --- |
| `snapshot` | emit the whole input as one JSON object |
| `grade` | dry run — what are this argv's two grades? changes nothing |
| `plan` | dry run — would this act pass, and if not which rule refuses it. Every read-only axis the same argv would meet as an `act` is evaluated, including the enforcement surface, the termination conditions, the segment-row existence check and the predecessor-landing check; the axes a dry run cannot reach are named on stderr rather than passed over silently |
| `act` | check, record, perform a pipeline act |
| `exec` | check, record, perform one bash line |
| `wait` | block until a dispatched stage terminates; writes no row, evaluates no boundary and takes no `--snapshot-digest`. Its exit status is the stage's own rc, 11–14 below, or 15 when the waiting shift is already at the hard limit |
| `close` | resolve a pending approval from the harness-written transcript (`--void` records that it should not have been asked, `--reject` that it was asked and the answer is no — on a judgment approval a flag may only agree with the label the person chose) |
| `prompt` | the canonical question and the gate's menu for one pending approval, as JSON — what you carry verbatim into `AskUserQuestion`; changes nothing |

**Several `act` kinds take FIELDS after `--` rather than a command**, because what they perform is the ledger row itself. **Write them; they are not bookkeeping.** The merge rule reads a `cycle` row, and termination condition 1 counts `segment` rows — a run that never writes either cannot merge anything and cannot propose that it is done, and both failures look exactly like the mechanism working.

```
act --kind segment    -- 상태=<…> 워크트리=<path> 선행=<세그먼트 id CSV>|없음 '선언 파일 집합=<CSV>' [브랜치=<세그먼트 브랜치>] ['리뷰 정책=<선리뷰후머지|선머지후리뷰|리뷰없음>']
act --kind cycle      -- 사이클=<n> P0=<n> P1=<n> '리뷰 HEAD=<sha>' '리포트 경로=<path>' ['모드=전체|델타'] ['기준 사이클=<n>']
act --kind problem    -- 동일성=<…> '현재 단=<n>' '생성 등급=<축2 토큰>'
act --kind judgment   -- 등급=1 '판단 부류=<열세 값>' 기준=<…> '되돌리는 법=<명령>' 근거=<…>
act --kind clause     -- id=<절 id> 상태=<충족|불가능|보류> 근거=<…>
act --kind blocked    -- 스코프=run  원인=해소 사유=<선행 막힘의 사유> 근거=<…>
act --kind blocked    -- 스코프=cone 원인=막힘 사유=<…> 근거=<…> '앵커 세그먼트=<id>' ['의존 세그먼트=<CSV>']
act --kind obligation -- '의무 id=<RO-…>' 근거=<…>
act --kind obligation-done -- 동일성=<problem 행의 동일성> 근거=<원장에서 찾을 수 있는 객체를 지목>
act --kind obligation-drop -- 동일성=<problem 행의 동일성> 근거=<원장에서 찾을 수 있는 객체를 지목>
```

**`obligation` and the two `obligation-*` kinds are different series and are not interchangeable.** `obligation` fulfils a deferred REVIEW obligation and takes an `RO-` id. The other two dispose of an obligation a `problem` row opened, and they are what makes condition 3 satisfiable.

**`종결` says the work was done; `포기` says this run will not do it.** They are checked at different times because they make claims in different tenses. `종결` cites a past act, and the past cannot be rewritten, so it is never revisited. `포기` requires the segment to be terminal, and segment state is reversible — so it is **re-verified every time the open set is computed**, and moving that segment back out of a terminal state re-opens the obligation. Do not use `포기` to make a number go down; it will come back.

**The rationale must name an object the gate can find in this ledger, and prose alone is refused (exit 2).** The recognised forms are a row anchor `A-<8 hex>` — the leading eight of the `prev=` every row already carries, so any row is addressable — an approval id `J-<8 hex>`, a review-obligation id `RO-<8 hex>`, or a segment id. Each resolves to the row that **declares** the object — the row whose own trailing `prev=` begins with the anchor, the approval's first `승인 id=` row, the review obligation's first `의무 id=` row, the segment's `segment` row — never to a later row that merely mentions it, so quoting an old id in a `근거` does not make it new. Two further floors: the object must sit **after** the problem row in the ledger (exit 3), which blocks closing a fresh obligation with something that predates it; and **one object closes one obligation** (exit 3), compared by the row the anchor resolves to rather than by its spelling. A closing act's own rows are rows like any other, so one close can supply the anchor for the next; that chain is not refused, and it is visible in `done-obligations`, where each closing row's anchor sits beside it.

**What the gate does NOT check is whether that act actually discharged the obligation.** It cannot, and it does not pretend to. That residual is carried to the morning by `<RUN_DIR>/done-obligations`, which names every disposed obligation with its disposition and its anchor — including the ones disposed by **exemption**, which write no row at all.

**Write `선행` on the `segment` row at PLANNING time, not later.** It is the cone's declared axis, and it is the only axis that sees a dependency *before* the predecessor merges — segments branch from the resolved base rather than from each other, so ancestry only says "that one already landed", and the moment a cone typically stands up is before that. Two floors follow from that and both are refusals at write time: the field is **monotone** (a later row may add and may not remove), and **absence is not `없음`** (in a repository with two or more segments, a row without the field is refused; `없음` is accepted as a positive statement of independence). `선언 파일 집합` is likewise carried at planning time — it is the sole input to "did this segment touch a file outside its declaration", which git cannot answer at all.

**Put `리뷰 정책` on the segment's FIRST row when the slice declared one.** The gate carries the value forward from row to row, and carrying forward can only propagate a value some first row actually wrote — a template that never writes one leaves every later resolution falling to the strict default, and the policy the slice declared reaches nothing. Omitting the field on a **later** row is inheritance and not a reset. A value exceeding that target's `리뷰 정책 상한` is refused with **exit 2** and is never quietly tightened to fit.

**`머지 대조`, `최종 사이클` and `수렴` are the gate's fields, never yours.** A `segment` row carrying any of them is refused with exit 2 in every state, with an empty value too (`머지 대조=`). `id` is the gate's too — it is carried from `--segment` — so a `segment` row carrying `id=` is refused with exit 2. A row of any kind whose field key has a space, a CR or a tab before or after it (` 상태=머지됨` on a `segment` row, ` P1=0` or ` 리뷰 HEAD=…` on a `cycle` row) is refused with exit 2 whatever the key is — write every key bare. On a `상태=머지됨` row the gate compares the merge against that segment's last `cycle` row and writes `머지 대조` (`충족` · `이월` · `기각` · `위반(카운트)` · `위반(미포함)` · `위반(카운트·미포함)` · `리뷰 없음` · `판정 불가` · `정책 면제`) and `최종 사이클` (the cycle number it read, or `없음`) itself — whatever `## 룰 설정` says, because this is an observation of what merged. Two more refusals, both exit 2, both on the row being written: a `머지됨` row whose worktree tip has **not** landed on the base, and a `완료` or `park` row carrying a `커밋` that **has** landed — unless this segment already has a `머지됨` row or the commit landed inside a sibling's `머지됨` row that carries a `커밋`. If you merged, write `상태=머지됨`; if the segment has no commit of its own, drop `커밋`. A `머지됨`, `완료` or `park` row whose `워크트리` differs from the segment's **recorded worktree** is refused with exit 2 as well. The recorded worktree is the one named by the segment's first non-terminal row, **written before its first `머지됨` row, that names the segment's own worktree** — not the target's main checkout, the top level of its checkout when the directory exists and is inside a repository, and **on the segment's branch**. The segment's branch is the `브랜치` of the first such row that carries one; a candidate's branch is what its directory has checked out — unknown when the HEAD is detached, so a detached checkout pins no branch and matches none — or the row's own `브랜치` when the directory is gone or outside a repository. When a non-terminal row naming a checkout leaves `브랜치` off, the gate fills it from that checkout's current branch, and a `브랜치` you pass is kept as written — so pass the segment's branch when you know it. **No row carrying `브랜치`, or rows naming checkouts of two different branches, leaves the segment with no record** (a re-fork onto a new branch lands here too). A row naming the main checkout or a directory inside it, such as the `계획됨` row you write before the segment's worktree exists, is not that row and never becomes the record, and a non-terminal row written after a `머지됨` row never becomes the record either. A tree another segment named earlier is not excluded: a follow-up or fix segment that inherits a tree and its branch records that tree. So the segment's rows name the segment's own worktree, or the main checkout before that worktree exists — never a linked worktree on another branch. The gate reads the merged tip in the recorded worktree, so a terminal row always carries the segment's own worktree, even after that directory has been removed — never the main checkout, and a later non-terminal row naming another checkout does not move it. When a terminal row is refused for naming a worktree other than the record, name the segment's own tree if that is where it worked; if the record was established on a tree the segment did not work in, do not name another checkout: write a `스코프=cone` block whose `사유` names the refusal and the recorded worktree, and end the shift with a `사유=중단` handoff — a `park` row would name a worktree too and meet the same refusal. A segment with no such row — its first row already terminal, every non-terminal row before its first merge on the main checkout, no row carrying `브랜치`, or rows on two branches — has no recorded worktree: its `머지됨` row is accepted with the tip unread, so under `선리뷰후머지` it reads `판정 불가` (or `리뷰 없음` with no `cycle` row), which condition 11 holds. To avoid that, write a non-terminal row naming the segment's worktree before its terminal row; once a `머지됨` row is written without a record, no record can be established, so do not name another checkout: write a `스코프=cone` block whose `사유` says the segment has no recorded worktree, and end the shift with a `사유=중단` handoff (the `머지됨` row already makes the segment terminal). Pick `리뷰 정책` on the first row; a row that loosens it (to `선머지후리뷰` or `리뷰없음`) against the previous row's policy — the strict default when the previous row names none or there is no previous row — is refused with exit 2 on a `머지됨` row always — that merge happened under the previous policy, and condition 11 reads it — on any other row once the segment carries `머지 대조`, and on any row once the segment has left planning: **a loosening is accepted only while every earlier row of the segment reads `상태=계획됨`, the segment has no `cycle` row, and no stage has been dispatched for it** — a `승인` or `자율 승인` row with `kind=skill` naming the segment, or a `stage-result` row of the segment, ends planning as surely as an `실행중` row does. After execution starts the gate cannot tell whether the segment's code already reached the base outside it. If the planning row left the policy off while the slice declared a looser one, correct it on the `실행중` row. To recover from the refusal, restate the previous row's policy (or omit the field to inherit it). Restating it or tightening it is accepted. A `segment` row over the row cap is refused with exit 1 naming the longest field you passed; the gate's own fields are never trimmed to make room.

**Termination condition 11 holds a segment under `선리뷰후머지` whose last row carrying `머지 대조` reads `위반(…)`, `리뷰 없음` or `판정 불가`.** Any value other than `충족`, `정책 면제`, `이월` or `기각` holds it, an empty one included. A carry-over merge — the last cycle's open P1 findings carried over to issues with a `리뷰 이월` row, then merged on `다음=이월 머지` — records `이월` when the review covers the merged tip, and is not held. A merge of a last cycle a person dismissed at the seat with a `리뷰 기각` row — P0 findings included — records `기각` when the review covers the merged tip, and is not held either. It is on while `리뷰-후-머지` is not set to `끔`. The violating row stays where it is — the ledger is append-only — and the LAST row carrying `머지 대조` is the answer; a later row without the field, such as a `완료` written after the merge, does not clear it. The resolution is an appended second `상태=머지됨` row carrying the segment's recorded worktree (its own worktree, never the main checkout), whose comparison the gate derives again — what goes before it depends on which half failed. A coverage violation (`위반(미포함)`): dispatch a review that covers the merged commit, write its `cycle` row, then the second row. A count violation (`위반(카운트)`): a person looks at the merged last cycle's findings at the seat and writes its `리뷰 기각` row, then the second row reads `기각`. You cannot write a dismissal — it is seat only — so a count violation holds the run under condition 11 until a person answers; do not dispatch another review as its cure. If that checkout has been removed, or the segment has no recorded worktree, the second row cannot read the merged tip and records `판정 불가`, so condition 11 stays: do not repeat the review and do not name another checkout — write a `스코프=cone` block whose `사유` names condition 11 and the unreadable tip, and end the shift with a `사유=중단` handoff (the `머지됨` row already makes the segment terminal).

**Bind a remote merge to the segment worktree's HEAD.** Spell it as the REST merge `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge -f sha=<워크트리 HEAD> -f merge_method=<merge|squash|rebase>`, with the full 40-character sha of the implementation worktree's HEAD; the branch is not deleted in this argv — the REST merge has no such argument, and deleting a branch is not a merge. The review rule compares the review against that HEAD, and the REST merge merges at once or is refused (409 when the pull request's head is another commit), so a merge made by that request merges what the rule approved. **A `gh pr merge` without `--admin` is not a binding, `--match-head-commit` or not**: on a base that requires a merge queue it enables auto-merge while required checks are pending and enters the queue once they have passed, comparing the head only at the request. The gate cannot see from the argv whether the base requires a queue, so it refuses that spelling as unbound on every target. On a base that requires a merge queue the REST merge is refused with 405, so no bound merge passes the gate there: that merge goes to a person through the `park` ending **The merge** below gives a 405. **Do not use auto-merge or the merge queue for a segment merge** — `gh pr merge --auto`, GraphQL `enablePullRequestAutoMerge` and `enqueuePullRequest`: GitHub compares the head only when the request is made and merges later, so a commit pushed to the segment branch in between (a fix cycle's push) is what lands. The gate reads them as merges with no binding whatever head they name. Under `선리뷰후머지` with `리뷰-후-머지` on, a merge argv for a segment that has a `segment` row is refused with **exit 2** before the rules run when the binding is missing, names another commit, or the worktree HEAD cannot be read — the message names the argument and the HEAD. The REST path is read with its `?query`, `#fragment` and trailing `/` removed, and `gh api`'s short options are read letter by letter as gh reads them, so `-iXPUT` is a PUT. Flags ahead of `api` (`gh --hostname=github.com api …`) are skipped the way gh skips them to find its command, and an argv whose `api` word may or may not be that command (after `--`, or taken as a flag's value) is read as a merge with no binding. A merge spelling that has no binding argument (`…/merges` whatever fields it carries — a `sha` there binds nothing on the server — and `mergeBranch`), a REST merge whose query string carries a `sha` key (gh sends it beside the body's `sha`, and which one the server reads is not the gate's to know), a `gh` call inside a `find -exec` whose words carry `{}` (find puts each match's path there, so the gate cannot read the endpoint that runs; it is judged at `머지`), a GraphQL body in a file, and one carrying a `#` comment, a `"""` block string, a fragment, a directive, a second field or operation, or its input object passed whole as a variable are refused the same way; spell the merge as the REST merge above, and send any other GraphQL a segment act needs inline with `-f query=`. Any other non-GET GraphQL body is read as a base change with no binding unless every operation is a `query` or calls only mutations that move no ref (comments, reactions, labels, assignees, issues, reviews, pull request state, project items): `updateRefs`, `updateRef`, `createCommitOnBranch` and every mutation the gate does not know are judged at `머지`, refused the same way, and are not on the collaboration surface — push to the segment branch and merge with the REST merge above instead. So are the REST writes that move a branch without a pull request — a non-GET `…/git/refs…`, `…/contents/…` (with or without `branch`; without it the commit goes to the default branch) and `…/merge-upstream` — and the background merge `…/pulls/<n>/merge-async`, which merges or enqueues after the request whatever `sha` it carries. Respell the merge that way and call again; that is the whole repair. **A local `git push` to the base is bound by what it puts there.** The gate strips the wrappers (`command`, `env`, `lockf`, `timeout`, …) and git's global options, runs `git push --dry-run --porcelain` with the same arguments where the push runs, and reads which remote refs would change. A push that updates the base is a merge **whatever you declared**: below `머지` it is exit 8, above it (`배포`, the target's cutpoint you normally write) it is judged at `머지`. Every commit it would put on the base must be the segment worktree's HEAD, or the act is refused with exit 2 naming the updated ref and the HEAD. Every spelling the dry-run can reproduce meets that one comparison — `U:<base>`, `U:heads/<base>`, `git -c … push`, `git -C <dir> push`, `command git push`, `env git push`, the empty refspec `:`, a glob, `--all`, `--mirror`, `--branches`, a configured `remote.<name>.push` — so a local base ref ahead of the reviewed HEAD (an unpushed commit in the main checkout) is refused through all of them. **A push the dry-run cannot reproduce is refused, not read.** On a target with a base branch, a push inside `bash -c`/`sh -c`, `env -S` or under `sudo` (and every such string the gate cannot show runs no push: one that names `git`, carries an expansion, a glob or a group, or whose command word is off the gate's short list of commands that run no text of their own — `.`, a path, an interpreter and `make` are all off it — so call the command directly instead of inside a shell string), one inside a `find -exec` whose words carry `{}` (find puts each match's path there, so the dry-run's literal `{}` is not the push that runs), one behind an environment assignment other than `LANG`, `LC_*` or `TZ` (`HOME=` and `XDG_CONFIG_HOME=` included, since the dry-run would read another configuration than the push) or behind an `env` option, one carrying a `-c` key that runs a command or `--config-env`, and one carrying a push option outside the gate's allow-list — an abbreviation such as `--no-dry` or `--exe=` included — is refused with **exit 2** before any rule runs, whatever you declared. The allow-list passes the options that decide what goes where (`-f`, `--force-with-lease`, `--force-if-includes`, `-u`, `-d`, `--all`, `--branches`, `--mirror`, `--tags`, `--follow-tags`, `--prune`, `--atomic`, `--repo`, `-o`, `-4`/`-6`, `--thin`) and drops those that change only the output or that the gate sets itself (`-q`, `-v`, `--progress`, `-n`, `--dry-run`, `--porcelain`, `--verify` and their `--no-` forms). `--receive-pack` and `--exec`, in any prefix, are refused as a form on every push. Respell it as `git push <remote> <refspec>` without that wrapper or option and call again. Push `HEAD:<base>` or `<segment branch>:<base>` — a segment's act runs in the segment worktree, so `HEAD` is that tree's HEAD. A push that would change nothing on the base is not bound. When the dry-run names no ref (the remote is unreachable, or it printed nothing but `Done`), the gate reads the refspecs instead and treats `:`, a glob, `--all`, `--mirror` and `--branches` as base pushes of the local base ref. **These checks run at `머지` and above, where the review rule fires**, and they first compare the row the review rule reads with the row the gate reads. The rule picks the segment's last `segment` and `cycle` rows by substring, so a sibling row whose text carries `id=<segment> ` or `세그먼트=<segment> ` becomes the row it reads; when the two picks differ the merge is refused with exit 2 naming the series. Write one more row of that series for this segment so it is the last one, and call again.

**`act --kind obligation` has its `--target` compared against the obligation row's `대상`.** A mismatch is exit 2. The landing test runs in that target's anchor repository, so fulfilling against a different target would measure the right commit in the wrong repository and report a confident wrong answer; the repair is to call again naming the target the row points at.

**A cone is the one `blocked` scope you may create; run scope you may only resolve.** A cone holds what stands on a refuted premise and lets its siblings keep running, which is what an open question needs. Declare `의존 세그먼트` or leave it out — the gate derives the cone either way and refuses a declaration that is a **proper subset** (exit 6). Widening passes.

**Use `grade` and `plan` rather than finding out by doing.** Without them the router has to learn by attempting, and that turns the progress-relative act budget into something that fires on grammar instead of on stagnation. Neither verb performs the act, neither takes act budget, and neither writes the row the act would have written.

**They are NOT free of ledger writes.** A common prelude runs ahead of the verb dispatch on every invocation regardless of which verb was asked for: the first call of a run appends a `run` row unconditionally, and later calls re-derive the authorization directory, overwrite the enforcement-surface baseline and append a `대상 추가` row. So a dry run does move the snapshot digest — but only its tip half, because the `run` and `대상 추가` rows are not components of the progress vector. The tip axis admits an ancestor inside a bounded window, so a router that reads a digest, asks `plan`, and then acts on the digest it read first is **not** refused, and **no forced re-read after a dry run is needed**. Re-read when the dry run sat among many other writers' rows, since the window is a few rows wide rather than a session long.

**And where that re-read is wanted it is a real `snapshot` call, not a file read.** `grade` and `plan` perform nothing and reach no acting path, so neither emits a digest however the flag is spelled — which is deliberate rather than an omission: emitting from a verb that answers a question would put a value in the file that no act of this run stands behind. So after a dry run there is no fresh emission to read, and the next acting call either calls `snapshot` or carries the value it held before the dry run, which the bounded ancestry admits.

### Judgment, not just acts

Not every decision is an act. For those, the question is **"may I choose this without asking?"** — the three grades of `_common/judgment-grade.md`. Grade 0 needs no record, grade 1 is adopted with a row carrying `등급`·`기준`·`되돌리는 법`·`판단 부류`, and grade 2 is escalated. **`팀 토론 진행` and `재설계` are never adopted as recommendations** — they are routing output, and whether to convene a team is the router's call rather than a stage's.

**You never choose to ask.** Submit your own recommendation with `act --kind judgment`; whether it becomes a question is the gate's decision. A grade-2 judgment is raised to a `절단점=판단` approval, and so is a grade-1 judgment that does not clear the auto-adoption floor. Both come back as exit 5, and the approval's id is derived from the judgment, so resubmitting the same one finds the open approval instead of opening a second. **With auto-resolution on (the default) neither waits**: the gate issues the approval, closes it at once as the adoption of your recommendation, and the act exits 0 with the `자율 승인` row naming the approval in `해소 승인` — see 「When an approval is pending」. A judgment approval left open from before is closed the same way on its resubmission — unless a person already answered it with free input, in which case it stays open. **A judgment approval of a held class is the exception**: the gate never closes a `사람-결정`, and closes a `시각-승인` as `승인` only when the visual sidecar's approval predicate holds, so while one is open the act comes back as exit 5, and the shift keeps routing under the **CFI-S4 exception** of the shift skill rather than ending.

**Once the answer arrives, resubmit the same judgment — that is the whole of the follow-up.** The approval's id is derived from the judgment, so the resubmission finds the closed approval rather than opening a new one, and the gate routes on its state: `승인` adopts the judgment and writes the row with `해소 승인=<id>`; `거부` and `무효` refuse the act and do **not** re-ask — except on an approval of a held class (`사람-결정` or `시각-승인`), where the resubmission writes the `자율 승인` row with `해소 승인=<id>` and exits 0 once the segment's `park` row is written (exit 3 before it), because parking the segment is what that answer asks for and the row is what marks it consumed; `대기` is still waiting, so leave it and come back. **One answer opens one judgment** — an id already named by a `자율 승인` row is spent, and a second judgment leaning on it is refused with a request for a new question. Nothing here re-opens a closed approval: only a question whose `기준` and `근거` differ hashes to a new id.

**The floor is a union.** Either arm admits: the manifest declared this `판단 부류` in a `자동 채택` row, **or** `되돌리는 법` is a runnable command whose argv0 grades at or below `워크트리쓰기`. Prose fails the second arm — it grades `등급 미상` — and that is the point of the field: produce the thing that reverses the decision rather than assert that one exists.

**The risk-handing classes are outside the union entirely.** `팀-구성`, `시각-면제` and `설계-골격` hand risk to the user, so neither arm admits them: the floor rejects them before it looks at the manifest or at the undo command. What follows is an **approval**, not a refusal — recording a judgment of such a class is permitted and only adopting it unattended is not. Declaring any of them in a `자동 채택` row is a hard stop when the manifest is frozen, and the runtime rejection is what makes the two agree instead of contradicting. `사람-결정` and `시각-승인` are outside the union too — not because they hand a risk on but because only a person, or for `시각-승인` the approval a person wrote into the visual sidecar, answers them — and their approval is not auto-closed either: it stays `대기` and holds its segment, unless a `시각-승인`'s predicate holds, which closes it as `승인`.

**What makes arm (a)'s input unforgeable** is three things, and it is worth knowing which: `## 인가` is exactly one section and the floor reads only that section; the `자동 채택` rows are inside `구속 다이제스트`, so appending one moves the digest and the next gate entry refuses; and the gate refuses any act that writes the manifest, at any cutpoint. The residual is that both sides of the digest comparison live in the same file, so a rewrite that moves the row **and** the digest field together is detected by nothing — which is why the write guard, not the digest, is the load-bearing half.

**A run may END with questions still open.** They do not count against termination condition 2, because a question's answer is an input to work that has not started and a successor run can consume it. An open approval of a held class, `사람-결정` or `시각-승인`, is the exception and does count: its question names a segment of this run, and a run that ended around it would leave it unanswered. What records them is the `done` file's third class, `종단 — 질의 잔여 N건 · 승인 <id>…`. A clause blocked on one is settled with `상태=보류` whose `근거` names that open approval id — which is a different disposition from `불가능`: impossible ends the clause, on hold hands it to the next run.

### Proposing that the run is done

`act --kind propose-done` carries the goal digest, the termination point decomposed into checkable clauses each with **evidence**, and the residual. **Evidence is a ledger reference or an observable artifact, never prose** — a proposal citing prose is the exact shape of "the check passes and the property fails", while one citing a merge commit is confirmed in the morning with one command.

**Settle the termination clauses before you propose done.** Enter this order when no unmerged, unparked segment is left to dispatch, no stage is alive, and no `shift_halts[]` element holds a segment. A plan with no implementation step and a design that stopped follow the same order.

1. Read the snapshot's `clauses[]` — one element per termination clause, with its `id`, `문면`, `상태` (`미정산`, `충족`, `불가능` or `보류`), `근거` and `요청`, the evidence request still open on it.
2. For each element whose `상태` is `미정산`, find by gate reads the evidence its `문면` asks for — ledger rows, the run directory, a merge commit's `git show --stat` or `git diff`, `gh pr view`, each through `exec … --surface 읽기` — and when you find it, write `act --kind clause`.
3. A clause whose evidence no read of this run can produce — its `문면` asks for a paid or credentialed call, a local launch, a device, or a person's confirmation — is not settled `불가능` without a question. A routing shift asks for it with `shift-halt` at site `종료 절 근거` (the shift's copy gives the form), and the seat puts that record to a person.
4. Once every clause is settled, check with `plan --kind propose-done` and then take `act --kind propose-done`.

**The evidence a clause row carries depends on its state.**

- **`충족` cites the ledger or an observable artifact** — a row anchor `A-<8 hex>`, a merge commit's full sha, a PR number, a run-directory or document path with its line, or `중단 답 줄 <n> · 첨부 <경로>` — never prose alone. The gate checks only that `근거` is not empty, so keeping to this is yours.
- **`불가능` cites what decided it** — a residual issue URL, a design step's `stage-result` row and halt record path, or the `중단 답 줄 <n>` of a `불가능으로 정산` answer.
- **`보류` names an open `절단점=판단` approval id**, and one approval holds one clause unless the design step opened it.

The disagreement runs both ways, and only one direction is obvious:

- The gate can **refuse** a proposal, naming the unmet conditions. A re-proposal against the same unmet set is rejected at the parser.
- The gate can also **end** the run. When every condition holds and the router reaches for something else, it must name a specific admissible next obligation — an open obligation's identity, a non-terminal segment, or a clause marked unmet. Failing to name one, the run terminates as satisfied. Without this the gate could only block termination, never cause it, and the router alone would decide when the night ends.
- **A goal can be unreachable.** The router may propose done with a clause marked impossible and its evidence; the gate accepts that on a reduced condition set.

**A run the PERSON decided to end is that same path, and it is the only way to record their decision.** When the user says to stop short of the termination point, propose done with the unmet clauses marked impossible and the user's own utterance as the evidence for each. Do not reach for `problem` to record the stopping: that row **creates an open obligation**, which is condition 3's input, so writing it makes the run harder to end — the act of recording the stop would worsen the thing being recorded.

This matters because of what `done` is for. `런 상태` in the snapshot is derived from the run directory's `done` file and from nothing else, so a run nobody proposed done for renders `진행 중` forever — indistinguishable from one that died quietly, and the watcher never self-stops either, so it becomes a zombie of its own. A decision that exists only in a conversation is not on disk.

### Dispatching a stage

A stage is `act --kind skill`, and the gate launches it through the wrapper. Never assemble a CLI command line in the router: `"$CLI_BIN" "$@"` is an argv laundering tool for anyone holding an allow-list entry, and the wrapper's only legitimate caller is the gate.

**What goes after `--` is exactly this, and getting it wrong costs money without saying so:**

```
gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <id> \
  --cutpoint <token> --surface <token> --snapshot-digest <H> \
  --emit-digest \
  -- <스테이지 종류> -p "/cc-cmds:<스킬>-unattended <인자…>"
```

`<H>` comes from the last `[gate-digest]` stderr line of the previous acting call's own `--emit-digest`, when that call is in the immediately preceding response and was its only one; otherwise from `<run-dir>/digest/gate-digest-router.json`, which the same call wrote; where neither is there take it from `snapshot` instead, and where the gate refuses the flag as an unknown argument drop the flag and keep taking it from `snapshot`. **Check its `actor` field before using `H`** — it carries the emitting stage id verbatim, `router` when the router wrote it, and a value that is not yours means the file is somebody else's emission rather than a stale one of your own; fall back to the round trip in that case.

**The first token after `--` is the STAGE KIND, and it is consumed before the CLI ever sees the rest.** `act --kind skill` calls the launcher as `<alias> <segment> <stage-kind> <cli args…>`, so a form that starts with `-p` hands `-p` over as the kind. The vocabulary check then falls back to `generic`, meaning the stage runs under settings that are not its own, and `-p` is gone from what reaches the wrapper. The kind is one of `audit`·`design`·`implement`·`review`·`reconverge`·`split`·`generic`, and it selects the settings variant rather than the skill.

Four parts, each with a failure it prevents:

- **`-p` is required.** The wrapper passes everything after `--` to the CLI, so without `-p` the prompt is never delivered. Omitting it while passing a bare skill name ends as `산출물 없는 정지 rc=0` — the model wakes with an **empty first user message** and terminates as a success. Omitting it while passing a quoted slash command instead fails loudly (`stage-wrapper: CLI arguments are required after --`, `크래시 rc=2`), which is the better of the two.
- **The prompt is a slash command**, leading `/` included.
- **It must be the `-unattended` variant** — and the reason is not that the plain name fails. The plain `design-audit`, `implement` and `review` skills carry `disable-model-invocation: true`, which closes the **Skill tool** path and nothing else; a headless stage that names one still reaches the same instructions by reading the file. So the failure mode is not an error, it is a stage running the interactive-shaped workflow with nobody to interview, and it is green. Nothing in this loop detects it, because there is nothing to detect: the dispatch is well formed and the stage produces output. Only the spelling in the prompt separates the two.

The first form is the dangerous one precisely because it is green: exit 0, cost charged, no output. Neither the gate nor the wrapper can catch it — a prompt is a string, and any string is a valid one.

**Issue the dispatch in the foreground; it returns within seconds.** The gate pins the attempt, writes a one-shot launch token, and starts `gate.sh supervise-stage` — a re-entry of the gate itself, not a second script — through a double fork that leaves it adopted by init before the call returns. That supervisor consumes the token (a caller without it is refused with exit 3 and starts nothing), runs the stage, writes `stage-result` and `cost`, and removes the per-segment files. The act's exit status is therefore LAUNCH success; how the stage ended is what `wait` reports.

**A routing shift does not wait in its turn at all.** When a stage's result, a pending CI verdict or the reset of a cut stage's limit is all that is left, it ends with a `대기` handoff (naming CI segments in `'CI 대기=<세그먼트>'`, segments waiting on their base branch in `'master 대기=<세그먼트>'` and cut keys in `'리셋 대기=<key>'`), and the gate process of the lead's `router-shift` call waits in the shell and launches a successor when the thing waited on moves — `autopilot-router-shift` 「Waiting on a stage」. Every "wait on it" below means that for a shift. The form that follows is this copy's own, for a lead that holds a wait itself.

**To wait for it, issue `gate.sh wait --manifest <매니페스트> --segment <id>` as a harness-tracked background command and put `Monitor` on its output.** When nothing is dispatchable or mergeable and two or more segment stages are live, wait on the earliest-declared live segment among those named in some segment's `머지 대기`; if none is named, on the earliest-declared live segment. It prints a heartbeat line every 300 seconds (`--interval`) and a final line, and its exit status is the stage's own rc, one of 11–14, or 15 — a shift entering `wait` past the hard limit is sent back at once, with a `gate:` line on stderr and no final line. `--timeout` defaults to 21600 seconds and ends the wait with 13, never the stage. Tracked is right for `wait` because it must die with the seat that issued it; the dispatch does not block, because the harness reaps a tracked job by walking its process tree and a blocking dispatch would take the stage down with the seat.

**The stage's stream is at `<run-dir>/log/<segment>.json`**, and its stderr beside it. That is where a stage's own account of itself lives when you need it.

Three conditions must **all** hold before a segment is dispatchable, and reading only the first is how a router concludes it may go: **dependency** (no predecessor unfinished), **capacity** (concurrent model streams within the cap, taken from each skill's declared value rather than estimated), and **exclusion** (no live stage already holding an exclusive resource — the experiment-worktree prefix, which counts repo-wide, and one live stage per output document path).

The **dependency** condition reads `선행` alone — implementation precedence, a predecessor that has not landed. A predecessor named only in `머지 순서` does not hold back the dispatch; it holds back the merge alone (see 「Merging and applying a segment」).

#### Re-attaching a cut stage

**A stage cut mid-turn is continued, not bought again.** A fresh dispatch starts a new session: a design or review team is spawned from nothing and re-runs every round it had already published, an audit re-reads everything, and an implement stage re-derives its whole context. `--resume <세션 id>` on `act --kind skill` instead continues the cut session's own transcript — its team members still running in the current round are resumed by `agentId`, witnesses already published are collected where they lie, and the turn goes on from the step it was on. Measured: a design stage that crashed mid-discussion was re-attached and finished `정상 완료`, and implement stages cut by the account's session limit were re-attached and finished after fresh re-dispatches had each thrown away some ninety turns — every one of those re-attachments improvised by a shift that read the gate's source, because no router text offered it. Where nothing offered it, one design was re-kicked as a new run five times running, each run paying again for the discussion round its predecessor had already published.

**Take this before every other arm that reads a stage's last `stage-result` row** — item 1 of 「Dispatching the design stage」, 「Recovering a review stage that crashed」, and any fresh re-dispatch of a segment — and for every stage kind. Each read goes through the gate (`gate.sh exec … --surface 읽기 -- <command>`) on the terms 「Recovering a review stage that crashed」 states: answered only by output carrying `게이트 통과`, exit 4 retried at most three times, a refusal never read as a file fact. `<key>` below is the segment id, or the step id for the design step. Re-attach only when all four hold:

1. **Nothing is running on it.** `<key>` is in none of `live_stages[]`, `orphan_stages[]` and `waiting_stages[]` — an orphan is settled as `외부 종료` by the next gate call, and is read here after that; a waiting key is in flight and is waited on.
2. **The last row was cut, not finished.** Read the stage's rows — `grep -nF '| 세그먼트=<id> | 스테이지=<id> | 종류=' <원장 경로>` for a segment, `grep -nF '| 세그먼트=- | 스테이지=<step id> | 종류=design |' <원장 경로>` for the design step — and take the last line. It qualifies when it reads **`종단 부류=크래시` and that attempt's stream carries the usage-limit envelope** (`grep -cF '"api_error_status":429' <절대 run-dir>/log/<key>#<실행 버전>.json` answers 1 or more), or when it reads **`종단 부류=외부 종료`** — the process and its supervisor vanished mid-turn: a machine asleep, a reboot, a process group ended. It also qualifies when it reads **`종단 부류=한도 종료`**, on the class alone — the 429 probe is not a condition for this class. The recorder that wrote it read `api_error_status` as a parsed value, which takes a number, a string and a serialization with spaces alike, while the probe counts only the bytes of a numeric serialization without spaces; the two do not measure the same inputs, so holding the probe as a condition would drop a differently serialized limit death from re-attachment without a warning. The reset paragraph below applies to it unchanged. **`종단 부류=거절 종료` qualifies too, once only** — the stage ended because the model refused, and its paragraph below replaces item 4 and the reset paragraph for it. Every class other than these four, and a `크래시` whose stream holds no 429, is not this subsection's: route it as before.
3. **There is a session to continue.** The row's `세션 id` is not `미상`, and the attempt's stream shows that session actually started: `grep -cF '"session_id":"<세션 id>"' <절대 run-dir>/log/<key>#<실행 버전>.json` answers 1 or more. A stage that died before its first request has no transcript to resume, and a fresh dispatch loses nothing.
4. **It has not already been re-attached three times.** Count this stage's `stage-result` rows carrying `세션 id=<세션 id> ` and one of `종단 부류=한도 종료`, `종단 부류=외부 종료` or `종단 부류=크래시` — every re-attachment keeps the session id, and only a cut adds to this count. Four or more means the original and three re-attachments all ended cut; route as before.

**A limit must have cleared first.** A stage is cut by a limit when item 2's last row reads `종단 부류=한도 종료`, or `종단 부류=크래시` with a 429 in that attempt's stream. Re-attaching it before the limit clears makes the first request die on the same limit and spends an attempt. It has cleared when **any one** of these three holds:

- **(a) The reset has passed.** Read the last `rate_limit_event` of the cut attempt's stream and its `rate_limit_info.resetsAt` (epoch seconds) — `jq -c 'select(.type == "rate_limit_event") | [.rate_limit_info.status, .rate_limit_info.resetsAt]' <절대 run-dir>/log/<key>#<실행 버전>.json`, last line — and compare it with `date +%s`. With no typed frame (a `크래시` stream can lack one; a `한도 종료` never does), (a) cannot be judged: it neither holds nor fails. **The `result` sentence (`resets 1:50pm (Asia/Tokyo)`) decides nothing** — a session limit names a time with no date, a weekly limit a time with a date, and some limit deaths name no reset at all, so there is no one rule that compares it with the clock. When (a) cannot be judged, copy that sentence into `막힌 지점` as a marker for a person.
- **(b) The shift itself is the observation.** All four hold: (1) the shift's own `교대 기동` row sits on a later ledger line than the cut `stage-result` row — read with `grep -nF '| 서수=<n> |' <원장 경로>`, `<n>` being the snapshot's `shift.n` (`서수=` is written by the launch row alone, so the read is unique); the cut row's line comes from item 2's read; (2) the two rows carry the same `레인`; (3) the cut row carries no `계정` field, or `계정=-` — an inventory id or `(미상)` fails this; (4) the class is `한도 종료`, or `크래시` with the cut stream's last `rate_limit_event` reading `rejected`. **The premise, stated:** a shift and a stage launch on the same model, so a shift reading this rule means a request succeeded from the same configuration home after the cut was recorded — under a live account limit a shift dies on its first request. A cut recorded after the shift's own launch is not covered by (b), whoever launched that stage: it waits for (a), (c) or the next shift's launch.
- **(c) The seat said so.** A `한도 해제` row sits on a later line than the cut row. Read it with ``grep -n '^- `한도 해제` |' <원장 경로>`` and compare the last line number. **The read is anchored at the row head, and must be**: the `exec` that runs it first writes a `자율 승인` row whose `argv` carries the series name backticks and all, so a read by the name alone always matches the shift's own read row — which is always later than the cut — and (c) would hold with no signal at all. A `막힌 지점`, `근거` or `--rationale` quoting the name does not match the anchored read either. (b)'s `| 서수=<n> |` read has no such trap, because the gate maps a `|` inside a value to `/`. The seat writes this row (「Shifting the loop, and re-arming the channel on every return」).

**Order is ledger line order.** The ledger only appends, so a later line is a later row. **Evidence is spent per cut**: a re-attached attempt that dies again lands a new `stage-result` row on a later line, so the same launch or the same signal never counts twice, and item 4's three re-attachments bound the attempts. When a branch holds, name it in the re-attaching act's `--rationale` (`한도 해제 근거=리셋 경과`, `교대 관측(기동 줄 56 > 절단 줄 52)`, `좌석 신호(줄 61)`) so the judgment lands on the approval row. When none holds, route other work; when nothing else is dispatchable and (a) can be judged for the cut key — its stream carries a typed `rate_limit_event` — end the shift with `사유=대기` and `'리셋 대기=<key>[,<key>…]'` naming the cut keys, and the gate's wait wakes your successor at the reset (「Waiting on a stage」). When (a) cannot be judged, or the gate refused that `대기` with exit 3, end the shift with `사유=중단` and put the measured values in `막힌 지점`, not an instruction to wait (`교대 기동 줄 41 < 절단 줄 52`, `레인 상이`, `계정 바인딩`, `한도 해제 행 없음`, `resetsAt 2026-10-01T04:20:00Z 미경과`).

**The dispatch keeps the stage kind, the target and the `--segment` of the attempt it continues** (`-` for the design step) and adds `--resume`:

```
gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <id | -> \
  --cutpoint <token> --surface <token> --snapshot-digest <H> --emit-digest --resume <세션 id> \
  -- <스테이지 종류> -p "계정 사용량 한도나 프로세스 종료로 앞 턴이 끊겼고, 이제 이어서 진행할 수 있습니다. 중단된 지점부터 하던 절차를 그대로 이어 가세요 — 처음부터 다시 하지 말고, 이미 끝난 라운드와 이미 쓴 절·커밋은 다시 하지 마세요."
```

**The prompt is that sentence, verbatim, and never the slash command again.** The resumed session is already inside its `-unattended` skill: the `-unattended` rule of 「Dispatching a stage」 is about which skill a NEW session loads, and re-sending the command re-enters the skill at its first step, which is the restart this subsection exists to avoid. The gate accepts only a session id that appears on this stage's own `stage-result` rows and refuses any other with exit `2`. It pins a new attempt number, so the continued turn gets its own stream and its own row under the same `세션 id`; wait on it like any dispatch, and route the row it lands as usual — a cut row comes back here under item 4's count.

**A `거절 종료` row is re-attached once, and a second one parks its cone.** A refusal is not cut by anything that clears by itself, so the crash retry and a fresh dispatch would buy the same refusal again. Count the key's rows carrying `종단 부류=거절 종료` on the rows item 2 read. One → dispatch the same `--resume` act above; the gate replaces the prompt with its own fixed refusal message, spends no continuation, and refuses with exit `2` a session id other than the last row's. Two or more, or a row whose `세션 id` is `미상` → do not dispatch: record `gate.sh act --kind blocked` with scope `cone` anchored on the segment and `원인=거절 소진`, and leave what the stage saved in place. The design step has no cone; stop the design as 「Dispatching the design stage」 describes, with the `거절 종료` rows as its evidence. The fixed-graph driver takes the same path on its own: one same-session re-attach, then a cone park with `원인=거절 소진` (a run park for the design step).

#### Dispatching the design stage

When the snapshot's `design_required` is `true` and a step in `steps[]` has `skill` `design`, this loop is the only thing that dispatches it — the fixed-graph driver's design arm is not on the router's path. The step id below is that step's `id` (`.steps[]? | select(type == "object" and .skill == "design") | .id // empty`), read from the snapshot, not from a read of the plan. **Both guards carry load and neither is decoration** — an object step written without an `id` yields nothing here rather than `null`, and an older string step yields nothing rather than a jq error. An empty result means the plan named no design step, which is the same conclusion the gate reaches before it refuses the dispatch with exit 3. **The selector is the front half of the gate's decision, and the back half is shell rather than jq.** The gate strips blank lines from that output and then requires exactly one line to remain, so three results read the same way here — no line at all, one blank line (a step whose `id` is the empty string), and two or more lines (a plan carrying more than one `design` step). All three mean `no single design step`, and all three take whatever disposition an empty result takes here. **An empty-string `id` is not a design step with a blank name.** Nothing on this path keys on that value: a run-directory file named with it and a `| 스테이지= |` grep both land on real things that are not this stage. **A design step is not a segment.** It has no `segment` row and is dispatched with `--segment -`; every ledger row about it — the dispatch, the stage's own acts, its `stage-result` — carries `세그먼트=-`, while its run-directory files (attempt pin, stream, pid record, halt record) are named by the step id. That is the row the fixed-graph arm writes too, so both paths leave one row shape. **Three guards, and the document's freeze line is none of them.** Every read below goes through the gate and is answered only by a call whose output carries `게이트 통과`, on the same terms as 「Recovering a review stage that crashed」.

1. **Resume is decided by the ledger.** Read this run's rows for the step: `gate.sh exec … --surface 읽기 -- grep -nF '| 세그먼트=- | 스테이지=<step id> | 종류=design |' <원장 경로>`. If a row exists the stage was dispatched already, and **the last such row decides** — a step dispatched again carries one row per attempt. **Take 「Re-attaching a cut stage」 first**: a row it re-attaches is continued in its own session and goes nowhere else in this list. `종단 부류=정상 완료` goes to item 5's freeze check. **`외부 종료`, `크래시` and `공허한 성공` may be dispatched afresh, and only onto an absent document** — the gate's termination condition 1 reads these three the same way. **`한도 종료` is read exactly as `크래시` here**, in this list and in the window of stopping the design below; it is never a `공허한 성공`, so no continuation counter applies to it. **`거절 종료` is in none of the three** — 「Re-attaching a cut stage」 takes it once, and a second one stops the design; it is never dispatched afresh. **A `공허한 성공` continued up to the cap is not dispatched afresh either**: when `gate.sh exec … --surface 읽기 -- cat <RUN_DIR>/continue/<step id>` answers `2` (the gate's continuation cap), stop the design as below, with the last `stage-result` row and `계속 소진` as its evidence — the gate reads the same counter, so condition 1 names the step and the proposal is recorded as `무효화`. This seat does not continue a stage, but a shift that continued the step up to the cap hands it the same ledger, and both seats stop the design there. The fixed-graph driver does not dispatch a `공허한 성공` design stage afresh first: it continues the same session, and runs a fresh process only when there is no transcript or the attempt ran zero turns. Each says the stage is over and nothing proves it carried anything off: `외부 종료` is written by the gate's prelude about a dispatch whose process and supervisor both vanished, without looking at the document; `크래시` is a non-zero exit, and `한도 종료` is a non-zero exit whose own stream shows the stage died of a usage limit that resets by itself — a limit death whose stream does not show it is still filed `크래시`; `공허한 성공` is a stage that returned zero without a frozen document. **One `공허한 성공` is not this case**: a stage that emitted a judgment and opened an approval on this step lands on the same class, stopped on purpose, and a person owes it an answer — an entry in `pending_approvals[]` whose `blocks` is the step id means stop the design as below, holding its clauses `보류` on that approval. For the three, go on to item 2, whose first bullet holds the stage dispatched again while it runs, and then item 3 in full: nothing at the path, or the stage's own spawn-time stub → item 4 dispatches again, on the next attempt number; anything else at the path → stop the design as below, because a stage that ended after saving left the document partway. **Two of the three buy one fresh dispatch and no more: a `크래시` whose stream holds no 429 envelope, and a `공허한 성공`.** Neither clears by itself, so the next attempt meets the same cause — a design cut by the background-wait cap returns zero at the same place again, and a stage a person stopped by ending its `pid` is a `크래시` with no limit behind it, which this depth undoes at most once rather than every time. The gate refuses no fresh dispatch, so stopping is this item's; the gate's termination condition 1 counts the same fresh attempts by the same definition and reads a spent depth as a step that will not be dispatched again. Count the step's fresh attempts on the rows already read: a row is a re-attachment when its `세션 id` is not `미상` and stands on an earlier row of the step, and every other row is a fresh attempt. A continuation row carries its session id on in the same way, so it is not a fresh attempt either — the continuation cap bounds it instead. **When the last row is one of these two and two or more fresh attempts already stand, stop the design as below** instead of going on to item 2; condition 1 then names the design step, so once the clauses are settled `propose-done` closes the run as `무효화`. Whether the stream holds the envelope is the read 「Re-attaching a cut stage」 item 2 makes (`gate.sh exec … --surface 읽기 -- grep -cF '"api_error_status":429' <절대 run-dir>/log/<step id>#<실행 버전>.json`). `외부 종료` and a `크래시` carrying the envelope keep the window as stated above. Every other class stops the design there. A stage that halted left a document partway through its walkthrough or a question for a person, and neither a second design nor the audit may take it.

   **A halt that asks a person does not stop the design.** When the last row reads `종단 부류=의도된 park`, read that attempt's halt record — `gate.sh exec … --surface 읽기 -- cat <절대 run-dir>/halt/<step id>#<실행 버전>.md`, with the row's own `실행 버전`. When it carries the closing fence and at least one option line under `**선택지**:`, the stage stopped on a question one of those options answers, and a person can give that answer inside this run: the seat asks it and writes a `중단 답` row (「Shifting the loop」), and the shift's 「Handing on a person's answer to a halt」 hands it on to the step. So do not propose done on it. Dispatch nothing that depends on the step, and end the shift with `사유=중단`, putting the record's absolute path in `막힌 지점` — that field is where the seat looks for a record to ask. An element of `answered_halts[]` naming the step is that answer already given, and the handing-on procedure takes it before this item; when that procedure cannot carry the answer out, its item 8 hands the record back to a person with a cone row of the form `스코프=cone 원인=막힘 '앵커 세그먼트=<segment or run-scope step id>' '사유=중단 답 라우팅 — <기록 파일 이름> — <reason>' '근거=중단 답 줄 <line>'`. **An answer already carried over is not asked again**: when the element naming the step reads `state` `이월`, the person answered and no account had room before the deadline, so the answer waits for the next run in its `이월` row — do not carry it again, do not put its record in `막힌 지점`, and end with `사유=이월` instead of `사유=중단`; the gate refuses a `사유=중단` whose only blocker is such an answer. Only a halt record that offers no option, or none at that path, stops the design as below. Measured: a design stage halted on one residual item with three options, the first of them a reversible disposition; the shift stopped the design here and the run closed as `무효화` while a person sat at the seat, so the answer that would have carried the run had nowhere to go but a new run.

   **Stopping the design is not a `blocked` row this loop writes.** A design step has no `segment` row; two cones anchor on a run-scope step id — the gate's deadline park, written when the step's launch cannot finish inside the run's deadline, and item 8 of 「Handing on a person's answer to a halt」's routing block — and both hold the whole run. Only the deadline park, whose `근거` carries the step's lineage, is released by a later attempt of the step as well; the routing block carries no lineage and is released only by a `원인=해소` row of the same `사유`. What stops is everything that depends on the step: dispatch none of it, and once nothing else in the graph is dispatchable, propose done with each clause that needs the document marked `불가능` and the `stage-result` row — plus the halt record's path when one exists — as its evidence. A clause held by an approval the stage's emitted judgment opened is `보류` naming that approval id instead. **The gate records that proposal as `무효화`, never as satisfied.** With no `segment` row, condition 1 names the design step instead of saying the run has not begun once the step's last `stage-result` row is not one item 1 dispatches again, a saved document already sits at the path, or the manifest names no document — item 1's window (`외부 종료`, `크래시`, or `공허한 성공` with no open approval on the step and not continued up to the cap, over nothing at the path or the spawn-time stub, and for a `크래시` with no 429 envelope or a `공허한 성공` only until two fresh attempts stand) is where the plain line stands; when every clause is settled that line is the only one left, and `propose-done` closes the run as `무효화`. That verdict is the gate's, not this loop's — a `1` still in `unmet_condition_numbers` is no reason to hold the proposal once the clauses are settled as above. **One approval may hold several clauses `보류` only when it was opened by the design step** (its `막는 세그먼트` is the step id): the step emits one judgment for the whole document, and every clause that needs the document waits on that one answer. Any other approval id named on a second clause is still refused.
2. **A stage still running holds everything — a spent dispatch pin does not.** Item 1's row is written only when the stage ends, and the stage puts a file at the document path when it spawns its team, hours before its last edit freezes it — so while it runs, item 1 finds no row and item 3 finds a document. Before item 3, look for the step itself. **Three signals, and they do not share one disposition.**

   - **Its id as `세그먼트` in the snapshot's `live_stages[]`, or its id in `orphan_stages[]` or `waiting_stages[]`** → **wait and advance nothing**: dispatch no step that depends on the design, and wait on it with `gate.sh wait --manifest <매니페스트> --segment <step id>` (the step id, never `-`); when the wait ends, start again from item 1.
   - **A dispatch record with no row** — `gate.sh exec … --surface 읽기 -- ls <절대 run-dir>/<step id>.attempt` answering present while item 1 found none — → wait on it the same way, **once**. That pin is the state `wait` answers **14** for: the attempt number was stamped and no row ever followed. `wait` does not remove the pin on that path, so a 14 means the pin is **spent**, not that the stage is still coming — do not wait on it a second time and do not start again from item 1. Go on to items 3 and 4 and dispatch; that takes the next attempt number. Reading 14 as "still running" is what turns 「wait → 14 → start over」 into a circuit with no exit, because nothing in it ever clears the pin.

   This guard is not about remembering a dispatch — the session that meets it is the one that took the seat mid-stage and never saw the dispatch at all.
3. **It fires only on an absent document, and the design stage's own spawn-time stub counts as absent.** `ls <스냅숏 design_doc>` through the gate. A document that exists is not this run's to design, whatever else it contains — a person's unfrozen document lacks the freeze line too, and a dispatch keyed on that line would write over it. Do not dispatch.

   **The one file that is not somebody's work is the stub the design stage writes when it spawns its team** — an H1 and the team's ledger comment block, with no `##` section yet. Ask the file rather than the path, through the gate: `grep -qF '<!-- cc-design-ledger' <문서>` true **and** `grep -qE '^## ' <문서>` false. Both → the previous attempt carried nothing off, there is nothing to write over, and the path counts as absent: go on to item 4 and dispatch. A person's document fails the first test and a saved one fails the second, so neither is mistaken for a stub. Measured: a design stage crashed on a session limit and left 2841 bytes with no `##` heading at the path; every later run stopped here on that file until a person renamed it by hand, which no procedure asks for and an unattended run has nobody to do.

   **This leans harder on item 2, which is why item 2 comes first.** The stub is at the path while the stage is still running, so the only thing standing between a live stage and a second dispatch is item 2's live-stage check — never reach item 3 before item 2 has answered.

   **Whether the graph goes on is the freeze line's to say:** a document carrying a line reading exactly `**상태**: 동결됨` (`grep -qxF '**상태**: 동결됨' <문서>` through the gate) → the graph goes on to its next step with that document as it stands; a document without that line — a person's hand-written draft included — → stop the design as item 1 says, naming the missing freeze line in the evidence, because an unfrozen document never goes on to the audit or to segment planning (item 5). **Record no judgment row for either**: the judgment vocabulary has no class for this decision, and borrowing a class meant for something else would put a mislabelled row where the morning audit reads classes.
4. **The dispatch.** Stage kind `design`, home alias, `--segment -`, document path first and task sentence second — the fixed-graph arm's shape:

   ```
   gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment - \
     --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \
     -- design -p "/cc-cmds:<스냅숏 design_skill> <스냅숏 design_doc> \"<## 의도 의 첫 비어 있지 않은 줄>\""
   ```

   **The slash command is the snapshot's `design_skill`, as it stands** — the selection function already picked it from the frozen plan: `design-base-unattended` when `design_scope` is `base`, `design-solo-unattended` when `design_tier` is `solo`, `design-solo-unattended` when `design_tier` is `team-4` and `design_path` is `solo-audit`, `design-discuss-unattended` otherwise. Do not pick it again from `design_scope`, `design_tier` or `design_path`: two readers of one choice are two places it can disagree. That skill's file is the one whose existence a dispatch presumes.

   The gate exempts exactly this form — `--kind skill`, `--segment -`, stage kind `design` — from the `segment` row and predecessor checks, and only when the frozen plan requires a design and names exactly one `design` step; it keys the stage on that step's id and refuses with exit 3 otherwise. Do not write a `segment` row for the step to get past a refusal: that row is what termination condition 1 counts, and a design step is not a segment. The path is the snapshot's `design_doc`, passed as it stands — never the `## 요소` key joined onto a worktree: for a document outside every repository that key is the absolute path with its leading `/` removed, and the gate refuses with exit 3 a design dispatch whose document argument differs from `design_doc`. The task sentence is the first non-empty line inside `## 의도`'s fence, copied verbatim. Wait on it with `gate.sh wait --manifest <매니페스트> --segment <step id>`.

   **The name belongs to the kickoff, and this loop never supplies one.** `## 요소`'s `설계 문서` is chosen in Act 1 (Step 5k) and frozen with the manifest; on a `design_required` run `(없음)` is a refused value there, rejected by the kickoff's own pre-freeze self-check and again by the gate's exemption. So when `design_doc` is `null`, do **not** compose a path for the argv. A path invented here names a document no other guard, no audit and no segment plan is looking for, and the run would go on around it. Let the gate refuse with exit 3 and stop the design as item 1 says.
5. **`정상 완료` on the row is not the freeze.** On this path the gate classifies a stage by its exit, its halt record and whether it wrote a gate row, and none of those says the document was frozen. So check both authored facts before anything reads the document: the freeze literal `설계 문서를 동결했습니다.` in the stage's stream (`gate.sh exec … --surface 읽기 -- grep -rlF --include='<step id>#*.json' '설계 문서를 동결했습니다.' <절대 run-dir>/log`) **and** a line reading exactly `**상태**: 동결됨` in the document (`grep -qxF '**상태**: 동결됨' <문서>`). Both → the next step of the graph; the stage names no next step, by contract. Either missing → stop the design as item 1 says, naming which of the two is absent in the evidence. **An unfrozen document never goes on to the audit or to segment planning.**

#### Dispatching the audit stage

When the design stage's last `stage-result` row is `정상 완료` and item 5 above found both freeze facts, the next step of the graph is the audit, if the plan names one. **A plan with no `design` step at all opens on the audit.** A run anchored on a document that was frozen before it began — a `doc` anchor entering at `design-audit`, or, on a plan frozen before the tiers were `solo` and `team-4`, a `lead-solo` design the kickoff wrote itself — has no design stage to wait on, so when `steps[]` names no `design` step and its one `design-audit` step has no `stage-result` row yet, the audit is the run's first dispatch. The one fact to check before it is the freeze line in the document (`grep -qxF '**상태**: 동결됨' <스냅숏 design_doc>`, through the gate); a document without it → plan no segment, and stop as 「Dispatching the design stage」 item 1 stops, naming the missing freeze line. The step id is read from the snapshot with `.steps[]? | select(type == "object" and .skill == "design-audit") | .id // empty`; as with the design step, an empty result, a blank line or two lines all mean `no single audit step`, and the gate refuses the dispatch with exit 3 on the same reading. **An audit step is not a segment either**: it is dispatched with `--segment -`, every ledger row about it carries `세그먼트=- | 스테이지=<audit step id> | 종류=audit`, and `gate.sh wait --manifest <매니페스트> --segment <audit step id>` waits on it.

```
gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment - \
  --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \
  -- audit -p "/cc-cmds:design-audit-unattended <스냅숏 design_doc>[ --base]"
```

Append ` --base` only when the snapshot's `design_scope` is `base`. The document argument is the snapshot's `design_doc` as it stands. The gate refuses with exit 3 an audit, split or re-convergence dispatch whose prompt does not begin with that step's slash command as written in this file, or whose document argument differs from `design_doc`; a `--resume` dispatch — a re-attachment, a continuation or a halt answer handed on — is exempt, because its prompt is the fixed sentence those sections give and the session it resumes is pinned to this step's own rows. Wait on it with `gate.sh wait --manifest <매니페스트> --segment <step id>`.

The gate exempts this form from the `segment` row and predecessor checks only when the plan names exactly one `design-audit` step and either requires a design or names no `design` step at all, and it checks its preconditions before it writes anything: when the plan has a design step, that step's last `stage-result` row is `정상 완료` — or the step has no row at all and the document is already frozen, the run having been kicked off again over it with its design skipped; the manifest's document carries the line `**상태**: 동결됨` exactly once; and neither the design step, if there is one, nor the audit step has a live attempt. A refusal is exit 3; do not write a `segment` row to get past it. Resume, re-attachment and continuation read the audit step's rows the same way 「Dispatching the design stage」 items 1 and 2 read the design step's, keyed on `종류=audit`; when the continuation cap is spent, the gate says to continue the audit no further, and no segment is planned on that run.

**The audit runs in a linked worktree of its own, detached at the base branch's tip — never in the main worktree — and the gate makes it.** The main worktree is the one every run and session on the repository fast-forwards after a merge, so an audit window of twenty-odd minutes there sees its own `HEAD` tree move, and the audit's freeze check reads that as a mismatch and halts with no automatic retry, however unrelated the merged paths are. The dispatch above creates `<main worktree>-run-<run id>-<audit step id>` with `git worktree add --detach` at the target's base branch when that path is absent, reuses it when a re-audit of the same key finds it there, adds it to the stage settings, and fails with exit 3 and launches nothing when the path is held by anything that is not a worktree of the target. Every act the audit stage then issues with `--segment -` runs in that tree. Do not create it with an `exec`, and do not write a `segment` row to name it — no row names it, and the gate resolves it from the audit step id. The document argument stays the main-worktree absolute path: `docs/` is gitignored, so the linked worktree does not carry it, and the audit takes its code root from the tree its acts run in.

**The audit edits the document**, so whatever was true of the document before it ran is read again after. Once its last `| 세그먼트=- | 스테이지=<step id> | 종류=audit |` row is `정상 완료`, check that its stream carries `이 명령은 여기서 종료합니다. 추가 리뷰 라운드는 없습니다.`, that at least one `<메인>/docs/design-audit/<slug>.reader-*.md` exists and that the document still carries `**상태**: 동결됨` exactly (`grep -qxF '**상태**: 동결됨' <문서>`), both through the gate, and that the snapshot's `audit_skeleton_due` is `null`. Any of the first three missing → plan no segment and dispatch no split, and stop as 「Dispatching the design stage」 item 1 stops, naming which fact is absent. `audit_skeleton_due` not `null` → 「Routing a skeleton-grade audit to re-convergence」 below.

#### Routing a skeleton-grade audit to re-convergence

An audit that ended `정상 완료` may still have found a defect that overturns a decision sentence of the document — its report's skeleton fence counts it, and its `stage-result` row carries `골격급=<n>` and `재수렴 요청=예`. The gate reads that row and fills the snapshot's `audit_skeleton_due` with `{"step": "<audit step id>", "skeletal": <n>}`; it is `null` otherwise. While it is not `null` the gate refuses segment planning and the split's dependency, so plan nothing on the audit: re-converge the document first, in this run, and audit it again.

```
gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment - \
  --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \
  --rationale '감사 골격급 재수렴' \
  -- reconverge -p "/cc-cmds:design-reconverge <스냅숏 design_doc> 감사 골격급"
```

The gate keys that `- reconverge` on the audit step only while the step's last row is that audit and holds the scope after the document to `감사 골격급`; its row then reads `세그먼트=- | 스테이지=<audit step id> | 종류=reconverge`. Wait on it with `gate.sh wait --manifest <매니페스트> --segment <audit step id>`. **After it ends**, read the re-convergence's terminal literal in its own stream, as `autopilot-router-shift` reads it. Present → dispatch the audit afresh on the same key with stage kind `audit` and `-p "/cc-cmds:design-audit-unattended <스냅숏 design_doc>[ --base]"` — ` --base` exactly when the snapshot's `design_scope` is `base` — and route it like the first audit; a re-convergence row reading `재수렴 판정=재설계 필요` additionally re-plans through `replan_due[]`. Absent — a halt, a crash, no literal — → `blocked` for the key with `사유=골격급 재수렴 종단 술어 거짓`, and no second re-convergence. A second dispatch on the same key while the first is live is refused by the gate's live-attempt rule, so dispatch it once.

**The fresh audit asks for no second re-convergence.** It reads itself as a re-audit, reports what remains, and when skeleton-grade items still stand it parks at `Step 7 / 골격급 재발` — `재수렴 요청=아니오` on its row — and a person answers it through the shift skill's 「Handing on a person's answer to a halt」.

#### Dispatching the split stage

When the snapshot's `design_scope` is `base`, `steps[]` carries exactly one step whose `skill` is `split`, and the audit is complete as above, dispatch it — `--segment -`, stage kind `split`:

```
gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment - \

Wait on it with `gate.sh wait --manifest <매니페스트> --segment <step id>`. The dispatch's surface is `워크트리쓰기`, the same as the design and audit dispatches — the gate grades a `skill` act from its table, so declaring `외부상태변경` here buys nothing; the tracker writes are authorized one by one, inside the stage, by their own `--reach 협업`. The stage is complete when its artifact predicate holds: the literal `베이스 분할을 마쳤습니다.` in its stream, and a registry at `<메인>/docs/design-base/<slug>.tickets.md` whose head line starts `<!-- cc-design-base-tickets v1; ` with a `doc-sha256=` equal to the document's current sha256, every `티켓` and `베이스` row `발행됨` (`문서만` when the tracker is `없음`) and every `관계` row `걸림` or `문서만`. Take 「Re-attaching a cut stage」 first — a row it re-attaches goes nowhere else here. Past that section, `외부 종료`, `크래시` — `한도 종료` read exactly as `크래시` — and a `공허한 성공` with no entry in `pending_approvals[]` whose `blocks` is the step id may be dispatched afresh, with the command above, on the next attempt number. **A fresh split is safe where a fresh design is not**: the split resumes from its registry, and a row already `발행됨` is never published again, so a second process over a partial registry finishes it rather than duplicating it. **A `크래시` whose stream holds no 429 envelope and a `공허한 성공` buy one fresh dispatch and no more** — count fresh attempts on the rows already read the way 「Dispatching the design stage」 does, and read the envelope the way 「Re-attaching a cut stage」 does; when the last row is one of these two and two or more fresh attempts already stand, dispatch nothing, write C2 — and C3 when the manifest carries it — as `불가능` citing the last `stage-result` row, and propose done, which the gate records as `무효화`. `외부 종료` and a `크래시` carrying the envelope keep the window open. A `공허한 성공` that opened an approval on the step holds C2 (and C3) `보류` on that approval instead. Every other class stops the split as a halt record does above.

#### Dispatching the visual stage

When `steps[]` carries exactly one step whose `skill` is `visual`, and every step its `depends_on` names — the audit, or the design when the plan has no audit — ended `정상 완료`, dispatch it — `--segment -`, stage kind `visual`:

gate.sh act --manifest <매니페스트> --kind skill --target <home alias> --segment - \
  --cutpoint 커밋 --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \

```

Wait on it with `gate.sh wait --manifest <매니페스트> --segment <step id>`. The stage is complete when its artifact predicate holds: the literal `시각 디자인을 검토 통과로 확정했습니다.` in its stream, and the document's visual sidecar reading `**상태**: 검토 통과`. Either alone is a `공허한 성공`. The visual step is not a segment and its rows carry `세그먼트=-`. **A visual step that did not end `정상 완료` — a halt included — holds only the screen slices**: plan and dispatch every slice whose `**화면**` field reads `없음` as if the step had not been there.

A slice whose `**화면**` reads `없음` never waits. **The predicate** is `visual-check.sh approval <설계 문서>`, read through the gate as `gate.sh exec … --surface 읽기 -- <plugin root>/orchestrator/visual-check.sh approval <스냅숏 design_doc>` — the helper's absolute path is argv0 and nothing stands before it, because the gate grades its own helper by subcommand only when called that way, and behind `bash` the read is refused whenever the auto-resolve switch is off; exit 0 is a predicate that holds, anything else one that does not. When a screen slice's turn comes and the predicate already holds, plan and dispatch it as any slice, with no judgment — unless a person closed its `시각-승인` as `거부` or `무효` in this run, which item 5 settles.

**The fixed judgment.** The judgment that waits is one per screen segment, always in the same words, because its id is a hash of the run, the segment and the question:

```
gate.sh act --manifest <매니페스트> --kind judgment --target <home alias> --segment <화면 세그먼트> \
  --cutpoint 커밋 --surface 읽기 --snapshot-digest <H> --emit-digest \
  -- 등급=2 '판단 부류=시각-승인' '기준=시각 승인 대기' '근거=<화면 세그먼트> 의 화면이 고정 좌석에서 구현 승인되었는가'
```

Its `막는 세그먼트` is the screen segment, never the visual step id. Resubmitting it never reaches the two-questions-per-segment cap, which counts distinct ids. Once a `자율 승인` row carries its id in `해소 승인`, do not submit it again: a resubmission after the adoption is refused as spent. **Exit 0 on a resubmission is not an adoption by itself**: the approval is adopted only when that row carries `결정=채택`. A row carrying `결정=거절 소비` is a person's `거부` or `무효` spent, and it leads to item 5, never to item 3.

1. **A screen slice's turn with no predicate.** For that slice and for every planned slice whose `선행` reaches it, write a `segment` `park` row with the plan row's `선행` and a `스코프=cone` `blocked` row anchored on it with `원인=막힘` and `'사유=시각 승인 대기'` — the pair this section calls a visual-wait park — before any branch or worktree is cut for them, and then submit the fixed judgment on the screen segment — one per screen segment when several are waiting. A slice not planned yet gets no row: the planning rule keeps it back while its `선행` is parked. When the predicate already holds, the gate closes the approval as `승인` inside that act and adopts it, so go to item 3. When it does not, the act ends on exit 5; under the **CFI-S4 exception** of the shift skill that holds the screen segment and its `선행` followers and the shift keeps dispatching the work outside them, naming the waiting slices in `막힌 지점`.
2. **Nothing left outside the held set.** End with `사유=승인`. The seat asks the person, naming `/cc-cmds:visual <설계 문서>` to run on the pinned seat and telling them to answer with the label `승인` once they have approved there; an answer in free words does not close the question, so the seat asks again for the label. On each turn read `answered_judgments[]` and the predicate: when `answered_judgments[]` carries that segment's `시각-승인` as `거부` or `무효`, go to item 5 whatever the predicate says; otherwise, when the person's `승인` stands or the predicate holds, submit the same fixed judgment again — it closes and adopts the approval. While a screen slice waits, do not propose done: the open `시각-승인` counts against termination condition 2.
3. **Adopted and the predicate holds.** Adopted means a `자율 승인` row with `결정=채택` carries the id in `해소 승인`. On a segment this run's shift left in a visual-wait park, write `상태=실행중` with the plan row's `선행` and dispatch its implementation as any planned slice. A `park` the fixed-graph driver wrote is not taken over: that run has its end row, the gate refuses its dispatches, and a new run plans the screen slices afresh.
4. **Adopted and the predicate is gone.** A sync or a re-publish removed the `**구현 승인**` line after the adoption. Do not submit the judgment again; leave the slice at `park` and write in `막힌 지점` — and the morning report — 「고정 좌석에서 `구현 승인` 을 다시 쓸 것」. When the predicate holds again, item 3 dispatches it under the approval already closed.
5. **Refused.** A person closed the `시각-승인` as `거부` or `무효`: the screens are not to be built. The segment is already `park`, so submit the same fixed judgment again to consume the refusal (`결정=거절 소비`), and settle the clauses that need those screens as `불가능` citing that answer. Until it is consumed the segment stays held. **A consumed refusal does not make the segment `실행중` again**: its exit 0 is not an adoption, the segment stays `park` for the rest of the run even when the predicate holds, and the gate refuses an implementation dispatch to it.

The same three walls stand around these items: the open `시각-승인` that refuses a dispatch to its segment, the `park` row, and the gate's own refusal of an implementation dispatch carrying a screen slice while the predicate does not hold or after a person closed its `시각-승인` as `거부` or `무효` — which is what stops item 4's or item 5's slice if it were dispatched anyway.

#### Planning the segments

Segment planning starts only after the audit has ended as above, or straight after item 5's freeze check when the plan names no audit step.

**A plan with no `implement` step plans no segment.** When `steps[]` names no step whose `skill` is `implement`, the graph ends at the design — or at the audit, when the plan names one — and there is nothing to plan. Once item 5's freeze check passes and, when the plan names an audit step, the check after the audit in 「Dispatching the audit stage」 passes too, nothing is left to dispatch: propose done, with each clause's evidence the design (and audit) step's `stage-result` row and the document's freeze line. Do not settle a clause as `불가능` because no segment exists: in that state termination condition 1 holds, so when every clause is settled satisfied the gate records the proposal as satisfied.

The snapshot's `슬라이싱` field is the read: its branch (`미통치`, `선언통치`, `선언불완전`), the slice ids in declaration order, and each id's branch name and worktree path. A slice the planning rule below defers gets none of the three calls — no `git fetch` and no `git worktree add -b` either — until that rule plans it. **For each slice, in declaration order, three calls:**

1. `gate.sh exec … --surface 읽기 -- git fetch` against the slice's target.
2. `gate.sh exec … --surface 워크트리쓰기 -- git worktree add -b <슬라이싱 의 브랜치> <슬라이싱 의 워크트리> <베이스>`.
3. The plan row, which the gate fills from the frozen document rather than from this loop:

   ```
   gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <slice id> \
     --cutpoint <token> --surface 읽기 --snapshot-digest <H> --from-declaration \
     -- 상태=계획됨 워크트리=<슬라이싱 의 워크트리>
   ```

   Pass no `레포`, `선언 파일 집합`, `선행`, `절단점` or `리뷰 정책`: under `--from-declaration` the gate refuses them, takes them from the document's `## 구현 슬라이싱`, and requires `워크트리` to be the derived path. On `미통치` there is one segment whose id is the plan's implementation step id.

**A slice with a `선행` is planned only once its predecessor's `segments[]` entry reads `"착지": true`**, so its branch is cut from a base that already carries that landing. That value is the dispatch floor's own landing judgment, and it covers both a segment whose last `segment` row is `머지됨` or `완료` and one parked after a `머지됨` — unless that merge still owed this run its apply. **A slice is planned when two conditions hold together**: every `선행` token's predecessor reads `"착지": true` in its `segments[]` entry, and every `머지 순서` token of the slice — read from the snapshot's `슬라이싱.세그먼트[]`, because a slice with no row yet is not in `segments[]` — already has a `segment` row. A slice whose `선행` is `없음` and whose `머지 순서` tokens all have rows is planned and dispatched at once, cut from the current base. A `머지 순서` token with no row yet (that slice still waits on its own `선행`) defers the slice until the row appears, and a slice carrying both lists follows the same product: with D `선행` A and D `머지 순서` C, D waits for C's row even after A has landed. Planned earlier, the slice is refused with exit 2 by the floor that requires every token to name a segment this ledger knows. The two imports below — a predecessor an earlier run already merged, and one the manifest's `선행 착지` row names — apply to a `머지 순서` token as well, and the planning act writes that predecessor's row itself; without them the row would never appear and the slice would never be planned. With C `머지 순서` B and B `선행` A, B is planned after A lands, and C is planned once B's row exists and runs alongside B. Pass no `머지 순서` on the planning row: the gate writes it from the declaration and carries it forward. **A predecessor an earlier run of the same document already merged needs no row from this loop**: the planning act above finds it in that run's ledger, checks its `머지 커밋` against the base branch, and writes its terminal row with `출처=<that run's id>` before the slice's own row — so plan the dependent slice directly, and never hand-write a `segment` row for the predecessor (a caller's `출처=` is refused). **A predecessor no run ledger records is brought in the same way from the manifest's `선행 착지` row**, which the kickoff froze after a person confirmed it — the row is written with `출처=매니페스트`, and for a repository this run does not target the gate asks the remote whether the commit is on its default branch. When that check refuses with exit 3 (the earlier merge or the row's commit has not landed, cannot be judged, or still owes its apply, or the row's slug is not the slice's `레포`), the refusal names where it looked; write nothing more and end the shift with a `사유=중단` handoff, as for the structural refusals below. **A refusal with exit 2 saying a token 「is declared in the frozen document and has no segment row on this ledger yet」 is a deferral, not an ending**: write nothing, make no `사유=중단` handoff, say nothing of a new run, and plan the same slice again once that token has a row. Any other refusal with exit 2 naming a predecessor that no ledger shows landed — a slice the document does not declare, or one whose `레포` is not a target of this run — is the same ending: a run cannot gain a `선행 착지` row after its kickoff, so say in the handoff that a new run with that row is what plans the slice. When an earlier pass already made the slice's derived branch and worktree (the `슬라이싱` entry's branch and worktree), planning it again does not cut them a second time: skip calls 1 and 2 and issue call 3 alone. When a slice is planned, dispatch its implementation with the stage form above. **Two refusals are structural**: `선언불완전` (the refusal names the slice and the missing fields) and a resolved review policy other than `리뷰없음` on a plan that has no review step. The gate leaves the run-scope block for either inside the refusing act — this loop cannot create a run-scope block — so write nothing more and end the shift with a `사유=중단` handoff.

**A slice whose `슬라이싱` entry carries `입양` is a segment an earlier run cut**, handed to this run by the manifest's `세그먼트 입양` row: its `브랜치` and `워크트리` are that run's, and `입양` names the run — or is `-` for a branch a person cut outside any run, which has no earlier run, ledger or halt answer and is otherwise routed the same way. The branch and the worktree already exist, so skip calls 1 and 2 and issue call 3 alone, with `워크트리=<슬라이싱 의 워크트리>` as for any slice. The gate plans it only when that worktree is the target's, has that branch checked out, the earlier run did not land the segment, and none of the earlier run's stages is still running on it; on its refusal (exit 3, naming which) write nothing more and end the shift with a `사유=중단` handoff. **An answer the earlier run took and never handed on comes first.** When the earlier run's ledger holds a person's `중단 답` on the segment that no later `stage-result` row of it took up, and that answer is `재수렴` to an implement stage's binding-tier stop (CFI-U3 BT-STOP) or one an `이월` row of that ledger names (a carry act of that run found no account with room before its deadline and kept the answer for the next run), the planning act copies the halt record under this run's `halt/` and writes the answer as this run's own `중단 답` row with `출처 런` and `출처 기록`; read the snapshot again and route the `answered_halts[]` element, whose `origin_run` names the run the person answered in, by 「Handing on a person's answer to a halt」 before the review below — a binding-tier `재수렴` by item 5, an answer an `이월` row named by item 3's carry act. Until that carry act takes the answer, the gate refuses every other dispatch on the segment, the review included, with exit 3 and names the `--carry-answer` line. Any other open answer stays with the earlier run — its route re-attaches the halted session, which is that run's — and the planning act names it in a warning; carry that warning into the handoff's `막힌 지점` so the seat can put the question to the person again, and go on with the review. **An adopted segment's first stage is a full review, not the implementation** — its code is already on the branch. Push the branch first (`gate.sh exec … -- git push origin <슬라이싱 의 브랜치>`) so that the pull request's head is the worktree's HEAD, then dispatch the review of the pull request the entry's `PR` names, the way a segment's first review is dispatched; its findings come back through 「Re-dispatching the implementation after review findings」. **Open no pull request for it**: `PR` is the segment's pull request, and the merge row carries that number.

#### Pushing and opening a pull request

Every `segments[]` element carries `브랜치`, `HEAD`, `원격 팁`, `PR` (`번호`, `상태`, `HEAD`), `원격 단계` and `리뷰 줄`. **The target's cutpoint comes first, because `원격 단계` does not read it.** Below `push` (`커밋`, `브랜치`) nothing is pushed and no pull request is opened: dispatch the segment's review with `리뷰 줄` straight away, whatever `원격 단계` reads, and issue no `remote-check`. At `push`, push on `push 필요`, and where it then reads `PR 필요` open none — dispatch the review with `리뷰 줄`. From `PR` up: `push 필요` → push the segment branch (`--cutpoint push --reach 협업`); `PR 필요` → open its pull request (`--cutpoint PR --reach 협업`); `PR 있음` → dispatch the review with `리뷰 줄` and carry `PR.번호` as `PR=` on the `머지됨` row; `불일치` → write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` block whose `사유` names the remote tip, the PR head and the worktree HEAD; `미상` → read the remote again with `gate.sh act --kind remote-check --target <alias> --segment <id> --cutpoint 커밋 --surface 읽기 --reach 협업` (nothing after `--`) and read the snapshot again. Where this session's root carries a Bash hook of its own, issue the push or the pull request bare, then `gate.sh admit --request last` with no `--cutpoint`, then the same bytes once more; otherwise through `gate.sh exec`. A bare push names the remote and the branch (`git push origin <브랜치>`): outside the segment worktree the gate refuses a `HEAD` or `@` refspec and a push naming none with exit 2, and from any directory a push with anything before `git` (`env`, `command`, `nice` and the like). A ticket for a push is honoured only while that repository's HEAD, refs and push settings are the ones the gate graded; after a commit, a fetch or a changed setting in between, issue the push bare and admit it again.

**A refusal by the target's own hook is not retried.** `guard_refusals[]` lists each one with `조건`: while it reads `같음` the gate refuses the same act in the same form with exit 3. When the refused act is one the segment cannot do without and nothing this loop can do moves the condition — a commit, a `remote-check` after the remote moved — there is no shift-halt site for this loop to use: write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` block whose `사유` names the refusal by the element's `행위 다이제스트` and `형태`, never quoting `명령` or `거절 문면` — the gate call is itself judged by the same guard, so a `사유` carrying the refused words is refused too — then end the shift with a `사유=중단` handoff. The `park` makes the segment terminal, so the next shift does not walk into the same refusal.

#### Merging and applying a segment

**Whatever the review policy, merge a segment only when its snapshot `머지 대기` is empty.** A non-empty `머지 대기` names the predecessors, by `선행` or `머지 순서`, that have not landed yet: do other work, or wait as 「Waiting on a stage」 chooses. A refusal with exit 3 that names such a predecessor and its `상태` means the same — wait — whether the refused act was the merge or another act leaving the worktree whose grade the gate could not read; it is not **Any other cause** below, and nothing is written for it. A predecessor that was parked has already parked this segment through its cone.

**Below the `머지` cutpoint nothing is merged.** `다음` does not read the target's cutpoint, so a segment whose target stops at `커밋`, `브랜치`, `push` or `PR` reads `머지` or `이월 머지` once its review passes all the same — at `PR` only once the pull request's CI has a verdict, so such a segment goes through `CI 대기` first and ends on `완료` after it. For it, check no base, merge nothing and apply nothing — the gate refuses the merge above the cutpoint, and a `머지됨` for a tip that has not landed. End the segment instead with its `완료` row, carrying the worktree HEAD the review read as its full 40-character sha, and at `PR` the pull request's number as `PR=<n>` as well:

```
gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <id> \
  --cutpoint <token> --surface 읽기 --snapshot-digest <H> \
  -- 상태=완료 커밋=<구현 워크트리 HEAD> 브랜치=<브랜치> 워크트리=<구현 워크트리> 선행=<계획 행의 선행>
```

**Check the base before the merge.** Under `선리뷰후머지`, once `review_next[]` reads `머지` or `이월 머지`, first issue the pre-authorized `gate.sh exec … -- git fetch` against the target, then write the base check — nothing after `--`, every field is the gate's:

```
gate.sh act --manifest <매니페스트> --kind base-check --target <alias> --segment <id> \
  --cutpoint 커밋 --surface 읽기 --snapshot-digest <H> --rationale '베이스 판정 — <id>'
```

The gate asks the remote where the base is (`git ls-remote`, never the local tracking ref), merges the reviewed HEAD with it in an object directory of its own, and writes a `베이스 판정` row: `일치`, `이동` or `충돌`. Read `다음` again. `머지` or `이월 머지` → merge as below. `베이스 해소` or `베이스 해소 한도` → 「Branching on `다음` after a review」. Exit 3 naming a fetch → the base moved after your fetch; fetch once more and check once more, once. Any other exit 3 names why the gate did not judge; read `다음` again, which says what comes first. The same check twice writes one row, so a check that changes nothing costs nothing.

**The merge.** For a segment whose resolved review policy is `선리뷰후머지`, merge once its review has passed — its snapshot `review_next[]` element reads `다음` `머지` or `이월 머지` (see 「Branching on `다음` after a review」). On a routed run `다음` carries the segment's CI state too: `머지` and `이월 머지` mean the worktree HEAD's observed checks are not recorded as failed, not still running and not waiting on a rerun's result — on a target whose cutpoint is `PR`, `머지` or `배포` a HEAD with no `checks` row yet reads `CI 대기`, and only a `통과` or round 0's `미등록` five minutes old lets the merge through; below `PR` such a HEAD keeps the table's value — and only on those values do you check the base and merge. A failing check, required or not, reads as one of the twelve CI values instead. **Never send `gh run rerun`, a rerun or re-request REST path, or the `rerequestCheckSuite` mutation** — the gate refuses every spelling of them; a rerun is `act --kind ci-rerun`. The merge is pinned to the implementation worktree's HEAD as its full 40-character sha with the REST merge: `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge -f sha=<구현 워크트리 HEAD> -f merge_method=merge`. The gate refuses any other value (see **Bind a remote merge** above) — not the `리뷰 HEAD` of the last cycle row, which may be recorded abbreviated; the review rule is what checks that the review read that HEAD. A `gh pr merge` without `--admin` is refused as unbound even with `--match-head-commit`, and the branch is not deleted in this argv. When the REST merge is refused with 405 — GitHub's "merge cannot be performed" — the status does not say why, so read the response body's `message` and `gh pr view <n> --json state,headRefOid,mergeCommit,mergeStateStatus` through the gate before writing anything, and branch on the cause:
- **Already merged** (`state` reads `MERGED` and `headRefOid` equals the implementation worktree's HEAD, all 40 characters — an earlier shift's merge whose record did not land, or a person's that merged what the review read): park nothing; go on to the `상태=머지됨` record below with that `mergeCommit`. **`MERGED` with any other `headRefOid`, or a `상태=머지됨` record the gate refuses, is the last bullet's case, not this one**: a commit was added to the pull request after the review, or the merge rewrote the commits into ones the gate cannot match to the worktree's tip. Recording it would put a merge of unreviewed content down as reviewed, and leaving it unrecorded would send the same merge every shift, so take **Any other cause** with `MERGED` and the `headRefOid` (or the refusal) as its `사유`.
- **A required check not finished yet** (the `message` names a required status check as expected or not yet succeeded, and `gh pr checks <n> --required` shows it pending rather than failed): this is not a refusal of the merge and nothing terminal is written. Read the checks once (`gh pr checks <n> --required`, through the gate) and do not watch them inside your turn. Still pending → write no block and no `park`; route other work, and when nothing else is dispatchable end with `대기` carrying `'CI 대기=<id>'` as *Waiting on a stage* describes. The gate wakes your successor when that segment's CI reaches a verdict, and the successor sends the same merge once more when the required checks read green.
- **A failed check, required or not** → read `다음` again and take its branch. Only when it still reads `머지` or `이월 머지` is it the next bullet's case. An exit 3 merge refusal that names the checks is read the same way: read `다음` again.
- **Any other cause** — a base that requires a merge queue, a missing required review, a conflict: no bound merge passes the gate and that merge goes to a person: write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` block whose `사유` names the 405 and the response body's `message`, then end the shift with a `사유=중단` handoff. The `park` makes the segment terminal, so the next shift does not send the same merge again. **A conflict is the base check's first.** A 405 whose `mergeStateStatus` reads `DIRTY` goes back to **Check the base before the merge** once — fetch, `base-check`, read `다음` — and takes this bullet only when `다음` still reads `머지` or `이월 머지` after it. Never merge or rebase the moved base into a branch yourself: only a `베이스 해소` dispatch does that, and what it adds is reviewed before it merges.

Under any other policy pin the same way, and issue no apply act afterwards. Either way read `gh pr view <n> --json mergeCommit` and record it:

```
gate.sh act --manifest <매니페스트> --kind segment --target <alias> --segment <id> \
  --cutpoint <token> --surface 읽기 --snapshot-digest <H> \
  -- 상태=머지됨 PR=<n> '머지 커밋=<M>' 워크트리=<구현 워크트리> 선행=<계획 행의 선행>
```

Every `segment` row this loop writes for the segment, this one and a `park` alike, carries the plan row's `선행` again. The gate does not trust `머지 커밋`; it checks it when the apply act runs.

**The apply.** After the `머지됨` row is written, read the snapshot again and look at `적용` on that segment's `segments[]` element. `없음` → the merge is the segment's end — it has no apply command, its cutpoint is below `배포`, or its handover to a person is already recorded — so issue neither the fetch nor the apply act. `대기` or `인계` → first issue the pre-authorized `gate.sh exec … -- git fetch` once more: the merge happened on the remote, and until a fetch the local clone holds neither M nor an `origin/<베이스>` that contains it. Then:

```
gate.sh act --manifest <매니페스트> --kind apply --target <alias> --segment <id> \
  --cutpoint 배포 --surface 외부상태변경 --snapshot-digest <H> -- 적용
```

The argv is the fixed token `적용`; the gate runs the frozen apply command itself after checking five preconditions it does not let any rule switch off, and it writes `적용 준비` and `완료` itself. Do not write either state for a segment that still has an apply pending: the gate refuses both from `act --kind segment`. An apply act that reaches a segment owing no apply is answered with `적용 불필요` and exit 0, and the gate writes nothing: that too is the segment's end, not a refusal. **When the apply act is refused on a precondition**: a missing or stale remote ref (precondition 4) → fetch and issue it once more, and only once. Any other precondition refusal → write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` block whose `사유` names the refused precondition number and the gate's wording, then end the shift with a `사유=중단` handoff. The `park` makes the segment terminal, so the next shift does not walk into the same refusal.

#### Branching on `다음` after a review

Once a segment has a `cycle` row and has not merged, the snapshot's `review_next[]` carries one element for it: `세그먼트`, `다음`, and the last cycle's `사이클`, `리뷰 HEAD` and `리포트 경로` (absolute). **`다음` is the only value this loop branches on after a review** — not the counts in `cycles[]`, not `review_carry`, which carries the gate's cycle cap `REIMPL_CYCLE_CAP` and re-check round cap `RECHECK_ROUND_CAP` for display only. The gate derives it from the ledger and the report by the table in `_common/pipeline-sidecar.md` §3.2, and the merge rule reads the same facts in the same order, so a branch taken on anything else meets a refusal. Take it only when that review's `stage-result` row is `정상 완료` and the segment has no live stage:

- **`머지`, `이월 머지`** → 「Merging and applying a segment」.
- **`이월`** → carry the findings over by `_common/carryover-issue.md`: one issue per finding, then the `리뷰 이월` row (`act --kind review-carry`), then read `다음` again and merge on `이월 머지`. `이월` comes only after the lead fix's re-check.
- **`수정`** → 「Re-dispatching the implementation after review findings」. **The twelve CI values come only on a routed run, where the review would otherwise merge or send a fix.** Their elements also carry `head sha`, `PR`, `실패 체크`, `재실행 회차` and `기본 브랜치`, and a `CI 대기 한도` element `상태` and `대기 시계` besides. The gate refuses (exit 3) a review fix dispatch while `다음` reads `CI 대기`, `CI 재실행`, `CI 대기 한도`, `CI 대조`, `master 대기`, `master 재합류` or `master 수리 불가`.

- **`CI 기존 실패`**, **`CI 수정 한도`** → the rerun failed again and the base branch fails the same workflows, or the CI fix budget is spent. - **`CI 대조`** → the rerun failed again while the base branch's CI is red, or after the base fixed a failure the segment does not have yet.   ```

Once the reading has moved — other signatures, another event — `다음` reads `CI 대조` again, and the match act runs once more against the new reading; a reading that differs only in its tip or in when it was observed leaves the wait as it is.
- **`master 재합류`** → the base branch fixed a failure the HEAD still has. Issue `act --kind base-check` as before a merge — when the remote tip is missing, the pre-authorized `git fetch` once and the check once more — and branch on its `판정`: `이동` → dispatch the segment's implementation with `베이스 해소: <베이스>` on a line of its own and `부류=master 재합류` beside it, `<베이스>` the check's `베이스`; the gate admits it only while `다음` reads `master 재합류` and the latest `베이스 판정` reads `이동`, and the dispatch spends no cycle budget. Once it pushes, `다음` reads `해소 리뷰`. `충돌` → read `다음` again and take the `베이스 해소` branch. `일치` → dispatch nothing; read `다음` again.

Other segments waiting on the same event stay at `master 대기`.

**`ci_early[]` sends the one rerun while the review still runs.** `다음` keeps the table's value until a review ends, so a check that failed while the segment's review is live would wait out the whole review. The snapshot's `ci_early[]` names each such segment — a live review stage, a settled round-0 failure on the worktree HEAD, no rerun spent on it — with `세그먼트`, `head sha`, `PR` and `실패 체크`. For an element, issue the same `git fetch` and rerun act as `CI 재실행` above with the element's `head sha`, although a stage is live on the segment: the gate takes the act on that predicate. Do not issue it more than twice for the same head in one shift, and do not name the segment in `CI 대기` for it — the review's end wakes your successor. **An exit 11 on it stops nothing**: write no `shift-halt` and no `park`, and leave the segment to the `CI 재실행` branch after the review ends, which takes the refusal there. Any other exit is read as that branch reads it.

**A declared segment's review carries `--slice <seg>`.** When the segment came from the document's `## 구현 슬라이싱` — its id is a slice id — every `/cc-cmds:review-unattended` dispatch for it, a full or a delta review alike, adds `--slice <seg>` to the prompt, so the review counts other slices' findings apart from this one's. The gate refuses (exit 3) a review dispatch whose `--slice` is not its `--segment`. The reviewer cannot see which slices have landed, so the same dispatch would write the same report again: dispatch the review of that segment once more, the same kind as the refused one, without `--slice`, so every finding counts as this segment's own, and name the refusal in `--rationale`. That second review's row is written as any other; a second refusal of the same kind is the review's failure, not another re-dispatch.

#### Routing a segment after its implementation ends `정상 완료`

A process A that only emitted its plan and a process B that carried it out both end `정상 완료`, so the last stage's row cannot say whether the branch now has anything to review. The snapshot's `implement_next[]` says it: one element per segment whose last `stage-result` row is an implement stage that ended `정상 완료`, with `다음`, `단계`, `plan_sha256`, `앞선 커밋` and `무커밋 구현`. When a segment has an element and is in none of `live_stages[]`, `orphan_stages[]` and `waiting_stages[]`, this subsection decides its next act; an `answered_halts[]` element on the same key still comes first, through 「Handing on a person's answer to a halt」. **Do not dispatch a review for a segment whose element reads a `다음` other than `리뷰`.** Such an element comes before the segment's `review_next[]` element too: after a re-implementation's process A, `review_next[]` already reads `확인 리뷰` while this element reads `구현`, and the implementation goes first — the gate admits it past the cycle cap for that reason. The value is the gate's, derived from the ledger and the segment worktree, and no stream, memory or git probe of your own overturns it.

- **`리뷰`** → the last run carried a plan out and the branch is ahead of its base. Dispatch the review as 「Spelling a review dispatch」 says.
- **`구현`** → the last run only emitted its plan, or the branch has no commit over its base. Dispatch the implementation in the form 「Re-dispatching the implementation after review findings」 shows, `<n>` being the segment's last `cycle` row's `사이클`, or `1` when it has none, and `· 수정 대상: …` added only when the segment's `review_next[]` element reads `수정` or `CI 합류 수정` — with the `CI 합류: <head sha>` line as well on the latter. Write no phase into the prompt: the stage resolves A or B from the ledger itself. When the gate refuses the dispatch (exit 3), do not fall back to a review: write a segment `park` row and a `스코프=cone` block with `'사유=구현 재파견 거절'` and the refusal text in `근거`.
- **`사람`** → three implementation runs after the segment's last void boundary left no commit. Write a segment `park` row (with the plan row's `선행`) and a `스코프=cone` block with `원인=막힘` and `'사유=무커밋 구현 한도'`, whose `근거` names the element's `무커밋 구현`, its `plan_sha256` and `앞선 커밋 0`, and go on with the other segments.
- **`판정 불가`** → the segment worktree is gone or no base ref resolves, so whether the branch carries a commit cannot be read. Write a segment `park` row and a `스코프=cone` block with `'사유=구현 산출 판정 불가'`.

#### Spelling a review dispatch

**Every review dispatch of a segment starts from the line the gate prints.** `gate.sh review-line --manifest <매니페스트> --segment <seg> [-- <flag>…]` prints the whole prompt, built from the segment's rows the way the fixed-graph driver builds its own: `/cc-cmds:review-unattended <브랜치> --report-path <abs>[ --slice <seg>][ --base-sha <sha>][ --declared-files "<집합>"][ <flag>…] "설계는 <문서 인자>"`. The branch and the declared set are the last values the segment's rows carried — a clipped set is read back whole from the file its row names — and the report path is the next cycle's, so a review sent again after a crash names the same report. The flags this dispatch adds go after `--`: `--recheck <리포트 경로>` for a re-check, the three `--basis-*` flags of a delta, the three `--resolve-*` flags of a resolution review, and `--no-slice` for the one review that answers a refused other-slice section, which drops `--slice` and never reaches the prompt. The gate puts them before the `설계는` directive, because the review reads its document argument from there to the end. Pass the printed line as the one argument after `-p`, in single quotes, under `-- review -p '<line>'`, and change nothing in it: its `--report-path` is the cycle's canonical report, and the gate refuses a review dispatch naming any other (exit 2). **Declare why the review goes** with `--trigger '<토큰>'` before `--`, on the `act` and on its `plan` alike: one of `첫 리뷰`, `리뷰 P0`, `리뷰 P1`, `CI 실패`, `베이스 충돌`, `버전 경합`, `리베이스`, `해소 리뷰`, `중단 답`, `중단 인계` that the ledger stands behind for the segment, or `라우터 판단` together with `--trigger-reason '<사유>'` only when none of those holds. Anything else is exit 2 with no row, and the refusal prints the tokens that hold, so redeclare one of them; a recovery dispatch declares none. The lead fix takes only the line's branch and directive (「Branching on `다음` after a review」), and the recovery dispatch is spelled as 「Recovering a review stage that crashed」 says, with the report path of the review it recovers. **Do not rebuild these arguments from an earlier stage's stream log or from memory**: no row keeps an earlier prompt, and the grep that looks for one finds the skill's own text. Exit 3 means no row of the segment names a branch — there is nothing to review yet.

#### Re-dispatching the implementation after review findings

When a segment's `review_next[]` element reads `다음` `수정`, that review's `stage-result` row is `정상 완료`, and the segment has no live stage, dispatch the implementation again with the review report as its fix target. The values are already in the snapshot's `cycles[]` and `문서 인자`:

```
gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <seg> \
  --cutpoint <token> --surface 워크트리쓰기 --snapshot-digest <H> --emit-digest \
  -- implement -p "/cc-cmds:implement-unattended <문서 인자> \"세그먼트 <seg> (사이클 <n>) · 선언 파일: <files> · 수정 대상: <리포트 절대 경로> 의 P0·P1\""
```

`<n>` is that cycle row's `사이클` and the report path is made absolute as 「Dispatching a review cycle in delta mode」 item 2 says. When the element reads `CI 합류 수정` instead, the same directive carries ` · CI 합류: <head sha> · 실패 체크: <…> · PR: <…>` after `의 P0·P1`, the three values the element's. The gate refuses a prompt whose document argument differs from the snapshot's `문서 인자`. Once the fix ends, the next review is that subsection's to dispatch. The gate refuses (exit 3) a review while no implementation or lead fix followed the last `cycle` row and the segment's worktree HEAD is still that row's `리뷰 HEAD` — the same HEAD is not reviewed twice. **The gate caps the cycles**: it counts the segment's `cycle` rows at every implementation dispatch and refuses with exit 3 once they reach `REIMPL_CYCLE_CAP` (2), unless `다음` reads `재구현`, or reads `확인 리뷰` with a `정상` re-convergence after the last `cycle` row, no lead fix after it and the segment's `implement_next[]` element reading `구현` — the same re-implementation's run after its process A. On that refusal dispatch no implementation and read the segment's `다음` instead: past the cap it is a step of the segment's ladder — `리드 수정`, `확인 리뷰`, `재수렴`, `재구현` — or a value that ends the review loop — 「Branching on `다음` after a review」 routes each.

#### Dispatching a review cycle in delta mode

A segment's second and later review cycles re-read almost everything the first one read. A **delta** cycle reads only the files changed since the segment's last full cycle for new findings and re-adjudicates every P0/P1 that cycle raised; the review skill and the gate decide whether it holds, and this loop only offers it. **If the segment's last `stage-result` row reads `종류=review` with `종단 부류=크래시`, `한도 종료` or `외부 종료`, go to 「Re-attaching a cut stage」 and then, for a `크래시` or `한도 종료` it declines, 「Recovering a review stage that crashed」 before dispatching anything from here** — a fresh dispatch early-stubs the report path that subsection reads its roster from. Five things, in order:

1. **Basis selection.** Filter `cycles[]` to this segment and take, among the rows whose `모드` is `전체` or empty, the one with the numerically largest `사이클`. **`사이클` is a JSON string in the snapshot**, so a string maximum picks `"9"` over `"10"` and offers a basis the gate then refuses as stale, on every re-dispatch alike; compare it as an integer, which is what this expression does — `[.cycles[] | select(.["세그먼트"]=="<세그먼트>" and (.["모드"]=="" or .["모드"]=="전체"))] | max_by((.["사이클"] | tonumber?) // -1)` — and a `null` result means there is no basis. None → dispatch a full review exactly as before. One → carry that row's `사이클`, `리뷰 HEAD` and `리포트 경로` into the `/cc-cmds:review-unattended` prompt as `--basis-cycle <n> --basis-review-head <sha> --basis-report-path <abs>`, alongside the `--report-path`, `--base-sha` and `--declared-files` you already pass. All three or none: the skill treats a partial set as absent.
2. **Path resolution.** The basis row's `리포트 경로` may be relative to the target's base. You hold the manifest path, so build `dirname(<매니페스트>)/../../<경로>` and pass the absolute result; an absolute value goes through as-is. No new snapshot key exists for this.
3. **The row's mode is copied from the report, never from the dispatch.** After the stage ends, read the report overview's `- **리뷰 모드**: …` line and write `모드` and `기준 사이클` on the `cycle` row from that line: `- **리뷰 모드**: 전체` → `모드=전체` (or omit both fields); `- **리뷰 모드**: 델타 (기준 사이클 <n>, 기준 리뷰 HEAD `<sha>`)` → `모드=델타 '기준 사이클=<n>'`. The skill degrades to a full review when any eligibility check fails, and only the report says whether it did. The gate compares the row against the report on every `cycle` write and refuses with exit 2. **There are two repairs, and the refusal's wording says which one applies.** A mode mismatch — the row says one mode and the report the other — is repaired by rewriting the row to what the report says. Every other refusal of a delta claim (the basis number or head on the report line, the basis row, its report, the ancestry, a `사이클` not above its basis) that still stands once the row's `사이클` is this cycle's number and its `모드`·`기준 사이클` match the report line is repaired by **no** row: rewritten as `모드=델타` it meets the same check again, and rewritten as `모드=전체` it meets the mode comparison, because the report still says `델타`. Re-dispatch this segment's review as a full review **without the three basis flags**, and write no `cycle` row until a report the gate accepts exists.
4. **No new question point.** When a basis exists, attempting delta is the default. Whether it holds is decided by the skill's eligibility checks and the gate's write-time checks, not by asking.
5. **The snapshot window is a limit, stated rather than hidden.** `cycles[]` is the ledger's last twenty `cycle` rows, so a segment whose basis row has been pushed out of the window by other segments' cycles gets a full review. That errs toward reading more, never toward a false delta.

#### Recovering a review stage that crashed

A review stage that dies usually leaves its team's work on disk: every seat publishes into a witness scratch directory under the run directory, and `/cc-cmds:review-unattended --recover` synthesizes the report from that directory without spawning anyone. The fixed-graph driver dispatches that recovery on its own; this loop has to dispatch it too, or a crashed review's witness is never read and the next dispatch buys the whole review again. **Evaluate this before re-dispatching a crashed review** — a fresh review early-stubs the same report path, and that stub replaces the ledger block the recovery reads its roster from. **Every review dispatch this loop issues carries the absolute `--report-path` `gate.sh review-line` prints**, the ordinary ones included: that is the gate's canonical report of the cycle, and the gate refuses a review dispatch with any other path or none (exit 2) — a report elsewhere could land on another review's, or relative to a segment worktree that is torn down, where no session holds its path and item 2 blocks every crash, so this subsection never fires.

**A probe answers only when its output carries `게이트 통과`.** Every read below goes through the gate, and a gate refusal exits non-zero with nothing on stdout — the same observation as `grep` finding no line or `ls` finding no file. The refusal these reads meet most is exit 4, a stale snapshot digest, and it is routine exactly where they sit: right after a stage's row lands and right after the recovery ends. So a call whose output lacks that line is a refusal whatever its exit code, and never branch on the refused call. **Only exit 4 is retried here**: re-read `H` and issue the same probe again, **at most three times in a row for one probe**. Every other refusal code does what 「Reading the exit codes」 says for it — 6 is not re-declared to match, 7 stops, 11 is not retried — and a code of 1 with no gate line means the shell rejected the line before the gate ran. On a call that carries the line, the command's own exit code is the answer: for `grep` and `ls`, 0 is a match or a present file and 1 is none; any other code means the probe did not run as written (an unresolved path, a bad argument), which is not an answer either — fix the probe when the fault is in its own argv. **A probe that stays unanswered ends the subsection**: when the retries reach three, when the table forbids retrying its code, or when the fault is not one the router can fix in the argv, write item 3's `blocked` form with `사유=리뷰 <class> — 복구 판정 읽기가 답하지 않는다 (<exit code>)` and dispatch nothing. Reading a refusal as a file fact is not harmless: at item 3 it parks the segment while the witness is still on disk, and no second recovery is allowed for the same crash. Five things, in order:

1. **One terminal class triggers it.** None of the values below is in the snapshot — `segments[].마지막 스테이지` carries only the segment id on this path — so read the segment's `stage-result` rows from the ledger with a read through the gate: `gate.sh exec … --surface 읽기 -- grep -nF '| 세그먼트=<id> | 스테이지=<id> | 종류=' <원장 경로>`, and take the last line. The row the gate writes carries `종류=<stage kind>`, `실행 버전=<attempt>` and `종단 부류=<class>`. Only `종류=review` with `종단 부류=크래시` or `종단 부류=한도 종료` belongs to this arm — the two take one disposition — and only once 「Re-attaching a cut stage」 has declined it — continuing the review's own session finishes the round and the synthesis that this recovery can only rebuild from what was published; every other class is routed as before and is not a recovery target. `<class>` in every `사유` of this subsection is that row's own `종단 부류`. A `--recover` dispatch that ends `크래시` or `한도 종료` is not recovered again — record it under item 3's `blocked` form as `리뷰 복구 종단 부류 <class>`. Reading the ledger here has the standing the delta section's read of the report has: an artifact the stage just produced, read to write a row, not a decision carried across turns.
2. **A report that already carries the termination predicate is not recovered, and a report path you do not hold is not rebuilt.** The report path is the `--report-path` passed on that review dispatch — the canonical path the review line printed, the only one the gate let through, and the same value the ordinary `cycle` row's `리포트 경로` comes from. The gate records it on that dispatch's own `자율 승인` row as `리포트 경로=<path>`, never clipped, so read it from the ledger through the gate whichever session issued the dispatch: `gate.sh exec … --surface 읽기 -- grep -nE '^- .자율 승인. .*\| kind=skill \| 결정=act \| 대상=[^|]* \| 세그먼트=<id> \| .*\| 리포트 경로=' <원장 경로>`, and take the last line's `리포트 경로`. When no such row carries it — a dispatch written before the field existed — do not reconstruct the path by listing `docs/reviews/`: record item 3's `blocked` row with `사유=리뷰 <class> — 원래 리포트 경로를 원장에서 얻을 수 없어 복구를 파견하지 않는다` and dispatch nothing. With the path in hand, **first check that the file exists** with `ls <report path>` through the gate. On a call that carries `게이트 통과`, a non-zero exit means no file: the stage died before its early stub, so there is no completed report — skip the predicate test and go straight to the basis-flag check below and then item 3, whose Zero branch is where such a crash lands. Grepping an absent file exits 2, which is not an answer, so the existence check comes first. With the file present, test it through the gate: `grep -qE '^- \*\*발견 요약\*\*: 🔴 P0 [0-9]+건 \| 🟠 P1 [0-9]+건 \| 🟡 P2 [0-9]+건 \| 🟢 P3 [0-9]+건' <report path>`. A match means the file already holds a completed report — dispatch nothing and record `사유=리뷰 <class> — 리포트에 종료 술어 줄이 이미 있어 복구를 파견하지 않는다`. With no match or no file, **a review dispatched with the three basis flags is not recovered.** The recovery arm does not carry the delta mode into its report — its `리뷰 모드` line is absent or reads `전체` — so a report built from a delta corpus would reach the `cycle` row as a full review, and the delta section's basis selection would take that row as the next full basis with nothing refusing it. Re-dispatch the segment's review as a full review without the three basis flags, as the delta section's item 3 repair does, and write no `cycle` row for the crash. **A crashed re-check stays a re-check**: when the crashed dispatch carried `--recheck <cap report>`, the re-dispatch and the item 4 recovery carry the same `--recheck <cap report>`, because without it the report counts only new findings and an item the lead fix recorded as `수정 불가` drops out of `발견 요약` — a `0/0` the `다음` table reads as `머지`.
3. **Name exactly one witness directory, or dispatch nothing.** Each directory is `<run-dir>/cc-team-witness-<slug>.<tag>.XXXXXX`, and its `.attempt` stamp holds the stage id the gate handed the stage, verbatim — on this path `<segment>#<attempt>`, with `<attempt>` the row's `실행 버전`. Enumerate and compare in one read, with no shell glob: `gate.sh exec … --surface 읽기 -- grep -rlxF --include=.attempt '<segment>#<실행 버전>' <absolute run-dir>`; each printed file whose parent directory is named `cc-team-witness-*` is a candidate. A glob that matches no directory fails in the shell before the gate runs, which looks like an empty answer and is not one. `-x` makes the comparison whole-line, so `S1#2` does not take `S1#21`. **Match on the stamp, never on the directory name** — the name carries a sanitized tag — **and never choose by mtime**: attempts of one segment interleave, and mtime order lies.

   Every `blocked` row in this subsection takes this one form, and only `사유` changes:

   ```
   gate.sh act --manifest <매니페스트> --kind blocked --target <alias> \
     --cutpoint <token> --surface 읽기 --snapshot-digest <H> --emit-digest \
     --rationale '<why>' \
     -- 스코프=cone 원인=막힘 '사유=<사유>' '근거=<the stage-result row>' '앵커 세그먼트=<id>'
   ```

   - **Exactly one** → item 4.
   - **Zero** (the call carries `게이트 통과`, `grep` exits 1 and prints nothing) → the stage died before its first spawn and nothing is on disk to recover. **When the item 1 row reads `종단 부류=크래시` and `일시 원인=예` and item 2 found no report file**, the review died of a dropped connection with nothing saved: dispatch the same cycle's review again, as a fresh dispatch with the same `--report-path` and the same flags as the dispatch that crashed, and add `--recovery '전송 단절'` to the act — `gate.sh act … --kind skill … --recovery '전송 단절' -- review -p "<the crashed dispatch's prompt>"`. This session's own turn reached the API after the crash, and that is the evidence the connection is back; nothing else is probed. The gate checks the premises from the ledger and allows two such dispatches per cycle; when it refuses with exit 3, or when the row does not read `일시 원인=예`, write the `blocked` form above with `사유=리뷰 <class> — 시도 <n> 의 위트니스 디렉터리가 없어 Step 4 미도달, 복구를 파견하지 않는다`.
   - **Two or more** → the `blocked` form above with `사유=리뷰 <class> — 시도 <n> 에 위트니스 디렉터리 <k>개, 지명 불가: <every candidate path>`. Dispatching without a name buys a stage that is certain to fail: with no `--scratch-dir` the recovery arm lists the candidates and recovers nothing.
4. **The dispatch.** Stage kind `review`, the same target as the review it recovers, both paths absolute:

   ```
   gate.sh act --manifest <매니페스트> --kind skill --target <alias> --segment <id> \
     --cutpoint <token> --surface <token> --snapshot-digest <H> --emit-digest \
     -- review -p "/cc-cmds:review-unattended <target> --recover --scratch-dir <abs witness dir> --report-path <abs original report path>[ --recheck <abs cap report>]"
   ```

   Carry no `--base-sha`, `--declared-files` or basis flags; the recovery reads only the directory and the report's ledger block. Carry `--recheck <abs cap report>` exactly when the crashed review was a re-check — its dispatch carried that flag (item 2) — with the same value. Issue it as a harness-tracked background command like every stage. It pins a new attempt of its own, so its `stage-result` row is not the crash it recovers.
5. **The `cycle` row comes from the recovered report, and only from a clean one.** The report is clean when all four hold: the recovery's `stage-result` row reads `종단 부류=정상 완료`; the report path now matches item 2's termination predicate; the file carries no `- **발견 요약(부분 복구)**:` line (test it with `grep -qF -e '- **발견 요약(부분 복구)**:' <report path>` — the `-e` keeps the leading `-` from being read as a flag); and no `<report path>.recover.md` exists beside it (`ls <report path>.recover.md` through the gate — a non-zero exit means absent only on a call that carries `게이트 통과`). Otherwise write no `cycle` row — a partial-recovery line is deliberately not the predicate, and a diversion to `.recover.md` means the report path holds a report this recovery did not write — and record item 3's `blocked` form naming which: `리뷰 복구 종단 부류 <class>`, `부분 복구`, or `.recover.md 로 우회`. Do not dispatch a second recovery for the same crash.

   From a clean report, read the `리뷰 HEAD` line with a probe anchored at the line head that also requires the value: ``grep -E '^[-*[:space:]]*\*\*리뷰 HEAD\*\*: `?[0-9a-f]{40}`?$' <report path>``. Exactly one printed line is the value; no line, or more than one, is absent. An unanchored probe is not enough — a finding that quotes the label matches it, and a label with no 40-character sha behind it is no source for the field. **No `리뷰 모드` line is required.** Item 2 already refused to recover a review dispatched with the basis flags, so the recovered report is a full review, and a report with no mode line is read by the gate as `전체`, which is the truth here.
   - **`리뷰 HEAD` present** → write the `cycle` row: `P0` and `P1` from the `발견 요약` line, `리뷰 HEAD` from that line's sha, the report path as `리포트 경로`, the crashed review's cycle number as `사이클`, and no `모드`·`기준 사이클` fields.
   - **`리뷰 HEAD` absent** → the recovery arm is not bound to emit that line and nothing may stand in for it, so a required field of the row has no source. Do not park the segment for that: write no `cycle` row and re-dispatch the segment's review as a full review **without the three basis flags**, carrying an absolute `--report-path` like every review dispatch. That is what a crashed review got before this subsection existed, so a clean recovery never leaves the night worse off than no recovery would. This re-dispatch is a review, not a second recovery.
