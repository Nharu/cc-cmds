# autopilot seat — re-kickoff, items 2–8 of Step 1.0

**A person's re-kickoff and the seat's run the same items.** The seat's own re-kickoff (`act2-seat.md` 「Seat re-kickoff」) performs items 2 through 7 below with the substitute each item names under **Seat (`--auto`)**, skips 7.8, and prints item 8's screen. A person's re-kickoff takes none of those substitutes and passes no `--auto`; its output is unchanged. The seat's `--asked` file is `${TMPDIR:-/tmp}/cc-rekick-seat-<원천 런 id>.asked` (empty when no wait was answered), and a must-wait question an item meets is asked as that section says, never substituted.

2. **Integrity.** `rekick.sh verify --prev <id> --base <원천 base>`. On `판정 실패`, say in one line which check failed (the `검사 … 실패` lines name it) and go to Step 1 as a first kickoff — there is no partial carry. On `통과`, keep the three `해시` values; every later call is bound to them. **Seat (`--auto`):** the same call; `판정 실패` is no successor run and one terminal line, never a first kickoff.
3. **Targets.** The target list is the source manifest's `## 대상` rows (the `대상` lines of `verify`), not an entry judgment — this path does not run Step 1. Run Step 2's disk verification for each row (main worktree and common git directory, base branch, remote slug, `실행 워크트리`) and compare with the row's identity fields byte for byte. A target that matches is confirmed without a question. Only a target that does not match takes Step 2's confirmation; when its `원격 슬러그` or `공통 git 디렉터리` moved, end that question's text with its permission fields verbatim — 「이 대상에 이어지는 권한: 절단점=…, 리뷰 상한=…, 종단 상한=…」 — a worktree that only moved does not take the tail. The home target is the row carrying `홈=예`; there is no home question. Then do what Step 2 does next: resolve `<base>` by Step 6's rule, mint the run id, create the kickoff trace. That fixes the new run id and the new `킥오프 일시` (the trace's first line). If this `<base>` differs from `<원천 base>`, treat the home target as one that failed verification and ask its confirmation. A re-kickoff whose source and disk are unchanged asks nothing here. **Seat (`--auto`):** the same verification; a target that fails it, and a home target under a different `<base>`, is a must-wait question (key `대상확인 <별칭>`), asked before the run id is minted.
4. **Graph.** `rekick.sh graph --prev <id> --base <원천 base> --expect-sha256 <매니페스트 해시> [--accepted <별칭,…>]`. Its `건너뜀` lines are the steps removed with their grounds; `그래프 바뀜` means 5l is asked, offering the drawn plan as the proposal. **Seat (`--auto`):** no `--accepted`; `그래프 순수` is approved under the text `좌석 재킥오프`, and `그래프 바뀜` is no successor run — one terminal line naming the changed plan, after `단계=중단` is appended to the trace — because the seat cannot approve a plan change for a person.

   4b. **Adoption.** `rekick.sh adopt --prev <id> --base <원천 base> --expect-sha256 <매니페스트 해시>`. It writes nothing and prints one line per segment the source left unlanded: `입양후보<TAB><세그먼트><TAB><브랜치><TAB><워크트리><TAB><PR><TAB><HEAD>`, or `입양불가<TAB><세그먼트><TAB><PR 또는 없음><TAB><사유>`. A candidate's worktree, branch, open pull request and its head, read at this call, still equal what the source's last gate-written `원격 판독` row for the segment recorded, the pull request comes from the target's own repository and its base is the target's base branch. A candidate line may end with tail cells: `마지막행=park` with `원인=<행 종류>:<원장 줄 번호>` or `원인=없음`, `중단기록=<기록 이름>` per unanswered halt record of the segment, and `이월=재수렴` when the gate would carry the source's `재수렴` answer. No line means nothing to adopt. Question 6.9, the rows of 7.1 and 7.2, and item 8's lines all come from these lines. **Seat (`--auto`):** add `--auto` — a segment whose last row is a `park` it never landed from is then `입양불가` with the reason `park`.
5. **Defaults and the deadline.** `kickoff-defaults.sh --carry <원천 base>/docs/pipeline-run/<id>.plan.md --kickoff-at <3 의 킥오프 일시> --expect-sha256 <매니페스트 해시>`, its standard output saved byte for byte to a scratch file under `${TMPDIR:-/tmp}` — the blank-rows file 7.2 hands over. A non-zero exit means the source moved after it was verified: say so in one line and stop — no new run is started. `마감 ok` is the new deadline; any other `마감` row means 5e is asked once, with no silent fallback to the defaults file's `deadline`. **Seat (`--auto`):** add `--auto` to the call. When the previous interval cannot be carried it falls back to the new `킥오프 일시` plus the source `재킥오프` row's `길이` and marks the `마감 ok` row `출처=길이`; 5e is never asked, and any row other than `마감 ok` is a `--carry` failure — no successor run.
6. **Questions — these nine and no others** (anything else is carried, not asked; a person who wants a different value calls again with an intent, which is a first kickoff):
   1. a target that failed verification in 3 — Step 2's confirmation; the answer rewrites only that target's identity fields;
   2. each `대상추가` line of `graph` — Step 2's confirmation and that target's 5b–5d; accepting one re-asks 5p and 5q with the carried rows as the first option, no recommendation tail, and 「이 런의 모든 대상에 적용」 on each; a refused one does not become a target;
   3. each `빈칸` row of `--carry` — one 5o confirmation for all of them; every confirmed scalar row is carried into the draft as `--set <범위>:<키>=<파일 값>` (the row's own scope, key and file value, verbatim), each confirmed row is recorded in the `--asked` file as its own `5o <범위>:<키>` line with the row's scope cell verbatim, and a confirmed `auto-adopt` or `act-allow` row goes into the `--rows` file;
   4. `그래프 바뀜` — 5l;
   5. a Step 3 check that now fires (the stage rules status, the visual-fidelity marker, a residual item of the frozen document) — run Step 3 and ask what it asks;
   6. a deadline `--carry` could not compute — 5e, once; record the answer as given under `5e` and the absolute instant it was resolved to, once, under `5e 값`;
   7. a carried value today's vocabulary refuses — a `질문` line of `verify` (an auto-adoption class), a cutpoint outside today's `CUTPOINTS`, a rule key that can no longer be turned off — its original question, never a silent fix or drop;
   8. a `질문 베이스설계` line of `verify` — whether to bind to the changed base contract;
   9. each `입양후보` line of 4b — whether to take over that segment. Ask 「이전 런 <id> 의 세그먼트 <세그먼트> 를 이어받을까요? PR #<n> · 브랜치 <B> · HEAD <h 앞 12자>. 이어받으면 새 런은 이 PR 의 전체 리뷰부터 시작하고, 다시 하면 새 브랜치에서 처음부터 하며 옛 PR 은 그대로 둡니다.」 When the line carries `마지막행=park`, add that fact and the cause row its `원인` cell names — the row kind and its ledger line number, or 「원인 행 없음」 for `원인=없음`. For each `중단기록` cell, name the record and add 「이 기록은 원천에 남고 이어지지 않습니다」. For `이월=재수렴`, add 「원천의 재수렴 답이 이어집니다 — 새 런은 문서를 재수렴하고 구현한 뒤 리뷰합니다」. The two options are `이어받기 — <세그먼트> · PR #<n> · <B> · <h 앞 12자>` (the default) and `다시 하기 — <세그먼트> · PR #<n>`; record the chosen label verbatim under `입양 <세그먼트>`. A segment on an `입양불가` line is not asked about.

   Record each question asked and its answer verbatim as one `<키><TAB><답 축자>` line in a scratch file under `${TMPDIR:-/tmp}` — the `--asked` file — with the keys `rekick.sh` reads: `대상확인 <별칭>`, `대상추가 <별칭>`, `5p`, `5q`, `5e`, `5e 값`, `5l`, `5o <범위>:<키>`, `7.7 절단점 <별칭>`, `7.7 룰 <키>`, `7.7 자동채택`, `7.8`, `입양 <세그먼트>`. A key asked again is recorded again; the last line of a key is the one that counts.

   **Seat (`--auto`):** of the nine, the seat asks only the must-wait ones — 6.1, 6.7 and 6.8 (and the hook check's `질문` row) — and substitutes the rest: 6.2 adds no target (no `--accepted`); 6.3 keeps the previous values (no `--set`, no `--rows` from it); 6.4 is item 4's substitute; 6.5 prints the status line of `stage-rules.sh status` as a notice — with 「ClickUp 발행 슬라이스가 머지된 플러그인에서 이관」 and the `migrate` command beside it when that line says untagged — and runs nothing else, carries the source's visual-fidelity marker byte for byte (`있음(인가)` included) with a notice, and only notices a residual item; 6.6 is item 5's substitute; 6.9 is not asked — 7.1 takes over every candidate 4b's `--auto` call printed, and no `입양` key goes into the seat's `--asked` file. The seat's answers go into the seat's `--asked` file under the same keys.
7. **Writes, in this order — any failure stops before the next write and nothing is started.** **Before 7.1, run Step 6's deadline re-check on the new deadline** — `마감 ok`'s value, or 5e's resolved value. On `지남`, ask 5e again, append its `5e` and `5e 값` lines to the `--asked` file, and render with the new value: the re-check comes before the draft so that the value written is the value `verify-subset` checked, and the draft is never edited after it.
   1. `rekick.sh render-manifest --prev <id> --base <원천 base> --run-id <new> --kickoff-at <ts> --deadline <새 마감> --expect-sha256 <매니페스트 해시> --expect-grant-sha256 <인가 기록 해시> --arg '<$ARGUMENTS>' --asked <파일>`, adding `--targets <파일>` with the target rows when 6.1, 6.2 or 6.7 changed one, `--rows <파일>` with the `사전 인가` and `자동 채택` rows 6.2, 6.3 or 6.7 took, `--set <범위>:<키>=<값>` per 6.3 scalar row, `--rule <키>=<켬|끔>` per 6.7 rule answer, `--bind-base <verify 의 지금 해시>` on a 「묶는다」 answer to 6.8, and `--visual-marker <값>` from 6.5. The seat writes a row for every candidate the call derives. `--auto` fixes `승인 문면` to `좌석 재킥오프` and `사용자 확인 문면` to `좌석 재킥오프 <원천 런 id>` plus ` / <답>` per answer, and adds `좌석 연쇄=<k> | 뿌리 런=<id> | 원인=<종료 토큰>` to the provenance row; it refuses with exit 3, printing no draft, when `k` exceeds the source's `연쇄 상한` — no successor run.
   2. `rekick.sh verify-subset <초안> <원천 매니페스트> --expect-sha256 … --expect-grant-sha256 … --asked <파일>`, with the same `--set` entries as 7.1 and, whenever there is one, `--blank-rows <5 에서 저장한 파일>` — each `--set` entry must equal one `빈칸` row of it in scope, key and value — `판정 통과` or stop, naming the failed checks. Its `입양` check fails when the seat's `--asked` file carries an `입양` key, and otherwise asks only that each row is one this call derives. When `입양` is the only failed check, render once more with `render-manifest --auto --no-adopt` and verify that draft without the flag; on `통과`, notice every 4b candidate as `재검증불일치` and go on with that draft. Any other failed check, or a second failure, is no successor run and one terminal line.

Exit 3 means a shift, a relay, a stage or a fresh waiter is still alive in the source — stop like any failure above, because `detect` judged it stopped and that judgment no longer holds. Exit 2 whose message names `--cause` or `--successor` as an unknown argument, or `end-abandoned` as an unknown verb, means the source is pinned to a gate copy older than this verb — the call is forwarded to that copy before the verb is dispatched, and a copy without the flags stops on the first one it does not know: it is not a failure of this re-kickoff and does not stop it. Judge it by that shape, in either language the copy may speak: a copy pinned after the gate's messages turned English prints `gate: unknown argument: --cause`, `gate: unknown argument: --successor` or `gate: unknown verb: end-abandoned`, and one pinned before prints `gate: 알 수 없는 인자: --cause`, `gate: 알 수 없는 인자: --successor` or `gate: 알 수 없는 동사: end-abandoned`. Say in one line that the source's pinned gate copy is older than this verb, so this re-kickoff could not close the source, and go on — do not predict when its watchers leave, because they run that same older copy. Any other exit 2 stops like any failure above.

**An adopted segment is the new run's from its row alone.** The re-kickoff does not take the first kickoff's last adoption step of recording the worktree as the target's `실행 워크트리`: the target rows stay byte for byte the source's, and planning and the snapshot read the worktree from the `세그먼트 입양` row. The fixed driver (`run.sh` — the path a deferred kickoff starts through `fleet.sh dispatch`) does not read `세그먼트 입양` rows and does such a segment over; a re-kickoff is never deferred, so its adoption rows are consumed only on the router's shift path.

**A stop after the trace exists appends `단계=중단` to it first** (CFI-9) — a failed `--carry`, a failed `verify-subset`, an interview copy whose hash does not match.
