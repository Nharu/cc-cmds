# 시각 디자인 공유 계약 — 생성, 검토, 모델, 다듬기

`visual`(대화형), `visual-unattended`(무인 생성)와 `visual-publish-unattended`(무인 발행 — `수정 요청` 을 받아 다시 생성할 때)가 함께 읽는 규칙이다. 화면을 어떻게 만들고, 어떻게 검토해 통과시키며, 어느 모델의 누가 무엇을 돌려주고, 수정 목록을 어떻게 다듬는지를 정한다. 연결 파일의 문법은 같은 디렉터리의 `sidecar.md` 가 소유한다. 이 파일의 규칙은 두 팔에 똑같이 걸리고, 팔마다 다른 것은 각 스킬 본문이 말한다.

## 1. 디자인 시스템과 토큰

- **토큰 값은 정규화하지 않는다.** `oklch(...)`, `#rrggbb`, `rgb(...)`, `hsl(...)` 을 쓰인 바이트 그대로 둔다. 색 공간 변환이 필요한 스택이면 그 변환은 토큰을 소비하는 구현의 몫이다.
- **테마 래퍼를 축자로 보존한다.** `@media (prefers-color-scheme: dark)` 나 `:root[data-theme="dark"]` 봉투를 벗기지 않는다 — 벗기면 어두운 테마 토큰이 조건 없이 걸려 테마 전환이 깨진다.
- `tokens.css` 는 사용자 정의 속성 블록만 담고, `</style` 를 (대소문자 무관하게) 담지 않는다 — 화면 머리의 토큰 블록(§2)에 바이트 그대로 들어가기 때문이다. `tokens.md` 는 토큰마다 한 줄 `--이름` → 값 → 쓰임을 분류 표제(`### 색`, `### 간격`, `### 그림자`, `### 글꼴`, `### 모서리` … 실제로 있는 것만) 아래 적는다.
- Design System 아티팩트에 올리는 목록은 `project/tokens.json` 의 `{"tokens":[{"name","value","usage"}]}` 꼴이다. `tokens.css` 의 사용자 정의 속성마다 `name` 은 속성 이름, `value` 는 값을 바이트 그대로, `usage` 는 `tokens.md` 의 쓰임이다. 테마 래퍼는 목록에 담지 않고 `tokens.css` 에 남는다. 이 목록은 레포에 두지 않는다. 화면 캔버스가 디자인 시스템을 쓸 때는 같은 목록을 `project/ds/<폴더>/tokens.json` 사본으로 싣고 색인의 `designSystems` 에 기록한다.

## 2. 화면 생성 규칙

- **화면은 `var(--…)` 만 쓰고, 그 정의는 머리의 토큰 블록이 담는다.** 색·간격은 토큰 변수로만 적는다. 토큰 블록 밖에서 `:root` 를 다시 선언하지 않는다. `var(--x, #fff)` 의 대체값도 리터럴이다.
- **외부 자원을 부르지 않는다.** 이미지·글꼴·스크립트·스타일을 `http:`·`https:`·`//`·IP 리터럴·상대 경로로 부르지 않는다. 그림은 인라인 SVG 나 인라인 `data:` URI 로 넣는다. 허용되는 바깥 참조는 발행 뒤 캔버스 런타임 `./support.js` 하나뿐이다.
- **접근성 문턱**: 글자 대비는 WCAG AA(본문 4.5:1, 큰 글자 3:1)를 실제 토큰 값으로 재서 넘긴다. 터치 대상은 최소 44px 정사각형이다. 선언된 뷰포트마다 반응형으로 확인하고, 흔한 폭에서 가로 스크롤이 생기지 않는다.
- **요구 화면과 상태를 빠짐없이 담는다.** 설계 문서가 말한 화면마다, 그 화면이 가질 상태(빈 상태·로딩·오류·비활성·포커스)를 화면 안에 보인다.
- 금지 목록(§5)의 항목을 쓰지 않는다. 레포 `system.md` 가 `**금지 해제**` 로 끈 id 는 예외다.

**토큰 블록.** 화면 한 장이 로컬 검토 렌더·캔버스·구현 번역 어디서나 같은 입력으로 그려지도록, 화면 파일이 토큰 정의를 직접 담는다. 두 팔의 모든 화면(대화형 생성, 무인 생성, 발행 스테이지의 다시 생성)이 머리에 다음 꼴의 블록 하나를 둔다.

```text
<style data-cc-tokens>
<docs/visual-system/tokens.css 의 바이트 그대로>
</style>
```

- 여는 줄은 앞뒤 공백을 뺀 내용이 정확히 `<style data-cc-tokens>` 인 줄이고, 닫는 줄은 그 뒤 처음으로 나오는, 앞뒤 공백을 뺀 내용이 정확히 `</style>` 인 줄이다. 블록 내용은 두 줄 사이의 줄들이다.
- 블록 내용은 `tokens.css` 와 줄 단위로 바이트가 같다. `tokens.css` 끝에 줄바꿈이 없는 것만 차이로 보지 않는다. 값 정규화도, 테마 래퍼 제거도 하지 않는다(§1).
- 블록은 `<head>` 안, 화면의 다른 `<style>` 보다 앞에 둔다.
- 화면이 쓰는 모든 `var(--x)` 의 `--x` 는 이 블록이 정의한다. 화면의 자기 `<style>` 은 `var(--…)` 만 쓴다.
- **블록의 바이트는 저자가 아니라 부모가 채운다.** 생성 저자는 머리에 빈 블록(여는 줄과 닫는 줄만)을 두고, 부모(스테이지 또는 대화형 좌석)가 파일을 쓰기 전에 §7 의 채우기 순서로 그 사이를 `tokens.css` 바이트로 채운다.

**무인 화면 형식.** 무인 팔은 화면마다 외부 자원 없이 홀로 렌더되는 HTML 문서 한 장을 만든다. 머리에 토큰 블록을 담고, `<x-dc>` 감싸기나 `{{구멍}}` 없이 값을 리터럴로 적으며, `./support.js` 를 부르지 않는다. 발행은 이 파일을 캔버스 아트보드로 그대로 올린다. 파일은 `sidecar.md` §1 의 화면 사본 자리에 둔다.

화면을 스택의 부품·상태·라우팅으로 옮기는 판단은 구현의 몫이다. 화면은 빌드 입력이지 구속 문서가 아니다.

## 3. 검토 루브릭

회차마다 새 검토자 하나가 화면 전부를 읽고 발견과 판정을 낸다. 검토자는 앞 회차의 검토자가 아니다 — 같은 눈은 자기가 놓친 것을 다시 놓친다.

**다섯 축**

1. **방향 충실도** — 인터뷰 기록 `## 시각 방향`(대화형에서는 사람이 답한 방향)의 분위기·밀도·레퍼런스를 따르는가.
2. **디자인 시스템 준수** — 색·간격·글꼴·모서리가 토큰 변수이고 `tokens.md` 의 쓰임과 맞는가. 리터럴 값과 토큰 블록 밖의 `:root` 재선언이 없는가.
3. **요구 화면·상태 포괄** — 설계 문서가 요구한 화면과 상태가 모두 있고, 선언된 뷰포트마다 반응형인가.
4. **접근성** — §2 의 대비·터치 문턱을 넘는가. 포커스가 보이는가.
5. **아티팩트 형식 충실도** — §2 의 형식(무인은 토큰 블록을 담은 일반 HTML, 구멍·외부 참조 없음)을 지키는가.

**분류**

- `치명` — 화면이 렌더되지 않거나, 렌더 이미지가 토큰이 비어 배경·색·간격 없이 그려졌거나, 요구 화면이 없거나, 외부 참조가 있다.
- `주요` — 축 하나를 실제로 어긴다. 금지 목록 `판단` 항목 위반과 기계 검사 발견(§4)은 언제나 `주요` 다.
- `사소` — 고치면 낫지만 통과를 막지 않는다.

**판정은 구조 규칙이다.** `치명` 이나 `주요` 가 하나라도 있으면 `REJECT`, 없으면 `ACCEPT` 다. 검토자의 전체 의견은 판정을 바꾸지 않는다. 판정을 내지 못한 회차는 통과하지 못한 회차로 센다.

**금지 목록 읽기.** 검토자는 그 팔이 받은 금지 목록(대화형은 `visual-config.sh bans`, 무인 생성은 `visual-config.sh snapshot --part bans`, 무인 발행은 호스트 금지 목록 파일을 읽어 둔 사본)의 `판단` 항목을 루브릭으로 읽고, 해제된 id 는 건너뛴다. 목록에 없는 새 「AI 티」 패턴을 찾으면 수정 목록이 아니라 금지 후보로 낸다 — 형식은 `sidecar.md` §2 의 `### 금지 후보` 줄이고, id 는 목록에 이미 있는 id 와 겹치지 않는 `[a-z0-9-]+` 다.

**렌더.** 검토용 렌더 이미지는 `visual-capture.sh ref <화면> --out <트리 밖 임시 디렉터리>` 로 찍어 검토자에게 넘기고, 회차가 끝나면 지운다. 렌더할 수 없는 머신에서는 HTML 원본만으로 검토하고 사이드카에 `**검토 렌더**: 불가(환경)` 를 적는다. 그것은 선언된 강등이지 정지가 아니다. 렌더 없이 그 사실을 적지 않고 `검토 통과` 를 쓰지 않는다.

**검토자 봉투.** 검토자는 읽기 전용이고, 돌려주는 것은 판정 한 줄(`판정: ACCEPT|REJECT`)과 발견 목록이다. 발견 한 줄은 `<분류> | <축> | <화면 id> | <무엇이 어디서 어긋났는지>` 이고, 금지 후보는 따로 `금지 후보:` 아래 줄로 낸다.

## 4. 기계 검사

`plugins/cc-cmds/orchestrator/visual-check.sh scan <화면 파일>… --bans <금지 목록 파일> [--lifts <system.md>] --tokens <base>/docs/visual-system/tokens.css` 이 내는 발견(`<규칙 id> <파일>:<줄> <문면>`)은 회차마다 수정 목록에 `주요` 로 들어간다 — 단, `token-block` 과 블록이 원인인 발견은 §7 의 채우기로 고쳐지고 수정 목록에 들어가지 않는다. 내장 규칙은 `token-color`(토큰을 쓰지 않은 색), `token-space`(토큰을 쓰지 않은 간격), `external-ref`(`./support.js` 와 인라인 `data:` 밖의 참조), `token-block`(토큰 블록이 정확히 하나가 아니거나 `tokens.css` 와 바이트가 다르다), `token-undefined`(파일 안에 정의 없이 `var()` 로 참조된 사용자 정의 속성, 이름마다 한 건)이고, 금지 목록의 `마크업`·`스크립트` 항목이 제 id 로 더해진다. 블록이 정확히 하나이고 일치할 때에만 블록 줄의 `token-color`·`token-space` 가 지워진다. `--tokens` 의 파일이 없거나 `</style` 를 담으면 종료 2 이고, 호출처는 파일 유무로 갈라 `--tokens` 를 빼지 않는다 — 그 디자인 시스템을 고칠 때까지 화면 검사가 서지 않는다. 보고 머리의 세 줄(검사 밖인 계산된 색, 해제된 id, 토큰 블록 대조)은 검토자에게 그대로 넘긴다 — 계산된 색은 검토자가 본다.

기계 검사는 검토 통과의 조건이다. 마지막 회차에 발견이 남아 있으면 `ACCEPT` 가 아니다.

## 5. 금지 목록 한 줄

```
<id> | <종류> | <설명> | <패턴 또는 ->
```

- `#` 으로 시작하는 줄은 주석이다. 구분자는 앞뒤 공백을 낀 ` | ` 이고, 셋째 구분자 뒤 전부가 패턴이다.
- 종류는 셋이다. `마크업` 은 패턴을 `grep -E` 로 화면의 스크립트 밖 문면(주석 뺀)에, `스크립트` 는 스크립트 영역에 건다. `판단` 은 패턴 없이(`-`) 검토자 루브릭이 읽는다.
- 호스트 파일은 `${XDG_CONFIG_HOME:-$HOME/.config}/cc-cmds/visual-bans` 이고, 씨앗은 플러그인의 `plugins/cc-cmds/orchestrator/visual-bans.seed` 다. 쓰는 것은 사람 좌석의 `visual-config.sh seed`·`append`, 그리고 발행 스테이지 `visual-publish-unattended` 가 사람의 `금지-후보` `승인` 답 하나마다 한 번 부르는 `append` 뿐이다.

## 6. 모델과 저자 하위 에이전트

| 국면 | 키 | 기본값 | 누가 부르나 |
| --- | --- | --- | --- |
| 디자인 시스템 생성 | `ds-generate` | `fable` | `visual`·`visual-unattended` |
| 화면 생성 | `screen-generate` | `opus` | `visual`·`visual-unattended`·`visual-publish-unattended`(`수정 요청` 의 다시 생성) |
| 수정 목록 다듬기 | `polish` | `fable` | `visual`·`visual-unattended`·`visual-publish-unattended`(아래 강등 뒤) |
| 큰 화면 번역 | `implement-large` | `fable` | `implement`·`implement-unattended` |

`implement-large-threshold`(기본 300)는 큰 화면의 문턱이다 — `visual-check.sh size <화면>` 의 시작 태그 수가 그 이상이면 큰 화면이다.

값의 출처는 팔마다 하나다. 대화형 좌석은 `visual-config.sh models` 의 출력, 무인 팔(생성 스테이지와 발행 스테이지)은 `visual-config.sh snapshot --part models` 의 출력을 읽는다. 발행 스테이지에서 그 명령이 실패하면 위 기본값을 쓰고 그 사실과 사유를 종결 문면에 적는다. 둘 다 키마다 `<키> = <값> | <출처>` 이다.

국면을 맡는 것은 Agent 도구의 `model` 로 띄우는 **읽기 전용 저자** 하위 에이전트다. 파일은 부모(무인 스테이지 또는 대화형 좌석)가 쓴다. 저자가 돌려주는 봉투는 셋뿐이다.

- **생성 저자** — 파일 블록. 경로 한 줄 뒤에 그 파일의 전체 내용을 펜스로 감싸 돌려준다. 화면 파일은 머리에 빈 토큰 블록(여는 줄과 닫는 줄만)을 둔다 — 바이트는 부모가 채운다(§7). 부모는 경로가 이 국면이 쓸 자리(`sidecar.md` §1)인지 보고, 아니면 거절한다.
- **다듬기 저자** — 편집 쌍. 한 쌍은 `수정 <id>` 줄, 옛 문면 펜스, 새 문면 펜스다. 부모는 이번 회차 수정 목록에 없는 id 를 단 쌍과 id 가 없는 쌍을 거절하고 보고한다. 옛 문면이 파일에 정확히 한 번 나오지 않는 쌍과, 옛 문면이 토큰 블록 안에 걸치는 쌍도 거절한다.
- **번역 저자** — 화면 하나를 대상 스택으로 옮긴 번역문. 화면 머리의 토큰 블록은 `tokens.css` 의 사본이라 대상 스택으로 옮기지 않는다. 구현 스테이지가 그 번역문을 받아 제 파일에 쓴다.

`fable` 이 서빙되지 않으면(띄우기가 모델을 거절하면) 그 국면은 `opus` 로 떨어지고 그 사실을 보고한다. 이 배정은 `_common/team-model-tier.md` 의 팀 모델 어휘와 다른 층이다 — 저 어휘는 팀 역할의 모델이고, 이 표는 시각 국면의 저자 모델이다.

## 7. 다듬기 강등표

부모는 회차마다 검토자의 `치명`·`주요` 발견, 금지 목록 `판단` 항목 위반, 기계 검사 발견으로 수정 목록을 만들고 항목마다 id(`f1`, `f2`, …)를 단다. 금지 후보는 수정 목록에 들지 않는다. 처리는 수정 목록의 건수와 부류로 정한다.

| 수정 목록 | 처리 | `**다듬기**` 넷째 칸 |
| --- | --- | --- |
| 0건 | 다듬지 않는다 | `건너뜀` |
| 전부 기계 검사 발견이고 2건 이하 | 부모가 리터럴 값을 같은 값의 토큰 변수로 바꾼다. 값이 `tokens.css` 의 토큰 값과 바이트로 같을 때만 바꾸고, 그렇지 않은 항목이 하나라도 있으면 `opus` 저자로 간다 | `기계 치환` (넘어가면 `opus`) |
| 3건 이하 | `opus` 저자 | `opus` |
| 4건 이상 | 설정된 `polish` 모델의 저자 | `<설정 모델>` |

**토큰 블록 채우기.** 부모는 회차마다(생성 회차의 첫 쓰기 포함) 수정 목록을 만들기 전에 화면마다 토큰 블록을 채운다.

1. 여는 줄·닫는 줄 쌍(§2 의 문법)이 정확히 하나면 그 사이를 `tokens.css` 바이트로 바꾼다. 저자가 쌍 사이를 채워 냈어도 같은 바이트로 덮는다.
2. 쌍이 없거나 둘 이상이면 쌍을 모두 지운 뒤, `<head>` 여는 태그를 담은 줄 바로 다음에(그런 줄이 없으면 파일 첫 줄 앞에) 블록 하나를 쓴다.
3. 그 뒤 `scan --tokens` 를 다시 돌린 결과로 수정 목록을 만든다.

그래서 블록이 원인인 `token-block`·`token-undefined`·블록 줄 `token-color` 는 목록 건수에 들어가지 않고, 다듬기 저자나 기계 치환으로 가지 않는다(기계 치환이 블록 줄의 리터럴을 `var()` 로 바꾸는 일도 없다). 채운 뒤에도 `token-block` 이 남으면 부모가 다음 회차에 다시 채우며, 세 회차 상한(`review-cap`)은 그대로다.

다듬기는 수정 목록의 항목만 고친다. 다듬은 뒤에는 다음 회차의 새 검토자가 본다. 회차마다 사이드카에 `**다듬기**: <회차>회 — 수정 목록 <n>건 — <처리>` 한 줄을 남긴다.
